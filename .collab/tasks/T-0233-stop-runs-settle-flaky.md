# T-0233 agents 场景 22 硬停止：“中止后甲不再调用模型”偶发失败（59 → 60），查清多出的那次调用并改稳

## 目标
`ci-infra` 的 `agents` 任务里，场景 22 硬停止的最后一项“中止后甲不再调用模型”偶发失败。2026-11-14 在 PR #205
（提交 `a5eb5e1`，改动与智能体无关；运行 43547780457，job 132303000982）上是 `59 → 60`：中止报回 `done`、`aborted: 1` 之后，
等 5 秒记一次数、再等 20 秒又记一次，多了 1 次模型调用；整份验收只有这一项失败。人类 2026-11-14 要求：先查清多出的那一次是什么，
再决定改验收还是改接入包 / 工作台；判定不能放松。

查到的原因（实测与依据见核验记录 `docs/decisions/2026-11-04-agent-messaging-verification.md` 6.2 的 2026-11-14 补充）：

- 不是被叫停的那一轮晚到的调用。假模型在请求到达时就记账；`sessions.abort` 等那一轮停下才返回。
  本地对锁定镜像实测 25 次（10 次把网关限制在 0.5 核），那一轮在中止返回之后的调用都是 0 次。
- 多出的是 OpenClaw 自己按时钟跑的自动任务，落在了那 20 秒里：定时心跳（每 30 分钟，哪一刻随实例而定，在主会话
  `agent:main:main`）、memory-core 的 Dreaming（每天 03:00 UTC）、定时任务（`agent:main:cron:…`）。它们不属于被中止的会话，
  到点照常调用模型。失败那次的 20 秒约是 02:59:53 ~ 03:00:13 UTC，正好跨过 03:00:00。
  是心跳还是 Dreaming，从那次的日志分不出来（推断）；本地让定时心跳落进这段时间，现象相同（`84 → 85`）。
- 这项检查原来数的是甲的全部模型调用，所以是验收的数法有问题，接入包和工作台的中止逻辑没有问题。

做法：只改验收。假模型的记录多记 `session`（请求里 Runtime 行的会话键）和 `system`（系统提示词开头）；
这一项只数对话里的各轮：会话键和提示词都对得上的定时心跳、Dreaming、定时任务不计入、写进详情，认不出的一律照数。
等 5 秒、再看 20 秒、多一次就失败，都没变。没有采用“等调用数稳定下来再开始算”：没有晚到的调用需要等，
而且那样会放过中止几秒后才跑起来的排队消息。

- [x] 自动任务落在这 20 秒里时这一项通过：定时心跳、Dreaming、定时任务各一种，用仓库里的判定函数对真实网关实测
  （原来的数法分别是 `84 → 85`、`46 → 48`、`40 → 41`）。
- [x] 判定没有放松：没有中止、只中止了别的会话、中止后同一个会话里又跑了一轮（排队的没清掉），这一项都失败（同样实测）。
