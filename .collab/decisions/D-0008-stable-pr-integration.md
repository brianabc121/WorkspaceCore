# D-0008 并行开发、固定 PR 提交、统一集成与分层验证

## 背景
人类在当前对话明确批准方案并指派 Codex：“可以 给我写一套这个规则样式。并写在首页readme上。同时需要告知claude按照这个方案来”。因此本决策按已取得的批准发布，不再要求重复批准同一事项。

PR #232 曾因主干继续更新、任务编号冲突和全量 CI 触发范围过宽而产生重复等待。现有编号器扫描本机已知远端分支后取最大号加一，仍不具备跨会话原子占号能力。主要 workflow 对 PR 更新和 main 推送都会自动运行。

本决策替代 D-0004 的合并调度与验证门禁、D-0007 的 Codex 暂停假设；保留任务 owner / paths、独立环境、生成文件、审查与不可逆操作的既有保护。已有 Claude 任务继续由原 owner 完成，不因恢复并行开发自动转移目录或任务。

## 决策
### 1. 生效范围与当前实现状态

- Claude、Codex 按人类指派并行开发；开工从最新 main 开始，任务状态仍以 main 上的 `.collab/` 文件为准。
- 当前先人工执行本规则。通知、编号预留和集成队列统一记录在 [issue #235](https://github.com/brianabc121/WorkspaceCore/issues/235)，该 issue 不代替任务 owner / status 或正式交接单。
- 当前没有自动合并机器人、原子占号器、变更分类器或 `ci-gate`；本次不修改 workflow。现有 CI 可能仍自动跑全套，手工门禁按下表选择需要等待的结果，不能谎称未运行的检查已通过。
- 本次仅规则文档的首次发布由 Codex 完成并释放窗口；之后默认由 Claude 的一个明确登记会话担任唯一集成者。其他 Claude 会话也必须排队。接替须由现任集成者交接或人类明确指定，不得多个会话各自宣布接管。

### 2. 固定 PR 提交，不机械追赶 main

1. PR 进入验证后记录 head SHA、基线 SHA、改动类别和应执行检查，固定该候选。
2. main 有无关新提交时，不自动 merge/rebase 到 PR，也不为“保持最新”推送无业务意义的提交。
3. 确有冲突、依赖或契约变化时，由集成者核对影响，在独立集成分支生成最新 main + PR 的候选；不往对方工作分支推送。
4. 不能仅凭文件路径不同认定无关联：共享配置、依赖、迁移、权限、生成的 API 类型和运行时接入包都要检查。
5. 编号、任务记录等纯元数据冲突优先在最终合并提交处理，保留已提交的历史日志。若产品输入未变，只补元数据检查与必要的合并关联回归，不重新跑无关整套测试。
6. CI 证据必须指明实际验证的 SHA 与输入。旧 SHA 的绿色结果不能伪装成新 SHA 通过；产品输入相同的既有证据与新候选的轻量检查应分开记录。

### 3. 单一集成窗口与持久队列

- 准备合并时在 issue #235 留下 PR、head SHA、类别、检查结果、关联风险；按首次满足入队条件的记录顺序处理。
- 只有登记的集成者领取窗口，记录会话 / 分支、PR、head SHA、当前 main SHA 和验证清单；同一时刻只处理一个候选，其他代理继续开发功能分支。
- 候选验证期间，不合并其他 PR、不直接推送其他改动到 main。后来的小 PR 也不得插队；人类改变优先级时，先明确取消当前候选再重建受影响的验证。
- 集成者检查代码冲突及任务编号、迁移链、契约生成文件等语义冲突；验证所需结果成功后，用 merge commit 合并经过验证的候选。
- 发布前再次核对 PR head 与 main；发生变化时检查真实差异再决定补验范围，不笼统重跑全部 CI，也不在旧候选上盲推。禁止 force-push。
- 失败、缺少必要条件或中断时，记录原因并释放窗口，候选标为 blocked，交还作者处理；修复后重新满足入队条件。blocked 候选不阻塞其他已就绪 PR。
- 合并后确认 main 包含预期提交、必要的 smoke / 协作检查通过，再记录完成并释放窗口。同一代码输入的重复全量运行可在后台继续，不因它自动再次同步功能分支；发现 main 相关失败时停止后续集成并排查。
- 人工 issue 记录不是平台原子锁；当前依靠唯一登记的集成会话串行执行。后续自动化必须保存持久队列，不能只把 Actions `concurrency` 当作完整 FIFO 队列。

### 4. 分层验证门禁

| 改动类别 | 必须验证 |
| --- | --- |
| 非运行时文档、任务 / 交接 / 编号元数据；本次人类已授权的协作规则 | 协作校验、相对链接与格式、密钥检查、改动范围复核；涉及规则变更须有明确人类授权与独立复核 |
| 前端功能或样式 | 前端 lint、类型、单测、构建与 API 契约一致性；相关页面 / 浏览器回归 |
| 后端业务或接口 | 后端 lint、类型、相关单元 / 集成测试、OpenAPI 与生成类型一致性；受影响的前端及端到端回归 |
| 依赖、共享基础设施、Docker / Compose、迁移、安全、运行时接入包或影响范围不确定 | 对应完整集成 / 迁移 / 安全检查、平台矩阵和相关端到端验收；不确定时扩大验证 |

- 运行时提示词、嵌入脚本、workflow、工具模板与生产配置不因扩展名是 Markdown / YAML 就走纯文档门禁。
- 相关必需检查失败必须处理，不得忽略、伪造、用 `continue-on-error` 或取消必要测试来得到绿色。纯文档门禁不要求等待无关的业务全量作业。
- 通过的同一 SHA、同一输入检查保留；已确认的环境瞬态失败可只重跑失败 job 一次。再次失败、断言失败或原因不明时先排查；代码修复后重验受影响范围。
- 有能力时取消同一 PR 旧 SHA 的过期运行，不取消其他 PR、main 发布或协作同步作业；不能声明未实际执行的取消已成功。
- 未来 `ci-gate` 必须始终运行，并检查变更类别与所需 job 的结果。不能直接用 workflow 级 `paths` 跳过必需门禁，使 GitHub 一直等待 Pending；也不能让依赖失败导致门禁自身被跳过。
- 本规则不覆盖 GitHub 实际启用的分支保护 / ruleset；平台额外要求仍须满足，不能伪造旧检查或绕过限制。

### 5. 编号与审查

- 现阶段正式任务号由唯一集成者在 issue #235 登记预留后分配，作者取得编号再创建任务文件；未分配时先在 issue 提交摘要、owner 和 paths，不自行取全局最大号。
- `collab.py new` 当前仍自动递增，不能作为并行原子占号服务。工具未支持指定预留号时，由集成者按模板创建正式任务；未提交的新文件可以按已预留号整理，已有正式任务不追溯改号。T-0267 是本次发布的启动登记。
- 后续编号改造采用唯一内部 ID 并兼容旧 `T-xxxx` 引用，不能让新的展示编号重新引入共享计数竞争；本次不声称该工具已实现。
- Codex 的 PR 默认由 Claude 审查；Claude 的 PR 按人类要求安排交叉审查。审查意见留在 PR，不推送作者分支。只有当前登记的集成者可以合并，不能把“Claude”理解为所有 Claude 会话都可并行合并。
- 本次人类明确指派的规则发布走纯文档门禁与独立复核，由 Codex 完成一次启动发布，然后通知 Claude 接管默认集成职责。

### 6. 人类决定与后续工具改造

- 未授权修改人类负责的规范、修改协作协议、不可逆数据操作或进入新 Sprint，仍须由人类决定；人类当前对话已明确授权的同一事项不重复询问。
- 后续分别实施：唯一 ID / 原子占号、按改动分类的始终运行门禁、同 PR 过期运行取消、带持久状态与候选 SHA 核对的自动集成队列。
- 当前为个人账号仓库，不假定 GitHub 原生 Merge Queue 可直接启用；未来迁到适用的组织仓库时，再配置 `merge_group` 和保护规则。
- Claude 开工及每次准备合并前必须读取 README 的协作规则、此决策与 issue #235，并在通知 issue 记录已读及唯一集成会话标识。通知发布不等于对方已经读取。

## 理由
把开发并行与主干集成串行分开，避免 main 的无关推进、非原子编号和仅元数据改动导致反复整套 CI；保留真实冲突、依赖变化及合并结果的必要验证。

## 代价 / 后果
短期由登记会话人工维护队列和验证证据，工具自动化另开任务；合并吞吐按队列串行，但功能开发继续并行。当前 workflow 未改造，可能仍自动启动冗余作业；不能把规则文档当作自动化已经上线。没有关闭失败检查、放宽产品权限或新增数据迁移。

## 考虑过的其他方案
只让一个角色合并但不排队仍可插队；频繁 fetch 不能提供原子占号；直接放宽全部测试会丢失相关验证；现有个人账号仓库不直接采用组织仓库的原生 Merge Queue。采用先人工执行、再工程化队列和门禁的方案。
