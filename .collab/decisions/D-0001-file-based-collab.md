# D-0001 用仓库内文件作为 Claude/Codex 协作状态的唯一事实来源

## 背景
Claude 和 Codex 要在同一个 GitHub 仓库里协作开发。两者都没有跨会话记忆，彼此不能直接通信，
运行环境也不同：Claude 在云端会话里有专属分支并能访问 GitHub；Codex 云端任务通常在不联网的沙箱里运行。
需要一种两边都能可靠读写、人类也能一眼看懂的方式，来记录进度和交接。

## 决策
1. 协作状态全部放在仓库的 `.collab/` 下：一个任务一个文件（`tasks/`），一次交接一个文件（`handoffs/`，只增不改），
   决策单独存放（`decisions/`）。
2. 每个任务只有一个 `owner`（球权 = 下一步该谁行动），球权只能通过交接单转移。
3. 以 main 为准：状态变化和代码在同一个 PR 里，由人类合并后生效；PR 中的状态表示“合并之后”的状态。
4. 用 `scripts/collab.py`（只依赖标准库）完成状态流转，用 CI 中的 `check` 防止格式漂移和空交接单。
5. 规则写在 `AGENTS.md`（Codex 原生读取），`CLAUDE.md` 用 `@AGENTS.md` 引用，两边用同一份规则。

## 理由
- 仓库文件是两个代理都**一定**能访问的东西；GitHub Issues/Projects 在 Codex 沙箱里不一定能访问。
- 状态和代码同一个 PR 合并，二者不会不一致；`git log` 天然就是审计记录。
- 一任务一文件、一交接一文件，并行分支几乎不会在协作文件上冲突（单个 BOARD.md 必然冲突）。
- 人类合并 PR 是天然的把关点：未合并的交接不生效，杜绝两边同时接手。

## 代价 / 后果
- 交接速度取决于人类合并 PR 的节奏；着急时可以让接收方从发出方分支开工（见 `.collab/README.md`）。
- 任务文件里不记录 PR 编号（开 PR 前不知道编号），靠 PR 标题里的 `[T-xxxx]` 关联。
- 并行创建任务可能撞号：`new` 会扫描远端分支来降低概率，CI 兜底报错。
- 看板没有图形界面：用 `collab.py status` 或 Actions Summary 查看。

## 考虑过的其他方案
- **GitHub Issues + Labels 做看板**：可视化好，但 Codex 沙箱内可能无法访问，而且状态会和代码脱节。
- **单个 BOARD.md**：直观，但两个分支同时修改必然冲突。
- **代理之间用 PR 评论互相 @ 触发**：可以作为以后的自动化，但容易形成无人把关的循环，暂不采用。
