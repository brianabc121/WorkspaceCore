# D-0009 批量“车次”集成、测过即发布与停线规则（补充 D-0008）

## 背景
人类 2026-11-18 在对话中说：会有十几个开发好的需求等着合并，前面的 CI 跑得久，后面的都合不进去；
要求“参考下业内专家他们是怎么做的。再写一份方案放到github上作为版本更新执行手册”。

按 #235 的记录（2026-11-16 ~ 11-18）：
- 集成窗口一次只处理一个 PR；合并后集成会话一直占着窗口，等 main 的推送检查全部跑完（约 1 小时）才释放。
  10 次合并占窗口 52 ~ 148 分钟，中位数约 68 分钟。
- 其中多次 PR 的基线就是当时的 main，合并后 main 的内容和测过的 PR head 完全一样，那 1 小时是在重复测同一份代码。
- 最慢的 job：`ci-api / api` 约 56 分钟，`ci-infra / agents` 约 50 分钟。
- 偶发失败（Redis 连接超时一天至少 5 次等）每次再加约 1 小时，期间整条队列停着。
- 结果是吞吐上限约每小时 1 个 PR，12 个 PR 要 12 ~ 24 小时。

业内做法的调研见 [`docs/decisions/2026-11-18-merge-queue-research.md`](../../docs/decisions/2026-11-18-merge-queue-research.md)：
bors / Rust rollup、GitHub 合并队列、Zuul、Uber SubmitQueue、Google TAP、Chromium CQ、Shopify 都遵循“测的就是要合的”，
并且用**批量**摊薄 CI 时间、用**剔除 / 二分**隔离失败、把偶发失败当缺陷修。
GitHub 原生合并队列不能用于个人账号的仓库，所以先用手工“车次”模拟它的分组。

本决策只补充 D-0008，不替代它。D-0008 中没有被下面改动的条款全部继续有效：固定 PR head、唯一集成会话、
分层验证、不伪造检查、不跳过测试、编号预留、审查规则、人类决定的事项。

## 决策

### 1. 车次：一次验证一批已就绪的 PR
- 集成窗口一次处理**一个车次**。车次 = 当前 main + 若干个已在 #235 排队的就绪 PR，按排队顺序依次用 merge commit 合入一个新的车次分支，
  开一个车次 PR，只跑一次全套 CI。这是 D-0008 第 2.3 条“独立集成分支生成合并候选”的多 PR 版本，PR #242 合并 #241 用的就是这个办法。
- 只要窗口空闲、有 1 个以上就绪 PR 就发车，不为凑满而等待。车次验证期间新就绪的 PR 排下一车。
- 每车最多 **6** 个 PR；其中迁移、安全、共享基础设施、依赖、运行时接入包这几类合计最多 **2** 个，失败时容易归因。
- 人类可以给某个 PR 指定“单独发车”（相当于 Rust 的 `rollup=never`），集成者照做。

### 2. 上车条件（D-0008 的就绪条件不变，另加两条）
1. PR 固定 head 上的相关必需检查已经成功，审查（含安全审查）已完成、没有未处理的阻塞意见。
   **审查在上车之前做完，不占窗口。**
2. 上车后作者不再往这个 PR 推送。确实要改，先在 #235 说明“下车”，集成者把它从本车拿掉（见第 4 条）。

### 3. 组车时的冲突处理
- 手写代码冲突：后排队的 PR 不上本车，交还作者合入新的 main 后重新排队。
- 生成文件（`services/api/openapi.json`、`apps/web/src/services/schema.d.ts` 等）冲突：集成者在车次分支上按仓库命令重新生成，
  作为单独一个提交并写明原因；CI 的一致性检查负责核对。
- 迁移链：车次分支上 `alembic heads` 必须只有一个。两个 PR 都从同一个迁移往下接时，后排队的不上本车，由作者改迁移号后重新排队。
- 任务编号、任务日志等元数据冲突，按 D-0008 第 2.5 条在车次分支上处理，保留双方的历史日志。

### 4. 车次失败
- 失败能明确归到某个 PR（失败的测试或页面只和它改的区域有关）：把它移出，标为 blocked 交还作者，其余 PR 组成新的车次重测。
- 归不清楚：把车次对半拆开分别重测（二分），直到找到问题 PR。
- 失败的测试在“已知偶发清单”里，并且同一处失败在 main 或其他分支上也出现过：按 D-0008 只重跑失败的 job 一次；再失败按上面两条处理。
- 每次重组都开新的车次分支和车次 PR，不改写已经推送的车次分支。

### 5. 测过即发布，立即释放窗口
- 车次全部必需检查成功后，确认 main 仍是车次的基线，再用 merge commit 合并车次 PR（指定车次 PR 的 head SHA）。
  这样 main 的内容就是测过的内容，车上的 PR 在 GitHub 上会显示为已合并。
- 合并后核对 main 的 SHA、collab 检查通过，**立即释放窗口**；main 的推送检查在后台运行。
  这是对 D-0008 第 3 节“同一代码输入的重复全量运行可在后台继续”的明确规定。
- 单个 PR 的基线就是当前 main 时，它自己就是车次，同样合并后立即释放窗口。
- 合并后 main 的内容和测过的内容不一样（例如 main 在验证期间变了）的，不许合并，重新组车。

### 6. main 变红时停线
- main 的推送检查失败，集成者在 #235 宣布“停线”，查原因：
  - 已知偶发：重跑失败的 job 一次，不停线；同时确认对应的修复任务存在。
  - 真实问题：停线。修复 PR 作为下一车的**第一个** PR，可以和其他就绪 PR 同车；修复预计超过一个车次时间的，
    可以先在下一车里 revert 引入问题的合并，原作者重新开 PR 修好后再上车。
- 停线期间不发不含修复的车次。main 恢复绿色后在 #235 宣布解除停线。

### 7. 偶发失败的处理
- 每个偶发失败都要有任务跟进，优先级不低于 P1，记入执行手册附录的“已知偶发清单”。
- D-0008 的禁令不变：不得跳过、禁用、`continue-on-error` 必要测试来得到绿色。

### 8. 权限与记录
- 人类批准本决策，即授权当前登记的集成会话推送 `train/<YYYYMMDD>-<序号>` 形式的车次分支（用完删除）；
  环境不允许推送该名字时，用集成会话自己的工作分支，每车从 main 重新开始。
- 车次的发车、结果、发布、停线和解除，都在 #235 按执行手册的模板记录，写明车上每个 PR 的固定 head、车次 PR 的 head SHA 和 CI 结果。
- 执行细节、命令和留言模板见 [`docs/guides/integration-runbook.md`](../../docs/guides/integration-runbook.md)。
  执行手册可以随实际情况更新，但不得放宽本决策和 D-0008 的要求。

### 9. 后续工程任务（不在本决策中生效，分别开任务）
1. pytest 用模板库与多进程，目标是 `api` 降到 15 分钟以内（要实测）。
2. 拆分 `ci-infra / agents`，或缓存 OpenIM 镜像构建，缩短最长的 job。
3. 修复已知偶发清单中的问题。
4. 按 D-0008 第 6 节：同一 PR 旧 SHA 的运行自动取消、始终运行的 `ci-gate`。
5. 用 GitHub Actions 自动组车次，不依赖集成会话在线。
6. 是否把仓库迁到组织下以使用 GitHub 原生合并队列，由人类决定。

## 理由
- 批量：12 个 PR 每车 6 个，只需 2 ~ 3 次全套 CI，约 2 ~ 3 小时，而不是 12 ~ 24 小时；
  前面某个 PR 的 CI 慢，不再挡住后面已经就绪的 PR（它们一起上下一车）。
- 测过即发布：每车省掉约 1 小时的重复测试，又不降低保证，因为合进 main 的就是测过的内容。
- 剔除 / 二分 + 停线：保留 D-0008 “主干保持可用”的要求，失败只影响出问题的 PR。
- 这些都是 bors / rollup、GitHub 合并队列、Zuul、Shopify 等长期使用的做法。

## 代价 / 后果
- 车次失败时要剔除或二分，最坏情况下一车要多跑 2 ~ 3 次 CI。高风险类每车限 2 个，就是为了减少这种情况。
- 车次分支和车次 PR 会多一些 GitHub 记录；车上 PR 的合并记录出现在车次 PR 上，不在原 PR 上。
- 车次是“一批”上线，部署说明要合起来看。集成者在 #235 的发布记录里汇总需要重新部署的部分。
- 仍然是人工流程，依赖登记的集成会话在线；自动化在第 9 条另做。
- 本决策是协作流程的变更，只有人类改成 accepted 后才生效；生效前按 D-0008 执行。
  第 5 条“测过即释放”可以看作 D-0008 第 3 节的一种理解，但集成会话一直等全套检查跑完才释放，
  为免各自理解，也等人类批准本决策或单独确认后才执行。

## 考虑过的其他方案
- **维持一次一个 PR，只提速 CI**：CI 提速是要做的，但即使 `api` 降到 15 分钟，`agents` 还有约 50 分钟，十几个 PR 依然要排半天以上。
- **GitHub 原生合并队列**：个人账号的仓库不能用；迁到组织仓库会影响权限、Actions 额度和现有链接，交人类另行决定。
- **Zuul / Uber 式推测执行**：要同时跑多个候选，CI 并发额度不够，规模也不需要。
- **允许多个会话各自合并**：D-0004 时期出现过插队和重复跑 CI，D-0008 已否定。
