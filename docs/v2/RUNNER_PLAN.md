# 运行服务器方案（T-0134）：一台高配服务器，给所有智能体跑容器

> 状态：**草案，待人类批准**。第 14 节列出要人类决定的事项（都有推荐做法）。
> 这是 2026-11-06 对话里的“方案 A”：智能体不碰 Docker，经工作台的工具申请容器，由工作台在运行服务器上执行。
> 实施前先做核验（第 15 节 R0）：Docker Engine、gVisor、出口代理都要在锁定版本上实测，不按名称猜接口。
>
> **需求原文**（人类 2026-11-06）：
> 给我按照 A 的方案来设计。有些细节需要调整：未来我会单独开一台服务器，这台服务器将用来跑所有智能体的任务 / 测试等需求，
> 如：1. 智能体 1 号需要安装小红书进行抓取特定博主的内容；2. 智能体 2 号新写了一个项目需要跑测试流程；
> 3. 智能体 3 号需要对智能体 2 号写的项目进行实际跑一遍并作项目评估。
> 还需要创建一个页面能够对这台运行服务器的容器进行管理。之所以这样设计是因为，我只需要一台高配置服务器就可以，
> 而不是为每个智能体的服务器都是高配置。
> 这里跑容器的时候还需要设计好方案，要进行容器区分，有些容器跑完就可以删了，有些容器可能下一次还需要用。
> 为了提高效率，这里需要进行区分，智能体通过 workspace 平台调用并新建容器的时候，需要先考虑好这些事情。
> 同时还需要考虑好什么情况下容器会被回收：1. 创建容器的耗时，越耗时的容器需要尽可能发挥其价值；
> 2. 长时间不调用的容器，可能会出现占用资源的情况，可以先把它们删除掉，但是需要记录容器配置信息，方便下次智能体需要调用的时候能够快速创建容器；
> 3. 其他智能体创建的时候设置的删除回调机制，一旦触发也可以删除掉对应容器。
> 先调研看看业内专家是怎么做的，再根据我们项目的情况，写一份设计方案。

## 0. 一页看懂

```
智能体 1 / 2 / 3 号（各自的 OpenClaw 服务器，低配；仍然不开 exec、不挂 Docker socket）
   │  MCP 工具：env_find / env_create / env_exec / env_files / env_release …
   ▼
工作台（服务器 A）：权限、限额、模板、环境记录、回收策略、审计、执行记录、管理页面
   ▲  runner-agent 主动连进来（客户端证书；长轮询领指令、回报结果、每分钟对账）
   │
运行服务器（高配，一台）：runner-agent + Docker + gVisor
   ├─ 环境 A：1 号 · 常驻 · 小红书抓取（登录态和抓取进度在数据卷里）
   ├─ 环境 B：2 号 · 一次性 · 跑测试（跑完就删，只留输出）
   └─ 环境 C：3 号 · 会话 · 评估 2 号的项目（评估 Issue 关闭就删）
```

- **三层东西分开存**：模板（怎么造，长期保留）→ 环境（一个容器加它的数据卷）→ 运行（在环境里执行的一次命令）。
  删容器不丢模板和配置，下次能按记录快速重建。
- **容器分三类**：一次性、会话、常驻。智能体建容器时必须说清用途、类别、复用键和删除条件；工作台先找能复用的，找不到才新建。
- **回收分四种**：空闲到点（运行 → 停止 → 归档 → 删除记录，逐级释放）、删除条件触发（创建时登记的“回调”）、
  资源紧张时按“保留分”从低到高回收（重建越费时的分越高，越晚回收）、管理员手动。
- **隔离**：容器默认用 gVisor 运行，非 root、去掉全部 capability、限内存 / CPU / 进程数、默认没有网络，按模板放行域名。
- **页面**：智能体 → 运行服务器：总览、环境、模板、运行记录、设置；实例卡片上加“运行环境权限”。全部设置都在网页上完成。

## 1. 目标与边界

- 一台高配运行服务器承担所有智能体的重活：浏览器抓取、跑测试、把项目实际跑起来做评估。OpenClaw 服务器保持低配。
- 智能体不接触 Docker、SSH 密钥和运行服务器本身，只调工作台的 MCP 工具；工作台是唯一的权限来源。
- 容器只能从管理员批准的**模板**建；智能体可以提议新模板，管理员批准后才能用。
- 同一份方案里回答三件事：容器怎么分类、怎么复用、什么时候回收。
- V1 不做：多台运行服务器的调度（表结构留好 `host_id`）、GPU、Kubernetes、容器里再跑 Docker、安卓模拟器、网页终端。

## 2. 调研：业内怎么做

### 2.1 各家的做法

| 做法 | 是什么 | 我们借鉴什么 |
|---|---|---|
| **E2B**（AI 智能体沙箱） | 模板由 Dockerfile 定义；构建时先运行启动命令，等就绪检查通过，再给整个沙箱做快照，以后从快照建沙箱。沙箱超时后默认销毁，也可以设成**暂停**：保留文件系统和内存（含运行中的进程），暂停的沙箱不过期，可以自动恢复；暂停耗时约每 GiB 内存 4 秒 | 把费时的准备工作挪到“构建模板”时做一次；“停止但保留”是独立的一档 |
| **Daytona**（AI 代码沙箱） | 三段式自动回收：不活动 15 分钟自动**停止**（0 表示不停）；连续停止 7 天自动**归档**（移出本机）；自动**删除**默认关闭，设成 0 表示停止后立刻删 | 停止 → 归档 → 删除逐级释放资源，每级时长可配；一次性用途就是“停止后立刻删” |
| **Coder**（云开发环境） | 模板 + 工作区；工作区不活动超过阈值变为**休眠**（停止），休眠超过期限自动删除；每次活动把自动停止时间往后推（默认 1 小时） | “活动续期”：每次使用都重新计时；休眠和删除是两个不同的期限 |
| **OpenHands**（编程智能体） | 每个会话一个沙箱容器，会话结束清理容器；远程运行时支持暂停和恢复 | 按工作单元（会话）划分容器，单元结束就回收 |
| **GitHub Actions 自托管 runner** | 官方建议自动扩缩时用**一次性** runner：每个 job 一个全新环境，跑完就销毁，日志在销毁前送出。runner 主动用 HTTPS 长轮询（每次 50 秒）连 GitHub 领任务，GitHub 不需要连进 runner | 测试类任务每次用干净环境；runner-agent 主动连工作台，运行服务器不开入站端口 |
| **Kubernetes** | Job 的 `ttlSecondsAfterFinished`：完成或失败后过 N 秒自动删除（级联删除）。对象之间用 ownerReferences 记录“谁拥有谁”，拥有者没了，垃圾回收自动删掉它拥有的对象 | “跑完 N 秒后删”；删除条件挂在“拥有者”上（任务、Issue、项目），拥有者结束就回收 |
| **Modal**（无服务器沙箱） | 沙箱的文件系统快照就是一个镜像，可以用来建新沙箱；目录快照在最后一次使用 30 天后回收；内存快照（预览功能）7 天过期 | 归档时把关键目录做快照，重建时恢复；快照本身也按“最后一次使用”过期 |
| **Fly Machines** | 空闲时自动停止或**挂起**（suspend 保留内存、恢复更快，但不是所有程序都支持）；有请求自动启动；可设最少保持运行的数量 | “停止”和“挂起”的取舍；V1 只做停止，挂起留到以后 |
| **《Serverless in the Wild》**（微软 Azure Functions，ATC 2020） | 统计每个应用两次调用之间的空闲时长分布，据此决定保活多久、何时预热；比固定保活时长（例如 10 分钟）冷启动明显更少、浪费的内存也更少 | 保活时长不应该一刀切；V1 按“启动耗时”调整，V2 按每个环境的使用间隔自动调整 |
| **GreedyDual-Size**（Cao & Irani 1997，网页缓存） | 缓存淘汰时按“重新获取的代价 ÷ 占用大小”打分，再加上随时间推移的老化；GDSF 再乘上访问频率。分数最低的先淘汰 | 直接对应“越耗时的容器越要发挥价值”：重建越贵、用得越勤、占得越少，越晚回收 |
| **隔离方案** | 普通容器（runc）与宿主共享内核，不适合跑不可信代码；gVisor（runsc）是用户态内核，大多数现有镜像能直接跑，开销小，但不是 runc 的完全替代，有兼容性限制；Kata / Firecracker 是轻量虚拟机，隔离更强、开销更大 | 默认 gVisor；个别不兼容的模板由管理员明确改用 runc |
| **Docker 自身** | 资源限制（`--memory`、`--memory-swap`、`--cpus`、`--pids-limit`）；可写层限额 `--storage-opt size` 只在 overlay2 + XFS（`pquota` 挂载）上可用；`docker checkpoint`（CRIU）仍是实验功能，不支持带终端的容器 | 资源参数由 runner-agent 固定生成；磁盘限额依赖 XFS，部署时准备；V1 不依赖 checkpoint |

### 2.2 共识，以及我们怎么用

1. **先有配方，再有实例**（E2B 模板、Coder 模板、Daytona 快照）。配置和容器分开存，删容器不丢配置 → 第 3 节的“模板 / 环境 / 运行”。
2. **逐级回收**：运行 → 停止（保留磁盘）→ 归档（只留配置和快照）→ 删除（Daytona、Coder）→ 第 5、6.1 节。
3. **一次性的工作用完即删**（GitHub 一次性 runner、Kubernetes TTL、OpenHands）→ “一次性”类别。
4. **保活时长看重建代价和使用规律**（Serverless in the Wild、GreedyDual-Size）→ 第 6.1、6.2 节。
5. **删除挂在拥有者上**（Kubernetes ownerReferences）→ 第 6.3 节的删除条件。
6. **把费时的准备挪到构建时**（E2B、Modal）→ 模板构建；常用的环境可以“做成模板”。
7. **不可信代码要更强的隔离**（gVisor / Kata）→ 第 8 节。
8. **执行端主动连控制端**（GitHub runner 长轮询）→ 第 9 节。

## 3. 三层：模板、环境、运行

| 层 | 是什么 | 谁建 | 保留多久 | 重建代价 |
|---|---|---|---|---|
| **模板** | 怎么造这个容器：基础镜像（锁定 digest）、安装脚本、启动命令与就绪检查、要保存的目录、默认类别与回收时长、资源上限、网络策略与放行域名、用到的密钥名称、运行时（gVisor / runc）、附属服务（如测试用的 Postgres）。有版本；构建结果是运行服务器上的一个镜像 | 管理员在页面上建；智能体可以提议，管理员批准 | 长期；旧版本的镜像没人用就清理 | 最高：装依赖、下载浏览器，常常要几分钟 |
| **环境** | 从模板建出来的一个容器，加上它自己的数据卷（工作目录、缓存、登录态）。属于创建它的智能体，可以共享给项目成员 | 智能体经 `env_create` | 按类别和回收规则（第 6 节） | 停止的：几秒；归档的：从镜像重建 + 重放初始化步骤 + 恢复快照 |
| **运行** | 在环境里执行的一次命令（如 `npm test`）：命令、超时、退出码、输出、耗时 | 智能体经 `env_exec`；一次性环境建好就跑 | 记录保留 30 天；输出保留 7 天 | — |

每个模板都记下实测耗时：**构建耗时**、**启动耗时**（建容器到就绪）、**初始化耗时**（重放环境自己的初始化步骤）、**恢复耗时**（恢复快照）。
工作台用它们估算每个环境“重新唤起要多久”，显示在页面上，也返回给智能体。

## 4. 容器分三类

| 类别 | 用在 | 例子 | 跑完 / 空闲后 | 数据卷 |
|---|---|---|---|---|
| **一次性** | 跑一次就完，结果是输出或文件 | 2 号跑一遍测试；转一次格式 | 运行结束、取回输出后**立刻删除**；失败的保留 30 分钟（只停止，方便查看），然后删除 | 跟容器一起删 |
| **会话** | 接下来一段时间要反复用，但没有要长期保存的东西 | 3 号把项目跑起来做多轮评估；调试一个问题 | 空闲 15 分钟停止；停止 24 小时归档（不做快照）；删除条件触发时删除 | 停止时保留，归档时删除 |
| **常驻** | 里面有重建很贵或者重建不出来的东西 | 1 号的小红书抓取（登录态、抓取进度）；2 号开发中的项目 | 空闲 30 分钟停止（只释放内存和 CPU）；14 天没用归档：先把要保存的目录做快照，再删容器和数据卷 | 停止时保留；归档时做快照后删除 |

“空闲”的意思是：没有正在执行的运行，也没有被调用。每次调用都重新计时（Coder 的活动续期）。
各档时长是默认值，管理员可以在设置里改，也可以按模板改。

### 4.1 智能体建容器前必须回答的问题（`env_create` 的必填参数）

| 问题 | 参数 | 说明 |
|---|---|---|
| 做什么 | `purpose` | 一句话，显示在页面上 |
| 用完就扔，还是还要用 | `lifetime`：`once` / `session` / `persistent` | 按下表选 |
| 同一件事下次怎么认出来 | `reuse_key` | 同一件事用同一个键，如 `xhs:博主A`、`project:<项目>:dev`。一次性可以不填 |
| 什么时候可以删 | `delete_when` | 至少一个条件（第 6.3 节）；一次性默认“这次运行结束” |
| 要多少资源 | `resources` | 不超过模板上限；不填用模板默认 |
| 给谁用 | `share` | 只有自己（默认）/ 项目成员 / 指定的智能体 |

工具说明里给智能体的选择规则：

| 情况 | 选 |
|---|---|
| 跑一次就完 | 一次性 |
| 接下来几小时要反复用，没有要长期保存的东西 | 会话 |
| 里面有登录态、抓取进度、开发中的代码、很大的缓存 | 常驻 |

工作台的把关：
- **先复用**：同一个智能体（或共享给它的）已经有同模板、同 `reuse_key` 的环境，`env_create` 直接返回它（停止的会启动，归档的会重建），
  并说明“已复用”；只有传 `new: true` 并写明理由才另建。
- **提示改类别**：24 小时内用同一个 `reuse_key` 建了 3 次以上一次性环境，返回提示建议改用会话；常驻环境 7 天没用，提醒创建者确认还要不要。
- **超限额**不建，返回原因（第 8.4 节）。

## 5. 生命周期

| 状态 | 占用 | 怎么来 | 再次使用要多久 |
|---|---|---|---|
| `creating` 创建中 | 磁盘 | `env_create` | — |
| `running` 运行中 | 内存 + CPU + 磁盘 | 创建完成、启动、有人调用 | 立即 |
| `stopped` 已停止 | 磁盘（可写层 + 数据卷） | 空闲到点、管理员停止、资源紧张 | 几秒（`docker start` + 启动命令） |
| `archived` 已归档 | 只有工作台里的配置记录，加上对象存储里的快照（常驻才有） | 停止到点、资源紧张、管理员归档 | 镜像还在：启动耗时 + 初始化耗时 + 恢复耗时；镜像被清了：再加构建耗时 |
| `pending_delete` 待删除 | 同上一个状态 | 删除条件触发 | 宽限期内可以撤销 |
| `deleted` 已删除 | 只有记录（30 天） | 删除完成 | 不能恢复；同一个 `reuse_key` 再建是新的环境 |
| `failed` 失败 | 视情况 | 构建、创建或启动失败 | 管理员看日志处理 |

调用一个停止或归档的环境（`env_exec`、`env_files`）会自动唤起它；返回里带“唤起用了多久”。

## 6. 回收

### 6.1 空闲到点（逐级释放）

| 类别 | 空闲 → 停止 | 停止 → 归档 | 归档 → 删除 |
|---|---|---|---|
| 一次性 | 运行结束立刻删除（失败的停止 30 分钟后删除） | — | — |
| 会话 | 15 分钟 | 24 小时 | 归档后 30 天删记录 |
| 常驻 | 30 分钟 | 14 天 | 不自动删除；配置记录一直保留，直到创建者或管理员删除 |

**启动越慢，停得越晚**：空闲 → 停止的时长取 `max(类别默认, 启动耗时 × 20)`，最多 2 小时。
例如启动要 3 分钟的服务（加载模型、预热缓存），会话类空闲 60 分钟才停。
V2 按每个环境实际的使用间隔自动调整（《Serverless in the Wild》的做法：间隔大多在 40 分钟以内的，就保活 40 分钟）。

### 6.2 重建代价与保留分（“越耗时越要发挥价值”）

资源紧张时，工作台要选先回收谁。每个环境算一个**保留分**，分低的先回收：

```
保留分 = 重建耗时（秒） × 使用频率 ÷ 占用 × 老化系数
```

- **重建耗时**：回收这一级之后再用要多久。运行中的看启动耗时；停止的看归档后重建的耗时；
  常驻环境没有快照、数据重建不出来时记为“无穷大”，**不会被自动归档**，只会被停止，并通知管理员。
- **使用频率**：近 7 天的调用次数加 1。
- **占用**：运行中的看内存（GB），停止的看磁盘（GB）。
- **老化系数**：每空闲 7 天减半，免得很久以前很贵的环境永远占着资源（GreedyDual-Size 的“老化”）。

“越耗时越要发挥价值”还落在这几处：
- 模板镜像按同样的分数清理：构建越慢、用得越多、越小的镜像越晚清理；当前版本的镜像只在磁盘告急时才清。
- 启动慢的环境停得晚（6.1）。
- 先复用再新建（4.1）；可以共享给项目成员（第 7 节的 3 号）。
- 一个环境初始化很慢、又被反复重建，页面提示管理员“做成模板”：把它当前的文件系统存成新的模板版本（`docker commit`），以后建出来就带着这些东西。

### 6.3 删除条件（“删除回调”）

建环境时登记一个或多个条件，任何一个满足，环境进入“待删除”：

| 条件 | 例子 |
|---|---|
| `run_finished` | 这次运行结束（一次性的默认值） |
| `task_done:<任务>` | 任务完成或关闭 |
| `issue_closed:<Issue>` | 评估 Issue 关闭 |
| `project_archived:<项目>` | 项目归档 |
| `at:<时间>` | 到某个时间 |
| `idle:<时长>` | 空闲多久（比类别默认更短时才有意义） |
| `released` | 创建者调用 `env_release` |
| 总是生效 | 创建者实例被停用或删除；运行服务器被移除 |

- 条件挂在“拥有者”上（Kubernetes ownerReferences 的思路）：任务、Issue、项目由谁结束都算。
  比如 2 号建环境时登记了 `issue_closed:#12`，3 号评估完关闭了 #12，2 号的环境就会被回收——这就是“其他智能体创建时设置的删除回调，一旦触发也可以删除”。
- 判断方式：相关事件发生时立即检查，另外每 5 分钟对账一次，防止漏掉（与工作台“事件 + 周期对账”的一贯做法相同）。
- **宽限期**：一次性、会话的待删除 5 分钟后删除；常驻的 24 小时后删除，期间通知创建者（IM）和管理员，可以撤销。
  常驻环境删除前先做快照，快照保留 30 天，可以从页面恢复。
- 正在执行运行的环境，等这次运行结束（或超时）再删。
- 谁能改条件：创建者和管理员。其他智能体不能删别人的环境，只能对共享给它的环境调用 `env_release`（表示“我不用了”）。

### 6.4 资源紧张时

| 水位 | 动作 |
|---|---|
| 内存预留 > 85% 或磁盘 > 80% | 按保留分从低到高回收：先停止运行中的空闲环境，再归档停止的环境，再清理镜像，直到内存 < 70%、磁盘 < 65% |
| 新建或启动时资源不够 | 先按上一行回收；仍然不够就排队（最多 10 分钟），返回“排队中，第 N 位”，开始后用 IM 唤醒智能体 |
| 磁盘 > 95% | 紧急：拒绝新建，停止一次性运行，通知管理员（runner-agent 本地执行，不依赖工作台在线） |

不会被自动回收：管理员“保护”的环境、正在执行运行的环境。被保护的环境计入限额。

### 6.5 配置记录与快速重建（“删了也能快速建回来”）

环境归档或删除时，工作台保留它的**配置记录**：

- 模板版本（含镜像 digest）、资源、网络策略与放行域名、密钥名称（不含值）、共享范围、复用键、删除条件；
- 环境自己的**初始化步骤**：智能体用 `env_setup` 登记的命令（如 `git clone …`、`npm ci`），重建时按顺序重放；
- 常驻环境的**快照**：模板里声明的“要保存的目录”（如浏览器配置、抓取进度、代码目录）打包加密，存到工作台现有的对象存储，单个上限 5 GB（可调）。

重建 = 用模板镜像建容器 → 恢复快照 → 重放初始化步骤 → 启动命令 → 就绪检查。
页面和 `env_find` 都显示预计耗时；镜像已被清理的，会先在后台重新构建模板。

## 7. 三个例子

**1 号：抓取小红书特定博主的内容**
1. 管理员在页面上建模板 `xhs-browser`：Playwright + Chromium 镜像；网络只放行小红书相关域名（具体域名核验后填）；
   要保存的目录 `/home/runner/profile`（登录态）与 `/data`（抓取进度和结果）；默认类别常驻；内存上限 4 GB。
   或者 1 号用 `template_propose` 提议，管理员批准。
2. 1 号 `env_create(template="xhs-browser", lifetime="persistent", reuse_key="xhs:博主A", delete_when=["project_archived:<项目>"])`，
   第一次在环境里完成登录（扫码等需要人参与的步骤由管理员配合）。
3. 每天用 `schedule_wakeup` 叫醒自己，`env_exec` 跑抓取脚本，结果用 `env_files` 取回，写进知识库或附到 Issue。
4. 两次抓取之间空闲 30 分钟就停止（释放内存，登录态还在）；第二天调用时几秒内启动。
5. 14 天没用就归档：登录态和抓取进度做快照，删容器和数据卷；下次用同一个 `reuse_key` 调用时，从快照建回来，不用重新登录（只要登录态还有效）。

小红书网页版用浏览器抓取，是 V1 的做法；安卓 App 需要模拟器和 KVM，不在 V1（第 14 节 D11）。
抓取对象、频率与用途要符合平台条款和法律法规（如个人信息保护），由管理员在模板和任务里限定。

**2 号：写了一个项目，要跑测试流程**
1. 2 号的开发环境是常驻的（`reuse_key="project:<项目>:dev"`，模板 `node22` 或 `python312`），代码就在它的数据卷里，同时推到 Git。
2. 跑测试用一次性环境：`env_create(template="node22-test", lifetime="once", from_environment=<开发环境>, command="npm ci && npm test")`。
   工作台把开发环境的工作目录复制进一个全新的容器（干净环境，GitHub 一次性 runner 的做法），跑完取回输出和测试报告就删除。
3. 依赖下载慢时，模板可以给每个智能体配一个**缓存卷**（npm / pip 缓存），一次性环境挂上它，只属于这个智能体，不跨智能体共享（防止缓存被别人投毒）。
4. 需要数据库的测试，在模板里声明附属服务（如 `postgres:16` 的锁定 digest），和测试容器在同一个独立网络里一起启动、一起删除。

**3 号：把 2 号的项目实际跑一遍并评估**
1. 2 号把开发环境共享给项目成员（`share=project`，权限“复制”）。
2. 3 号 `env_create(lifetime="session", from_environment=<2 号的开发环境>, reuse_key="eval:<项目>", delete_when=["issue_closed:<评估 Issue>"])`，
   得到一份复制出来的环境：怎么折腾都不影响 2 号。
3. 3 号启动服务、跑多轮评估命令、看日志，把评估结论写进 Issue。
4. 评估 Issue 关闭 → 删除条件触发 → 5 分钟后删除。中途空闲 15 分钟会先停止，再用时几秒恢复。

## 8. 隔离与安全

### 8.1 智能体与运行服务器之间

- 智能体只调工作台工具；OpenClaw 服务器仍然不开 exec、不挂 Docker socket（`docs/AGENTS.md` 第 8 节不变）。
- runner-agent 只执行工作台下发的**固定几种指令**（第 9 节），指令里不能带任意 Docker 参数；安全参数由 runner-agent 按固定规则生成，工作台只能要求更严，不能更松。
- 运行服务器专用：不放其他业务数据，不和工作台、OpenClaw 共用一台机器。runner-agent 挂着本机的 Docker socket，等同于这台机器的 root，所以这台机器要当成可以随时重装的。

### 8.2 容器

| 项 | 默认 |
|---|---|
| 运行时 | gVisor（`runsc`）；不兼容的模板由管理员在模板上改成 runc，写审计 |
| 用户 | 非 root |
| 权限 | `cap-drop ALL`、`no-new-privileges`、不 privileged、不挂 Docker socket、不挂宿主目录（只用命名数据卷） |
| 资源 | 内存上限（`memory-swap` 等于 `memory`，不用 swap）、CPU、进程数上限；可写层和数据卷限额（需要 XFS + `pquota`，见 R0；做不到就定期测量、超限停止） |
| 文件系统 | 模板允许时根文件系统只读，`/tmp` 用 tmpfs |
| 时长 | 单次运行有超时（默认 30 分钟，模板最多 2 小时）；会话环境最长连续运行 12 小时 |

### 8.3 网络

- 每个环境一个独立的 Docker 网络，环境之间默认不通。
- 三档：**没有网络**（默认）/ **只放行指定域名**（经运行服务器上的出口代理，按域名白名单，记录访问的域名）/ **全部外网**（只能由管理员在模板上打开）。
- 永远禁止：私有网段、本机、云厂商元数据地址（如 `169.254.169.254`）、工作台和 OpenClaw 服务器的地址。由运行服务器的防火墙规则兜底，不只靠代理。
- 装依赖要用的软件源（npm、PyPI 等）按模板放行。

### 8.4 限额（管理员按实例设，下面是默认值）

| 项 | 默认 |
|---|---|
| 同时运行的环境 | 3 个（常驻最多 2 个） |
| 内存合计 / CPU 合计 / 磁盘合计 | 16 GB / 8 核 / 100 GB |
| 每小时 `env_exec` | 120 次 |
| 每天运行总时长 | 8 小时 |

整台服务器：内存按上限累计，不超卖（留出系统预留）；CPU 可以超卖到 2 倍；磁盘按水位（6.4）。

### 8.5 密钥

- 模板声明要用的密钥名称（如小红书账号的 Cookie），管理员在模板上绑定工作台密钥库里的条目；启动时以文件形式注入到 tmpfs（`/run/secrets/<名称>`），不进镜像、不进日志。
- **容器里的程序能读到注入的密钥**，所以只注入专用、权限最小的密钥。输出按已知密钥值精确匹配脱敏，再过一遍现有的密钥扫描；
  但挡不住有意编码后带出，这是已知风险，靠出口白名单和审计降低。
- 快照里可能有登录态，按密钥对待：加密保存（工作台现有的加密），页面上不能下载原文。

### 8.6 记录与通知

- 每次建、启动、停止、归档、删除、`env_exec` 都留执行记录（“AI 工具执行”，标明直接执行）和审计；命令原文脱敏后记录。
- 输出：工具最多返回最后 16 KB；完整输出最多 1 MB，存对象存储 7 天。
- 通知管理员：新建常驻环境、模板提议、常驻环境将被归档或删除、资源告急、限额用满、发现记录外的容器或丢失的容器。

## 9. 运行服务器与工作台怎么连（runner-agent）

- **添加**：管理员在页面上添加运行服务器，走现有的 SSH 自动部署流程（T-0089：先显示主机指纹、确认后安装；密码只用一次，换成专用密钥）。
  工作台装好锁定版本的 Docker、gVisor 和 runner-agent，并签发客户端证书（沿用实例的证书体系）。用户不需要在终端里做任何事。
- **连接**：runner-agent 主动连工作台的接入入口（新增 `/runner/v1/*` 路径，要客户端证书），长轮询领指令（GitHub runner 的做法）；运行服务器不需要开入站端口。
- **指令**：`build_image`、`create_env`、`start`、`stop`、`exec`、`put_file`、`get_file`、`snapshot`、`restore`、`delete`、`prune_images`、`report`。
  每条指令有 id，runner-agent 按 id 去重（重复下发不会执行两次）。`exec` 是写操作：超时或断线时记为“结果未知”，不自动重跑，由对账确认。
- **对账**：runner-agent 每分钟上报本机所有带工作台标签（`myworkspace.*`）的容器、数据卷、镜像及占用；工作台比对：
  记录里有、实际没有 → 标为丢失并通知；实际有、记录里没有 → 先停止，24 小时后删除。**没有工作台标签的容器一律不碰**。
- **断线保护**：运行超时、一次性环境的最长存活、磁盘告急，由 runner-agent 在本机执行，工作台掉线也守得住；但断线时不会自己归档或删除常驻环境。
- **指标**：沿用实例“服务器状态”的上报格式（CPU、内存、磁盘、网络），另外上报每个容器的用量。
- **升级**：页面上一键升级 runner-agent（重新部署接入包），容器和数据卷不受影响。

备选是工作台经 SSH 直接调用运行服务器的 Docker API（不装 runner-agent）。不推荐：工作台掉线时没人执行超时和磁盘保护；每次操作都等于拿着 root；日志和文件传输都挤在 SSH 上（第 14 节 D2）。

## 10. 智能体的工具（MCP）

| 工具 | 读 / 写 | 做什么 |
|---|---|---|
| `runner_templates` | 读 | 能用的模板：用途、默认类别、网络、资源上限、预计启动耗时 |
| `env_find` | 读 | 按模板、`reuse_key`、用途找自己的和共享给自己的环境；返回状态、上次使用、预计唤起耗时 |
| `env_create` | 写 | 第 4.1 节的必填参数；先复用；`lifetime=once` 时必须带 `command`，建好就跑，跑完就删；可选 `from_environment`（复制工作目录）、`files`（初始文件） |
| `env_exec` | 写 | 在环境里执行命令（参数数组，或者一段 shell 脚本）；60 秒内结束的直接返回退出码和输出；更久的返回运行编号，结束后用 IM 唤醒智能体 |
| `env_run` | 读 | 查一次运行的状态和输出 |
| `env_files` | 读 / 写 | 列目录、上传、下载（单个文件上限 20 MB，经工作台转存） |
| `env_setup` | 写 | 登记或修改这个环境的初始化步骤（重建时重放） |
| `env_update` | 写 | 改删除条件、共享范围、用途（只有创建者） |
| `env_stop` | 写 | 主动停止（释放内存，保留数据） |
| `env_release` | 写 | “我不用了”：创建者调用会触发 `released` 条件；别人调用只是不再使用共享的环境 |
| `template_propose` | 写（审批） | 提议新模板或新版本：基础镜像、安装脚本、放行域名、资源、要保存的目录。管理员在页面上批准（可以修改）后才能用 |

- 没打开“运行环境权限”的实例看不到这些工具（与例外三、六、七相同）。
- 只能用实例被允许的模板；`env_*` 只作用于自己的环境或共享给自己的环境，工作台按工作空间、实例和共享关系校验。

## 13. 与现有规则的关系

- `docs/AGENTS.md` 第 8 节：“不得放宽 OpenClaw 智能体的工具限制（只开工作台工具和 IM 发消息工具），不得开启 exec 或挂载 Docker socket”。
  OpenClaw 服务器上这条不变。但 `env_*` 让智能体能在别的机器上执行命令，是能力上的实质扩大，需要人类新增**例外八**。建议的写法：
  > 例外八：管理员按实例打开“运行环境权限”并选定可用的模板后，智能体经工作台在运行服务器上建、用、停、删自己的容器环境，并在里面执行命令（`env_*` 工具），直接执行、不审批；新模板或新版本（`template_propose`）、全部外网、runc 运行时、绑定密钥、超出限额需要管理员批准。它们仍必须经过权限范围、角色、模板白名单、网络与资源限制、gVisor 隔离、限额、执行记录、审计与通知管理员的保护，不得绕过；OpenClaw 服务器本身仍然不开 exec、不挂 Docker socket（人类 2026-11-xx 决定；见 `docs/v2/RUNNER_PLAN.md`）。
- 工作台是唯一的权限来源：runner-agent 只执行工作台下发的指令，不接受智能体直连。
- 外部 HTTP 与写操作：runner-agent 与工作台之间有超时、重试上限；`exec` 结果未知时不自动重跑，靠对账确认。
- 第三方接口核验：Docker Engine API、gVisor、出口代理都在锁定版本上核验（R0），写进 `docs/decisions/`。
- 设置放在网页上：添加运行服务器、建模板、改回收策略、开权限都在页面上完成；部署指南只写“准备一台装好 Linux、能 SSH 登录的服务器，`/var/lib/docker` 用 XFS”。

## 14. 需要人类决定的事项

| # | 事项 | 推荐 | 其他选择 |
|---|---|---|---|
| D1 | 智能体用运行环境要不要每次审批 | **新增例外八**：按实例开权限、选模板后直接执行；新模板、全部外网、runc、密钥、超限额要批准 | 每次 `env_create` 都审批（安全但很慢）；只允许一次性环境 |
| D2 | 工作台怎么控制运行服务器 | **runner-agent 主动连工作台**（第 9 节） | 工作台经 SSH 直接调 Docker API |
| D3 | 隔离方式 | **默认 gVisor**，个别模板由管理员改 runc | 全部 runc（兼容最好、隔离最弱）；Kata / Firecracker（隔离最强，要虚拟化支持，开销大） |
| D4 | 默认网络 | **默认没有网络**，模板按域名放行；全部外网只能管理员在模板上打开；私有网段永远禁止 | 默认全部外网 |
| D5 | 回收默认值 | **第 6.1 节的表** | 按你的使用习惯调 |
| D6 | 常驻环境归档时做不做快照 | **做**：加密存对象存储，单个上限 5 GB，最后使用 30 天后清理 | 不做（归档等于丢数据，归档前要管理员确认） |
| D7 | 跨智能体共享 | **默认不共享**；创建者可以共享给项目成员，权限分“使用”和“复制” | 同一项目的成员默认都能用 |
| D8 | 谁能删环境 | **创建者和管理员**；其他智能体只能 `env_release`，或者触发创建者登记的条件 | 项目成员都能删 |
| D9 | 模板从哪来 | **管理员在页面上建，智能体可以提议，管理员批准** | 只允许管理员建 |
| D10 | 运行服务器归属 | **一台属于一个工作空间** | 多个工作空间共用（要按工作空间分资源） |
| D11 | 小红书 | **网页版 + 浏览器抓取** | 安卓 App（要模拟器和 KVM，gVisor 里跑不了，工作量大很多，放到以后） |
| D12 | 测试里需要 Docker（如 `docker compose` 起依赖） | **V1 不支持容器里跑 Docker**；用模板的附属服务代替 | 以后评估 Sysbox 或 gVisor 内跑 Docker |

## 16. 风险

| 风险 | 对策 |
|---|---|
| 容器逃逸，拿下运行服务器 | gVisor；运行服务器专用、可重装；runner-agent 的身份只能调 `/runner/v1/*`，拿不到工作台别的接口 |
| 工作台被攻破，用来在运行服务器上乱建容器 | runner-agent 只接受固定指令，安全参数本地生成，只能更严 |
| 智能体滥用算力（挖矿、刷接口） | 限额、CPU 监控告警、出口白名单、执行记录 |
| 注入的密钥被带出 | 只注入专用最小权限密钥；出口白名单；审计 |
| 抓取被平台封号或有法律风险 | 管理员在模板和任务里限定对象和频率；不抓个人隐私信息 |
| 磁盘被镜像、数据卷、快照塞满 | 水位回收、镜像清理、快照过期、XFS 限额 |
| gVisor 不兼容某些程序 | 模板构建后跑自检；必要时管理员改 runc 并写审计 |
| 回收太狠，智能体反复重建 | 启动越慢停得越晚；回收记录可查；V2 按使用间隔自动调整 |

## 17. 以后再做

- 多台运行服务器的调度（按剩余资源和镜像是否已缓存选机器）。
- 按每个环境的使用间隔自动调保活时长（《Serverless in the Wild》的直方图策略）、预热。
- 挂起（保留内存）：等 Docker checkpoint 或 gVisor 的 checkpoint 稳定后再评估。
- Kata / Firecracker、GPU、安卓模拟器、本地镜像仓库（清理后的镜像从仓库拉回，不用重建）。
