# MCP 管理器的一键部署：部署到智能体服务器或容器服务器（设计方案）

> 人类 2026-11-14 的三条要求（T-0233）：
>
> 1. 页面上要有“一键部署 MCP 管理器”。
> 2. MCP 管理器可以部署在其他服务器上，服务器从“智能体服务器”或“容器服务器”里选；
>    这两个服务器管理页面各加一个 MCP 管理器容器的入口，方便管理和查看。
> 3. MCP 管理器的容器不受这两个页面的管理程序限制——大模型的运行环境要保持稳定。
>
> 本文是这三条的设计方案，代码按它落实。MCP 管理器本身（会话桥）见 `LLM_BRIDGE_PLAN.md`，
> 聊天页面见 `LLM_CHAT_PLAN.md`。

名词：**MCP 管理器** = 一个会话桥容器（`services/llm-bridge`）；**智能体服务器** = `/agent-servers`
页面登记的 OpenClaw 服务器；**容器服务器** = `/runner` 页面登记的运行服务器。

## 1. 现状（2026-11-14 在代码里核对）

| 项目 | 智能体服务器 | 容器服务器 |
|---|---|---|
| 登记表 | `agent_servers` + `agent_ssh_targets` | `runner_hosts` + `runner_ssh_targets` |
| 工作台怎么登录 | 保存的登录密码（加密），固定主机公钥 | 专用 ed25519 私钥（加密），固定主机公钥；密码不保存 |
| 登录账号能不能直接用 Docker | 能（初始化时加进了 docker 组） | 不能（不是 root 时要 `sudo`，密码每次现填、只用一次） |
| 页面上的管理程序 | 部署 / 升级 / 卸载 OpenClaw 实例、重启、启动、清理无用镜像、容器列表、资源准入 | runner-agent（建、停、删、回收环境容器，磁盘紧急清理）、gVisor 安装、放置与配额 |
| 这些程序碰哪些容器 | 只进实例自己的目录（`~/myworkspace-openclaw/<实例短号>`）操作那一个 compose 项目；清理只删悬空镜像 | 只碰带 `myworkspace.runner=1` 标签、名字是 `mw-(env\|vol\|net)-<12 位十六进制>` 的对象 |

两处会波及别的容器的地方：

- `install-gvisor.sh` 第一次把 runsc 接入 Docker 时 `systemctl restart docker`——服务器上所有容器都会被重启。
- 容器服务器上报的“不是工作台建的容器”数量（`unlabeled_containers`）会把 MCP 管理器也算进去，页面上提示成外来容器。

同一台机器只能登记在一个池子里（`physical_host_registrations`），所以一台服务器要么是智能体服务器，要么是容器服务器。

## 2. 部署位置

部署时先选服务器类型，再选服务器：

| 类型 | 可选的服务器 | 工作台用什么登录去部署 | Docker 权限 |
|---|---|---|---|
| 智能体服务器 | 已经保存密码、确认过主机公钥、初始化完成的 SSH 服务器 | 保存的密码 | 直接用 |
| 容器服务器 | 已经用 SSH 部署过（装了专用密钥、确认过主机公钥）的服务器 | 专用私钥 | root 账号直接用；其他账号经 `sudo`：免密 `sudo` 直接用，否则页面上填一次登录密码（只用这一次，不保存、不进日志） |

说明：

- 同一台服务器可以部署多个 MCP 管理器（每个管理器是一套独立的账号），互不相干；数量不设上限。
- 部署 MCP 管理器**不走**两个页面的准入规则：不看智能体服务器的资源准入，不占容器服务器的配额和放置名额，
  也不因为那台服务器上正在部署实例、正在跑环境而被拒绝。它只有自己的一条规则：同一台服务器同一时间只跑一个 MCP 管理器的部署任务。
- 手动部署（自己写 compose、在页面上“手动添加”）照旧可用。

## 3. 部署过程

工作台经 SSH 完成，页面显示每一步的状态和脱敏后的输出：

| 步骤 | 做什么 |
|---|---|
| 连接 | 按固定的主机公钥登录 |
| 检查 | 只读：主目录、架构、Docker 与 compose 是否可用、要不要 `sudo`、这台服务器是不是工作台自己所在的服务器、一个空闲的本机端口 |
| 上传 | 把会话桥的源码、compose 文件、令牌文件传到 `~/myworkspace-llm-bridge/<编号>/`（令牌文件 600） |
| 构建 | `docker compose build` |
| 启动 | `docker compose up -d --wait` |
| 通道 | 部署在别的服务器时：生成这座管理器专用的转发密钥，装进登录账号的 `authorized_keys`（见第 4 节） |
| 验证 | 工作台按将来实际使用的那条路访问管理器的状态接口 |
| 登记 | 写入管理器登记（地址、令牌加密保存）和部署记录 |

任何一步失败：已经上传的目录、已经启动的容器和数据卷、已经装上的转发密钥都撤回，不留下带令牌的文件。

容器的固定设置：compose 项目 `mw-mcp-<编号>`；标签 `myworkspace.mcp-manager=<编号>`（容器、数据卷、网络都带）；
`restart: unless-stopped`（Docker 或服务器重启后自己回来）；`cap_drop: ALL`、`no-new-privileges`；
不挂 Docker socket、不挂宿主目录、不用特权模式、不用宿主网络。

其他操作（都是一个任务，页面上看进度）：

- **重新部署**：重新上传源码、构建、启动；数据卷、令牌、端口、转发密钥都不变（工作台升级后用它升级管理器）。
- **重启**：`docker compose restart`，再验证。
- **卸载**：停止并删除容器（可选连同数据卷）、删除目录、删除 `authorized_keys` 里的转发密钥、删除登记。
  服务器连不上时可以选“只删除登记”，页面写明服务器上还留着什么。

## 4. 网络：工作台怎么访问部署出去的管理器

| 方式 | 什么时候 | 管理器监听 | 工作台怎么访问 |
|---|---|---|---|
| `same_host` | 选的服务器就是工作台自己所在的服务器（检查步骤在那台服务器的 Docker 里找到了工作台的 API 容器） | 不对外发布端口，加入工作台的内部网络（`<项目>_integrations`），别名 `mcp-<编号>` | `http://mcp-<编号>:8787` |
| `tunnel` | 其他情况 | 只发布到那台服务器的本机地址 `127.0.0.1:<端口>`（18787–18886 里第一个空闲的） | 一条专用的 SSH 通道，把工作台进程里的一个本机端口转发到那台服务器的 `127.0.0.1:<端口>` |

`tunnel` 的做法：

- 部署时生成一把 ed25519 密钥，公钥写进登录账号的 `authorized_keys`，带限制：
  `restrict,port-forwarding,permitopen="127.0.0.1:<端口>",command="/bin/false"`。
  这把密钥**不能执行命令、不能开终端、只能转发到这一个端口**（在真实的 OpenSSH 上实测过，
  见 `docs/decisions/2026-11-14-mcp-manager-deploy-verification.md`）。私钥加密保存在工作台（用途绑定这一条部署记录）。
- 工作台的每个进程在第一次访问这座管理器时建立通道，之后复用；断了下次访问时重建。通道只在工作台进程的本机地址上监听。
- 部署记录里自己存一份服务器的地址、端口、账号、主机公钥。所以之后在服务器页面上改密码、吊销容器服务器的专用密钥、
  把服务器从工作台移除，都不影响这条通道——这是第 3 条要求（保持稳定）的一部分。
- 管理器的端口不暴露在局域网和公网上；同一台服务器上的 OpenClaw 实例、环境容器也够不着它（容器里访问不到宿主的 `127.0.0.1`），
  智能体只能照旧经工作台的工具访问（例外九的全部校验不变）。
- 前提：那台服务器的 sshd 允许端口转发（`AllowTcpForwarding`，默认允许）。不允许时“验证”一步失败并写明原因。

为什么不让管理器直接监听内网地址：要多开一个端口、要求工作台和服务器在同一个内网、同机的其他容器能直接连它。
通道的代价是每次访问多一层 SSH 加密，会话桥的调用都是秒级的，可以忽略。

## 5. 数据

新表（迁移 `0070`）：

`llm_bridge_installs`——一条 = 一座由工作台部署的管理器。

| 字段 | 说明 |
|---|---|
| `bridge_id` | 对应的管理器登记（唯一；登记删除时一起删除） |
| `target_kind` | `agent_server` / `runner_host` |
| `server_id` / `runner_host_id` | 来源服务器；服务器从工作台移除后置空，部署记录保留 |
| `server_name`、`address`、`ssh_port`、`username`、`host_key` | 部署时的服务器信息（通道用它登录） |
| `slot`、`project`、`install_dir` | 编号、compose 项目、目录 |
| `mode`、`port` | `same_host` / `tunnel`；本机端口 |
| `tunnel_key_ref`、`tunnel_public_key` | 转发密钥（私钥是加密引用） |
| `source_tag` | 部署的源码版本（内容摘要），页面用它提示“可以重新部署到新版本” |
| `needs_sudo` | 这台服务器上操作 Docker 要不要 `sudo`（页面据此决定要不要问密码） |
| `deployed_at`、`deployed_by` | |

`llm_bridge_deploy_jobs`——部署 / 重新部署 / 重启 / 卸载任务：类型、状态、目标、步骤、脱敏后的输出、错误、谁发起、幂等号。
同一台服务器同时只有一个进行中的任务（部分唯一索引）；工作台重启时进行中的任务标成“中断”。

不存的东西：服务器的登录密码、`sudo` 密码、各平台的登录凭据。

## 6. 接口（都在 `/api/v1/llm_bridge` 下）

| 接口 | 角色 | 说明 |
|---|---|---|
| `GET /deployments/targets` | admin | 两类服务器里可以部署的服务器，以及不能部署的原因 |
| `GET /deployments` | admin | 最近的任务；`available` 表示这个工作台带着会话桥的源码 |
| `POST /deployments` | owner | 部署：`target_kind`、`target_id`、`name`、`platforms`、`sudo_password`（可选）、`request_id` |
| `GET /deployments/{job_id}` | admin | 一个任务的进度 |
| `POST /bridges/{id}/redeploy`、`/restart`、`/uninstall` | owner | `sudo_password`（可选）；卸载另有 `remove_data`、`force` |
| `GET /installs?target_kind=&target_id=` | admin | 某台服务器上的 MCP 管理器（两个服务器页面的入口用），带是否在线 |

需要 `sudo` 密码却没给：`409 SUDO_PASSWORD_REQUIRED`，页面弹出密码框后重发。写操作都带 CSRF、校验工作空间与角色、记审计；
`request_id` 幂等。

## 7. 页面

**大模型客户端管理页（`/llm_bridge?view=manage`）**

- “添加管理器”分两种：**一键部署到服务器** / 手动添加。
- 一键部署：服务器类型（智能体服务器 / 容器服务器）→ 服务器 → 名称 → 平台 →（需要时）登录密码 → 部署；下面是任务进度。
- 管理器卡片上写明部署在哪台服务器、用哪种网络方式；工作台部署的管理器多三个按钮：重新部署、重启、卸载。
- 从服务器页面跳过来时（`?deploy=<类型>:<服务器>`）直接打开一键部署并选好那台服务器。

**智能体服务器页（`/agent-servers` 的服务器详情）与容器服务器页（`/runner` 的“设置”里每台服务器）**

各加一个“MCP 管理器”区块：

- 列出这台服务器上的 MCP 管理器：名称、在线 / 离线、网络方式、部署时间、已登录的平台。
- 每一个有“打开聊天”“管理”（跳到管理页并定位到它）；区块底部有“在这台服务器上部署 MCP 管理器”。
- 一行说明：这些容器不受本页面的重启、清理、回收和卸载影响；重新部署、重启、卸载在大模型客户端管理页面上做。
- 没有部署时只显示一行说明和部署入口。

实现方式：前端模块定义增加一个扩展点 `serverPanels`（`agentServer` / `runnerHost` 两个位置），两个服务器页面渲染已启用模块提供的区块。
`llm_bridge` 模块停用后区块自动消失，服务器页面不直接引用模块的代码（符合 `docs/modules/README.md` 的插拔规则）。

## 8. 保护规则：MCP 管理器的容器不受两个页面的管理程序限制

| 管理程序 | 对 MCP 管理器的影响 | 怎么保证 |
|---|---|---|
| 智能体服务器：部署 / 升级 / 卸载实例、重启、启动 | 无 | 这些命令只在实例自己的目录里对那一个 compose 项目执行；管理器在另一个目录、另一个项目。加回归测试钉住 |
| 智能体服务器：清理无用镜像 | 无 | 只删悬空镜像；管理器的镜像有标签并且在用。加回归测试钉住命令 |
| 智能体服务器：容器列表 | 只读地列出来 | 不提供任何操作 |
| 智能体服务器：资源准入 | 不适用于管理器 | 管理器的部署不调用准入检查 |
| 智能体服务器：改密码、移除服务器 | 无 | 通道用自己的密钥和自己保存的服务器信息；移除服务器不到服务器上执行任何命令。服务器上还有管理器时，移除前页面写明“它们会继续运行” |
| 容器服务器：runner-agent 的建、停、删、回收、磁盘紧急清理 | 无 | 只处理 `myworkspace.runner=1` 且名字符合 `mw-(env\|vol\|net)-…` 的对象；管理器的名字和标签都不符合。加回归测试钉住 |
| 容器服务器：配额、放置、空闲回收 | 不适用于管理器 | 管理器不是环境，不建环境记录 |
| 容器服务器：“不是工作台建的容器”提示 | **要改** | runner-agent 上报时把带 `myworkspace.mcp-manager` 标签的容器单独计数（`mcp_manager_containers`），不算进外来容器 |
| 容器服务器：gVisor 安装时重启 Docker | **要改** | 先 `systemctl reload docker`（实测：Docker 不重启就能登记新的运行时，已有容器不受影响）；runsc 仍没登记、而服务器上有运行中的 MCP 管理器时不重启，安装停下并说明原因，管理员在容器服务器页面勾选“允许重启 Docker”后再装；没有管理器时照旧重启 |
| 容器服务器：吊销专用密钥、卸载 runner-agent、移除服务器 | 无 | 吊销只删那一把公钥所在的行；卸载只删 runner-agent 自己的文件和带标签的对象；通道用自己的密钥 |
| Docker 或服务器重启 | 短暂中断后自己恢复 | `restart: unless-stopped` |

管理器自己的管理（重新部署、重启、卸载）只在大模型客户端管理页面上，只有 owner 能做。

## 9. 权限与安全

- 部署、重新部署、重启、卸载：owner；查看：owner / admin；member 403。后端校验，不只是页面上不显示。
- 浏览器拿不到管理令牌、转发密钥、服务器密码；`sudo` 密码只在这一个任务的内存里，用完即丢，任务输出里出现也会被抹掉。
- 转发密钥只能转发到一个本机端口；卸载时从服务器上删除并删除工作台保存的私钥。
- 管理器容器不挂 Docker socket、不用特权模式；OpenClaw 服务器本身仍然不开 exec、不挂 Docker socket（`docs/AGENTS.md` 的规则不变，本方案不需要改它）。
- 例外九不变：智能体仍然只能经工作台的工具访问会话桥，按实例的权限开关、限额、审计。
- 审计：`deploy_started` / `deploy_finished` / `redeploy_*` / `restart_*` / `uninstall_*`，记服务器和管理器，不记密码与令牌。

## 10. 测试与验收

- 后端：假 SSH 服务器上跑通两类服务器的部署、重新部署、重启、卸载；需要 `sudo` 密码的分支；失败回滚不留文件和密钥；
  通道（经假 SSH 服务器转发到一个真的本机 HTTP 服务）；角色与工作空间；幂等；迁移 upgrade / downgrade。
- 保护规则的回归测试：第 8 节表里“加回归测试钉住”的每一条。
- 前端：部署表单（两类服务器、密码框）、任务进度、卡片按钮、两个服务器页面上的区块、模块停用后区块消失。
- 浏览器验收：管理页一键部署表单与两个服务器页面的入口。
- CI：`agents` job 里已有一个要 `sudo` 密码、不在 docker 组的 sshd 账号——在它上面实际部署一个管理器（经通道验证）再卸载。
- 需要真实账号的部分（各平台真实登录与回答）仍然要人类验收。

## 11. 取舍与不做的

- **不做**：把已有的手动部署“接管”成工作台管理的；跨服务器迁移管理器的数据；在服务器页面上直接重启 / 卸载管理器（只给入口，操作集中在一个页面）。
- **容器服务器上每次操作可能要填一次密码**：因为那里的登录账号按设计不在 docker 组、密码不保存。root 账号或免密 `sudo` 的服务器不用填。
- **通道依赖 sshd 允许端口转发**：极少数加固过的服务器要先打开 `AllowTcpForwarding`（或只对这个账号打开）。
- **管理器占用的内存和 CPU 仍然是那台服务器的**：两个页面看到的整机负载里包含它，但不会因此去动它；
  服务器吃紧时受影响的是之后新建的实例或环境，不是管理器。
- 改 runner-agent 和 `install-gvisor.sh` 会让容器服务器的接入包版本变化，已部署的服务器在页面上会提示可以升级；不升级也不影响管理器（只是旧版本仍把它数成外来容器）。
