## 0. 一页看懂

```
大模型客户端 → 开发环境 → 新增开发环境
  运行位置：○ MCP 管理器容器（现在的做法）   ● 云端远程容器（本方案）
            └ 选容器服务器、镜像、资源、网络；或者选这个管理器已有的远程容器
                     │
                     ▼
工作台：在容器服务器上建一个“远程开发容器”（常驻，带数据卷），登记到这个开发环境上
        容器服务器页面能看到它：申请方写“MCP 管理器「1 号」· 开发环境「WorkspaceCore」”

新建会话 / 发消息（智能体经 llm_bridge_* 工具，或人在聊天页面）
  ▼
MCP 管理器：排队、会话、事件、额度都照旧；只是起官方程序这一步变成“远程操作”
  ▲ │  工作台来取远程操作（长轮询）；管理器不需要连工作台
  │ ▼
工作台：校验、转成容器服务器的指令 ───▶ runner-agent ───docker exec───▶ 远程开发容器
                                                                     claude -p … / codex exec --json … / codebuddy -p …
        ◀── 输出按块回传（JSONL 事件）── runner-agent ◀── 托管进程把输出写进容器里的文件
  │
  ▼  转给管理器，管理器用现在的解析代码显示、记账
```

- **整个官方程序搬进容器**，不是只把命令搬进去：官方程序自带的工具（读写文件、执行命令、改补丁）原样可用，只有每个回合的开始、结束和输出流要经过中转。
- **容器就是沙箱**：容器沿用容器服务器的全部宿主保护（默认 gVisor、非 root、去掉全部 capability、出口代理），所以“可执行命令”这一档在远程容器里比在管理器里安全得多（不再能读到管理器数据卷里的各平台凭据）。
- **管理器不连工作台**：工作台本来就能访问每一个管理器（同机直连或 SSH 通道），由工作台来取远程操作、推回输出，不加任何新的网络路径和凭据。
- **凭据分两种处理**（D1）：不会刷新的（API 密钥、Claude 长期令牌）每回合随进程注入、不落盘；会刷新的登录（ChatGPT 登录、Claude 网页授权、CodeBuddy 账号）在容器里单独登录一次同一个账号。
- **智能体看不到容器**：它们仍然只用 `llm_bridge_*` 工具、只能从管理员建好的环境里选；建、改、删容器都在页面上，只有 owner 能做。

## 1. 目标与边界

要做到：

1. “新增开发环境”弹窗多一个“运行位置”：MCP 管理器容器（现在的做法）/ 云端远程容器。
2. 选云端远程容器时，工作台在选定的容器服务器上新建一个容器（或者用这个管理器已有的远程容器），它出现在容器服务器页面上。
3. 用这个环境建的开发会话，Codex / Claude / CodeBuddy 都在这个容器里干活：克隆仓库、改文件、装依赖、跑测试。
4. 开发环境页能浏览远程会话的工作目录，和现在一样只读、先脱敏。
5. 容器的启停、回收不打断正在进行的回合；容器服务器离线时给出清楚的原因，管理器本地的环境照常可用。

不做：

- 智能体自己建、改、删远程容器（它们没有这类工具；需要自己的容器的，照旧用例外八的 `env_*` 工具）。
- 每个会话一个容器、一次性测试容器、Kubernetes 类的容器服务器、`codex.cloud` / `claude.cloud` 云端通道（第 20 节）。
- 改变“一个管理器每个平台一个账号”（`LLM_BRIDGE_PLAN.md` 第 8 节）：远程容器里登录的必须是同一个账号。

## 3. 业内怎么做

| 做法 | 是什么 | 我们借鉴什么 |
|---|---|---|
| **Claude Code 的 devcontainer 参考配置**【已核验：官方文档】 | 官方程序装在容器里跑。原文：“Because the container runs Claude Code as a non-root user and confines command execution to the container, you can pass `--dangerously-skip-permissions` for unattended operation.” 以 root 运行时程序拒绝这个参数。同一页警告：容器挡不住恶意项目带走容器里能访问的东西，“including the Claude Code credentials stored in `~/.claude`”，建议用仓库范围或短期的令牌 | 整个官方程序放进容器、以非 root 运行、容器即沙箱；凭据进容器是已知风险，要缩小范围 |
| **Claude Code 云端会话**【已核验：官方文档】 | “git credentials and signing keys stay outside the sandbox, and a proxy authenticates on the session's behalf with scoped credentials.”；网络默认受限 | 最好的做法是凭据留在沙箱外、由代理代为认证（第 9 节丙，列为以后的加强）；网络默认收紧 |
| **Codex 命令行的无界面模式**【已核验：0.169.0 帮助文本与实测】 | `codex exec --json` 每次跑一个回合、输出 JSONL 事件，`codex exec resume <会话号>` 续接；`--dangerously-bypass-approvals-and-sandbox` 的说明是 “Intended solely for running in environments that are externally sandboxed” | 远程 Codex 按回合起进程，和 Claude、CodeBuddy 一致；容器即沙箱时用这个参数 |
| **CodeBuddy Code**【已核验：2.184.0 帮助文本】 | `-y` 的说明里写着 “Isolated-sandbox full pass: `CODEBUDDY_IS_SANDBOX=1`” | 远程容器里“可执行命令”档带上这个变量（效果待核验） |
| **E2B、Daytona、Coder 等沙箱 / 云开发环境**【未核验：本会话打不开这几家的文档，按以往了解】 | 编程智能体在沙箱或工作区里运行，控制端经沙箱里的守护进程起进程、取输出；API 密钥多以环境变量传进沙箱 | 控制端不直连进程，经一个守护进程托管（我们是 runner-agent） |
| **GitHub Actions 自托管 runner**（`RUNNER_PLAN.md` 第 2 节已引用） | runner 主动连服务端领任务，日志边跑边分块上传 | 输出分块回传、按偏移续传 |

共识：

1. 把整个智能体放进容器，容器就是沙箱，容器里用“完全放开”的权限档，靠容器本身的隔离兜底。
2. 进程由容器旁边的守护进程托管，输出先落盘再分块回传，断线后按偏移续读。
3. 凭据尽量不进容器；进容器的要专用、可吊销、范围小。
4. 网络默认只放行必需的地址。
5. 环境 = 镜像 + 常驻数据卷，空闲时停止、用时自动启动。

## 4. 总体设计：三个关键选择

| 选择 | 推荐 | 不选的做法与原因 |
|---|---|---|
| 官方程序在哪里跑 | **在远程容器里跑**（第 6 节） | 程序留在管理器、只把命令经 MCP 工具发到容器：要关掉三家自带的读写和执行工具、换成我们的工具，每次工具调用都要绕一圈工作台（一个回合常有几十上百次），慢且行为和官方不一致；Codex 能否完全关掉自带的 shell【未核验】 |
| 管理器和容器怎么通 | **工作台中转，由工作台来取**（第 8 节） | 管理器直接调工作台：部署在别的服务器上的管理器只能经 SSH 通道被工作台访问，反方向要再开通道、再发一份凭据；转发密钥现在只允许本地转发（`permitopen`） |
| 容器里怎么跑一个回合 | **托管进程**：runner-agent 用 `docker exec -d` 起一个托管脚本，输出写进容器里的文件，runner-agent 读新增部分分块回传（第 7 节） | 直接复用现有的一次性 `exec`：没有标准输入、结束才有输出、超时就停整个容器 |

## 5. 远程开发容器（容器服务器这一侧）

### 5.1 归属与数量

- 容器服务器的环境加一种归属：**MCP 管理器**（`owner_kind = llm_bridge`，`owner_bridge_id`）。它由 owner 在大模型客户端页面上建，不属于任何智能体，不占任何智能体的容器配额。
- 一个远程开发容器可以给这个管理器的多个开发环境用（D2）：例如 Codex 环境、Claude 环境、CodeBuddy 环境都指向同一个容器，共用装好的软件、缓存和代码目录；每个会话仍然有自己的工作目录。最后一个用它的环境删除时，问要不要一起删容器。
- 数量和资源由工作空间一级的上限约束（D8，默认最多 5 个、合计 16 核 / 32 GB 内存 / 200 GB 磁盘，在容器服务器“设置”里改），另外照常过容器服务器的整机容量和放置检查。

### 5.2 镜像

| 选项 | 内容 |
|---|---|
| **内置“大模型开发环境”**（默认） | 锁定 digest 的 Debian 基础镜像 + Node 22 + Python 3 + Git + ripgrep + 常用构建工具；三家命令行装在 `/opt/mw/cli/`，版本和管理器一致（`docs/versions.md`：Codex 0.169.0、Claude Code 2.1.323、CodeBuddy Code 2.184.0） |
| 容器服务器上已有的模板 | 在模板镜像上加一层命令行（见下） |
| 自定义镜像 | 填镜像名，工作台建成一个模板：`FROM <镜像>`，再加一层命令行 |

- “加一层命令行”的做法：内置镜像里有一个自带 Node 运行时的命令行目录，其他镜像用 `COPY --from=<命令行镜像 digest> /opt/mw/cli /opt/mw/cli` 拷进去。要求镜像是 glibc 的 Linux、有 `/bin/sh` 和 `setsid`；建容器时检查，不满足就失败并写明原因。拷进不带 Node 的 `debian:bookworm-slim` 后三个命令行都能直接跑【已核验，V8】。
  这个目录约 1.2 GB，第一次构建要下载约 1 GB；同一台容器服务器上只构建一次，所有远程容器共用这一层。
- 额外要装的系统软件写在弹窗“高级”里的“安装步骤”（就是容器服务器模板的安装步骤），构建成镜像的一部分。容器里的程序以非 root 运行（5.3），运行中装不了系统软件，所以要装的东西放进镜像。
- 版本必须一致：管理器解析的是锁定版本的输出格式。管理器升级后，页面上提示“更新镜像”：重新构建模板、按新镜像重建容器，数据卷保留（容器服务器现有的重建流程）。回合开始前比对容器里的命令行版本，不一致就不开回合，提示更新镜像。

### 5.3 容器参数

沿用容器服务器的宿主保护（`RUNNER_PLAN.md` 8.1、8.2），不另开口子：

| 项 | 远程开发容器 |
|---|---|
| 运行时 | 默认 gVisor；可选 runc（兼容性好、隔离弱，页面标出来并通知管理员一次）；不提供 kvm |
| 用户 | 固定非 root（uid 1000，去掉全部 capability，`no-new-privileges`）。Claude Code 以 root 运行时拒绝跳过权限确认【已核验：官方文档】，所以不提供 root |
| 资源 | 预设：小（1 核 / 2 GB / 10 GB）、中（2 核 / 4 GB / 20 GB，默认）、大（4 核 / 8 GB / 50 GB）、自定义 |
| 目录 | `/workspace/sessions/<会话号>/`：会话的工作目录；`/workspace/.home/`：HOME，三家的配置目录、会话记录、容器里的登录（`CLAUDE_CONFIG_DIR`、`CODEX_HOME`、`CODEBUDDY_CONFIG_DIR` 都指到这里）；`/workspace/.mw/procs/<进程号>/`：托管进程的输入输出 |
| 密钥 | 可以勾选工作台密钥库里的密钥（例如 Git 令牌），按容器服务器现有的方式注入 `/run/secrets/` |
| 不变的 | 不特权、不挂 Docker socket 和宿主目录、不用宿主网络；出口只经出口代理，私有网段、工作台、OpenClaw 服务器、MCP 管理器永远连不到 |

### 5.4 网络（D4）

官方程序要连各自的模型接口，所以不能是“没有网络”。三档：

| 档 | 放行 |
|---|---|
| **只连模型接口和代码仓库**（默认） | 用到的平台必需的域名（模型接口、登录刷新等，清单在核验任务里实测，第 16 节 V3）+ 仓库地址所在的主机 |
| 再加常用包仓库 | 上面的 + npm、PyPI、Go、crates、Debian 软件源、GitHub 发布文件等预设清单 |
| 全部外网 | 任何公网地址 |

另外可以自己加域名（支持 `*.example.com`）。三档都只经出口代理走 HTTP / HTTPS（容器服务器 V1 的限制）。
三个命令行都走 `HTTPS_PROXY`【已核验，V6】。不登录时启动会连的域名已实测（核验记录 V3）；登录、刷新用的域名要用真实账号补测，补测之前“只连模型接口和代码仓库”这一档的清单不完整，页面上暂时推荐“全部外网”并写明原因。

### 5.5 生命周期与回收（D3）

| 情况 | 做法 |
|---|---|
| 类别 | 常驻（`persistent`） |
| 空闲 | 30 分钟没有托管进程、没有被调用就停止（可选 2 小时 / 不停止）；下一个回合自动启动，页面和回合进度里显示“正在启动远程容器…” |
| 归档 | **默认不自动归档**：工作目录里可能有没提交的改动，容器里还有登录。新增“不自动归档”标记，资源紧张时只停止、不归档 |
| 回收时 | 有托管进程在跑的容器算“正在执行”，任何回收都跳过它（沿用现有规则） |
| 删除 | 只在大模型客户端页面上删（删环境时问、或者删容器）：进入“待删除”，5 分钟后连数据卷一起删，不做快照（里面有登录凭据）；会话记录在管理器里，不受影响，但这些会话不能再续发 |
| 管理器删除 | 删除前列出它的远程容器，默认一起删 |
| 管理器停用（启用开关关掉） | 它的远程容器全部停止 |

### 5.6 容器服务器页面

- 容器表的“申请智能体”列改叫“申请方”：智能体显示名字；远程开发容器显示“MCP 管理器「1 号」· 开发环境「WorkspaceCore」”（多个环境共用时列出），图标区分；筛选多一项“MCP 管理器”。

## 6. 在容器里跑官方程序

### 6.1 每回合一个进程

| 平台 | 管理器里（现在） | 远程容器里 |
|---|---|---|
| Claude | `claude -p --output-format stream-json --verbose --include-partial-messages --session-id / --resume <号>`，每回合一个进程 | 同一条命令，在容器里由托管进程起；“可执行命令”档用 `--permission-mode bypassPermissions`（非 root，容器即沙箱） |
| CodeBuddy | `codebuddy -p …`，同上 | 同上；“可执行命令”档另加 `CODEBUDDY_IS_SANDBOX=1`（帮助文本说这是隔离沙箱下的完全放行，实际效果待核验 V7） |
| Codex | 常驻 `codex app-server`，JSON-RPC | **每回合一个 `codex exec --json`**（D7）：第一回合 `codex exec --json -m <模型> -C <工作目录> --skip-git-repo-check -`，之后 `codex exec resume <会话号> --json -`；提问从标准输入给（`-` 表示读标准输入）；图片用 `-i`。**只提供“可执行命令”档**，用 `--dangerously-bypass-approvals-and-sandbox`：Codex 0.169.0 自己的沙箱（bubblewrap）在 runc 和 gVisor 容器里都起不来【已核验，V2】，容器本身就是沙箱 |

- 【已核验：Codex 0.169.0】上面的参数都在帮助文本里；无登录实测时输出第一行是 `{"type":"thread.started","thread_id":"…"}`，接着 `turn.started`、`error`、`item.completed`；它经 `HTTPS_PROXY` 连接（先试 WebSocket，失败后退回 HTTPS）。
  命令、改文件、用量、额度这些事件的完整形状要用真实账号录一份（V1）。
- 会话号：Claude / CodeBuddy 和现在一样由管理器生成；Codex 取 `thread.started` 里的 `thread_id`。
- 续接判断：现在按管理器里有没有会话记录文件决定用 `--session-id` 还是 `--resume`；远程会话改成起回合前经中转查一次容器里的记录文件，判断规则不变。
- 模型列表、推理强度、额度查询：仍然由管理器本地的驱动给（同一个账号，结果一样）。回合输出里带的额度事件照常记账。
- 环境变量只给白名单：三个配置目录、`HOME`、`PATH`、代理变量、自动压缩的设置、`CODEBUDDY_IS_SANDBOX`（只在“可执行命令”档）、注入的凭据（第 9 节）。不带管理器自己的令牌。

### 6.2 管理器里要改的地方

- 驱动起进程的地方抽成一个“运行端”接口：`spawn(命令, 工作目录, 环境变量, 标准输入) → 逐行读输出、等结束、停止`。
  `LocalRuntime` 就是现在的 `asyncio.create_subprocess_exec`；`RemoteRuntime` 把这些变成远程操作（第 8 节）。`cli_stream.py` 逐行解析的代码不变。
- Codex 驱动加一条“按回合起 `codex exec`”的路径，只给远程会话用；本地会话仍然用 app-server。
- `engine.py` 建会话：远程环境时，建目录、克隆仓库、写固定参考资料（`AGENTS.md` / `CLAUDE.md`）都变成一个 `prepare_session` 远程操作；附件用 `put_files`；归档会话时 `remove_session`。
- 会话记录的 `workdir` 写成 `remote:<容器号>:/workspace/sessions/<会话号>`，管理器自己的文件浏览接口对远程会话返回“由工作台浏览”（第 10.2 节）。
- 远程回合多两种失败原因：`unavailable`（容器服务器离线、容器起不来、镜像版本不一致）和 `unknown`（中转断了，不知道容器里的进程做到哪一步，沿用现有语义）。

### 6.3 远程会话暂不支持的

页面和工具结果里写明，不假装支持：

- Codex 的插话（app-server 才有，`exec` 没有）。
- 压缩钩子（钩子脚本现在在管理器里，要搬进容器）。
- 官方程序里“账号下已有的会话”同步（`scope=account`）不扫远程容器。

## 7. 托管进程：容器服务器的新指令

现有的 `exec` 不够用（没有标准输入、结束才回报、超时就停整个容器），新增三条固定指令。runner-agent 仍然只执行工作台下发的固定指令，容器参数仍由它自己生成。

| 指令 | 做什么 |
|---|---|
| `proc_start` | 参数：环境、进程号（幂等）、种类（`turn` / `login` / `job`）、命令参数数组、工作目录、环境变量、标准输入（不超过 2 MB）、时限。runner-agent 确保容器在运行（停止的自动启动），把标准输入写进 `/workspace/.mw/procs/<号>/stdin`，用 `docker exec -d` 起托管脚本 |
| `proc_signal` | 对整个进程组发 TERM，10 秒后还在就 KILL（Debian 的 `sh` 里写 `kill -TERM "-<进程组号>"`，核验记录 V9） |
| `proc_input` | 只给登录用：往进程的输入管道写一小段（不超过 4 KB，例如粘贴的授权码） |

托管脚本：

- 作为 `sh -c` 的参数下发，**不放在容器里可写的位置**（免得被容器里的程序改掉）。
- `setsid` 起新的进程组；标准输出写 `out`，标准错误只留最后 64 KB 写 `err`，退出码写 `exit`，进程号写 `pid`。
- 标准输入读 `stdin` 文件，读完即删；`login` 种类改用一个命名管道，接 `proc_input`。

输出回传：

- runner-agent 对每个运行中的托管进程读 `out` 的新增部分（实现时在锁定的 Docker 上选定具体做法：一条长连接的 `tail`，或按偏移定时读），每 0.5 秒或每 64 KB 一块，
  `POST /runner-api/v1/procs/{号}/chunks`（带起始偏移）。工作台确认收到的偏移，重复的块按偏移去重。
- 进程结束：回报退出码、`err` 的末尾、总字节数；工作台确认后，runner-agent 删除这个进程的目录。
- 单个回合回传上限 64 MB，超过就停掉进程，回合失败并写明“输出过大”。

断线与重启：

- runner-agent 重启或和工作台断开：容器里的进程照样跑，输出照样写盘。runner-agent 回来后，在每分钟的对账里上报运行中的托管进程和各自的偏移，工作台从确认过的偏移接着收。
- 时限由 runner-agent 在本机执行（工作台掉线也守得住），到时限停整个进程组，**不停容器**（和 `exec` 不同）。
- 容器被停止或丢失：进程结果记为“未知”，回报给工作台。

记录：每个托管进程在容器服务器的运行记录（`runner_runs`）里记一条，命令只写“种类 + 平台 + 会话号”，不记提问内容和凭据；回收据此认为容器正忙。

## 8. 工作台中转

### 8.1 为什么由工作台来取

- 管理器有三种部署方式：本机（工作台的 Compose 里）、同一台服务器（工作台的内部网络）、别的服务器（工作台经 SSH 通道访问它的本机端口）。三种方式下，都只有“工作台访问管理器”这个方向是通的。
- 所以远程操作由管理器排队，工作台用长轮询来取；输出由工作台推给管理器。不需要新的网络路径、新的凭据，也不用改转发密钥的限制。

### 8.2 管理器新增的管理接口（只认管理令牌，只给工作台用）

| 接口 | 作用 |
|---|---|
| `GET /remote/ops?wait=25` | 取待办的远程操作（最多 20 条）；没有就等，最多 25 秒 |
| `POST /remote/ops/{操作号}/result` | 操作的结果（成功的数据或错误） |
| `POST /remote/procs/{进程号}/chunks` | 推输出块（偏移、数据） |
| `POST /remote/procs/{进程号}/exit` | 进程结束（退出码、状态、错误末尾） |

远程操作：`prepare_session`、`start_proc`、`signal_proc`、`input_proc`、`put_files`、`stat_path`（续接判断）、`remove_session`、`container_status`。
每个操作有操作号；管理器重启时把没完成的操作标为失败，对应回合按现有规则记为“结果未知”。

### 8.3 工作台这边

- 每个“有远程开发环境、而且启用了”的管理器，工作台跑一个中转循环；用 Redis 锁保证多个 API 进程里只有一个在跑。管理器没有远程环境时不轮询。
- 拿到操作先校验：操作里的容器是这个管理器、这个工作空间的远程开发容器；容器不在“待删除 / 已删除”；进程种类和命令符合这个环境的平台（只能起这个平台的命令行，`login` 只能起登录子命令）。
  管理器是工作台自己部署的组件，这一层是纵深防御：就算管理器被攻破，也只能在自己的容器里起自己平台的命令行。
- 转成容器服务器的指令，等结果，回报给管理器；runner-agent 推来的输出块直接转给管理器（管理器暂时连不上时在 Redis 里最多缓存 10 分钟、16 MB，再不行就停掉进程并回报“结果未知”）。
- 提问内容和输出只在内存和 Redis 里过一下，不写工作台数据库；凭据同样只在内存里，按容器服务器现有的 `secret_values` 做法在 runner-agent 领指令时才放进去（第 9 节）。

### 8.4 延迟

- 容器在运行时，从发出消息到容器里的进程起来，目标 3 秒以内（两段长轮询都是有活就立即返回）。
- 输出每 0.5 秒一块，聊天页逐字显示比本地慢 1 ~ 2 秒。开发回合本身动辄几十秒到几十分钟，可以接受。
- 容器停止时要先启动（几秒）；镜像需要重建时要几分钟，回合进度里写明。

## 9. 登录凭据怎么进容器（D1，最关键的取舍）

容器里的官方程序要登录才能用模型。各平台在管理器里的登录方式不同，有的凭据会自己刷新。三种做法：

| | 甲：每回合临时注入 | 乙：容器里单独登录同一个账号 | 丙：代理代为认证 |
|---|---|---|---|
| 做法 | 管理器把这个平台的凭据随回合下发，作为进程的环境变量注入，回合结束就没了 | 在页面上对这个容器点“登录 Claude / Codex / CodeBuddy”，流程和管理器的登录一样（网址和验证码、粘贴授权码），凭据留在容器数据卷的 HOME 里，官方程序自己刷新 | 出口代理对模型接口做 TLS 中间人，按请求换成真凭据；容器里只有假凭据 |
| 容器里的程序能不能拿到真凭据 | 回合进行中能 | 一直能 | 不能 |
| 额外操作 | 无 | 每个容器每个平台登录一次 | 无 |
| 主要问题 | 会刷新的登录（ChatGPT 登录、Claude 网页授权）在管理器和容器两处刷新，刷新令牌如果是轮换的，一处刷新会让另一处作废，管理器可能掉线【未核验，V4】 | 账号多一个登录设备；删容器时要记得在平台上撤销 | 要做 TLS 中间人、按平台核验；订阅登录的令牌经第三方代理改写可能不符合平台条款；工作量最大 |

**推荐：按凭据种类分开处理。**

| 管理器里的登录方式 | 远程容器里 |
|---|---|
| API 密钥（三家都支持）、Claude 的长期令牌（`setup-token`） | **甲**：不会刷新，每回合随进程注入；页面上不用做任何事 |
| Codex 的 ChatGPT 登录、Claude 的网页授权登录、CodeBuddy 的账号登录 | **乙**：在容器里单独登录一次；各自一条刷新链，互不影响 |

- 乙登录后，管理器在容器里查一次账号（用各平台的状态命令），和管理器这个平台的账号比对。不是同一个账号就拒绝在这个容器里开这个平台的回合，页面上写明（“一个管理器每个平台一个账号”，`LLM_BRIDGE_PLAN.md` 第 8 节）。
  查不到账号的（API 密钥类）按 `LLM_BRIDGE_PLAN.md` 第 18 节第 12 条的“未知账号”规则处理。
- 管理器里“更换账号”时，远程容器里这个平台的登录标成“账号不一致”，要重新登录。
- 删除容器前，页面提示到平台的设备管理里撤销这次登录（工作台做不到替你撤销）。
- 第 16 节 V4 如果证明刷新令牌不轮换、两处可以共用，就把甲扩大到所有登录方式，省掉乙的手动登录。
- 丙列为以后的加强（第 20 节）。
- 不管哪种，页面上都写明：**容器里执行的命令能读到这个平台的凭据**。建议给远程容器用专用的 API 密钥，网络用默认的“只连模型接口和代码仓库”。

| `runner_environments` 新列 | `owner_kind`（`instance` 默认 / `llm_bridge`）、`owner_bridge_id`（可空）、`no_auto_archive`（默认 false）。约束：`llm_bridge` 归属时 `owner_bridge_id` 不为空；管理器删除前先处理它的容器 |
| `runner_commands` | 新指令种类 `proc_start` / `proc_signal` / `proc_input`；凭据不落库 |

**管理器**（SQLite，`CREATE TABLE IF NOT EXISTS`，不改旧表的含义；退回旧版本时新表被忽略、远程环境不可用）：

| 表 / 字段 | 内容 |
|---|---|
| `environments.config` | 加 `location`（`local` / `remote`）和 `remote_container`（工作台给的容器号，管理器不知道容器服务器的任何细节） |
| `remote_ops` | 操作号、种类、会话、回合、参数（不含凭据）、状态、结果、时间 |
| `sessions.workdir` | 远程会话写 `remote:<容器号>:/workspace/sessions/<会话号>` |

数据字典、接口契约（`docs/api-contract.md`）、OpenAPI 与前端生成的类型同步更新。

## 12. 接口

**工作台**（都在 `/api/v1` 下）：

| 接口 | 角色 | 说明 |
|---|---|---|
| `GET /llm_bridge/remote/targets` | admin | 能选的容器服务器（剩余资源、不能选的原因）、内置镜像信息、工作空间上限与已用 |
| `GET /llm_bridge/bridges/{id}/containers` | admin | 这个管理器的远程容器（状态、资源、在用的环境、各平台登录） |
| `POST /llm_bridge/bridges/{id}/containers` | owner | 新建远程容器（`request_id` 幂等） |
| `PATCH /llm_bridge/bridges/{id}/containers/{cid}` | owner | 改资源、网络、空闲停止（带版本号） |
| `POST /llm_bridge/bridges/{id}/containers/{cid}/actions` | owner | `start` / `stop` / `update_image` / `retry` / `delete` |
| `POST /llm_bridge/bridges/{id}/containers/{cid}/login/{platform}` | owner | 在容器里登录（开始、送授权码、取消；和管理器的登录接口同样的形状） |
| `POST /llm_bridge/bridges/{id}/environments` | owner | 请求体加 `location`、`remote_container`（已有容器）或 `new_container`（新建容器的参数）；新建时先建容器再登记环境，任何一步失败都撤回 |
| 现有的会话文件浏览三个接口 | admin | 远程会话改由工作台经容器服务器读；路径与返回不变 |
| `GET /runner/environments`（已有） | admin | 返回多 `owner_kind`、`owner_label`、`owner_link` |
| `POST /runner/environments/{id}/actions`（已有） | admin | 对远程开发容器的 `archive` / `delete` / 改删除条件返回 `409 MANAGED_BY_LLM_BRIDGE` |

**runner-agent 接入**：`POST /runner-api/v1/procs/{号}/chunks`、`POST /runner-api/v1/procs/{号}/exit`；每分钟的上报里加运行中的托管进程与偏移。

**智能体工具**：不加新工具。`llm_bridge_environments` 的结果多 `location: "remote"` 和一句说明（例如“云端容器：可以装依赖、跑测试”）；`llm_bridge_session_create` 不变。
远程容器在建、在启动、需要登录时，建会话和发消息返回明确的错误（`UNAVAILABLE`，写明原因），不排一个注定失败的回合。

写操作都带 CSRF、校验工作空间与角色、`request_id` 幂等、记审计。不涉及任何服务器密码：容器服务器上的操作都经 runner-agent。

## 13. 安全与规则

| 风险 | 做法 |
|---|---|
| 容器里的命令带走凭据 | 第 9 节；默认网络只放行模型接口和代码仓库；出口代理记录访问；页面明示风险；建议专用的 API 密钥 |
| 一个管理器动别的容器 | 工作台按“管理器 + 工作空间 + 容器”校验每个操作；只能起这个环境平台的命令行 |
| 容器连回控制面 | 出口代理永远挡住私有网段、工作台、OpenClaw 服务器、MCP 管理器；整个设计不需要容器主动连任何控制面 |
| 提问和输出经过工作台 | 只在内存和 Redis 里转一次，不落工作台数据库；落库的仍只在管理器（和现在一样） |
| 托管脚本被容器里的程序改掉 | 脚本作为参数下发，不放在容器里可写的位置 |
| 浏览工作目录读到凭据 | 限定在会话目录里，解析符号链接后再检查；`.home`、`.mw` 永远不能读；预览脱敏 |
| 资源被长期占用 | 空闲停止、工作空间上限、整机容量检查 |

和现有规则的关系：

- **例外九**（`docs/AGENTS.md` 第 8 节）写着“开发会话只能使用管理员定好的环境与许可策略”。远程容器由 owner 在页面上建、策略由管理员定，智能体仍然只经 `llm_bridge_*` 工具、不能建或改容器，所以在例外九的范围里。
  为了不留歧义，人类 2026-11-18 决定（D6）在例外九末尾补了一句：
  > 开发环境可以是管理员在容器服务器上建的远程开发容器：建、改、删这些容器只能由 owner 在工作台页面上做，智能体不能经这些工具建、改、删容器；这些容器沿用例外八的宿主保护（不得使用特权模式、挂载 Docker socket 或宿主目录、使用宿主网络，不得访问私有网段、工作台与 OpenClaw 服务器）。
- **例外八**是智能体自己操作容器服务器；本方案里智能体拿不到容器服务器的工具，不涉及。
- **OpenClaw 服务器**仍然不开 exec、不挂 Docker socket。
- **容器服务器**：“runner-agent 只执行工作台下发的固定指令”不变，新加的三条也是固定指令；宿主保护在 runner-agent 本机生成参数时强制。
- **第三方接口核验**：第 16 节。核验不了的（例如某个平台在容器里登录走不通）做成接口桩，页面上写明“这个平台暂时只能用 API 密钥”，不标完成。
- **设置放在网页上**：建容器、登录、改资源都在页面上完成，不需要在服务器终端里做任何事。

审计：`remote_container_created` / `updated` / `deleted`、`remote_login_started` / `finished`、`remote_image_updated`，记管理器、容器、服务器、操作人，不记凭据和提问。

## 14. 与长时间任务（PR #255，T-0291 / T-0292）的衔接

PR #255 给管理器加了托管后台作业和会话里的 `llm-task` 命令（`docs/v2/LLM_BRIDGE_LONGRUN_PLAN.md`，已合并进 main `1d6046c`，`docs/AGENTS.md` 例外十）。本方案的实施在它之上做，衔接如下：

- 那份方案自己写了“重的作业不放在管理器上”，远程容器正好是它说的去处。
- **后台作业**：远程会话的作业用本方案的托管进程（种类 `job`）跑在容器里，进程组、日志上限、先 TERM 再 KILL 的做法和它的 `jobs.py` 一致；作业状态仍在管理器的 `jobs` 表里。
- **`llm-task` 命令**：它现在经本机地址（`BRIDGE_SESSION_API_URL`，默认 `http://127.0.0.1:8787`）的 `/session-api` 找管理器、靠回合令牌认身份。容器里连不到管理器，所以远程会话里改成“请求文件”：
  命令把请求写进会话目录的 `.llm-task/requests/`，runner-agent 在这个会话有回合在跑时顺带把新请求转上来，管理器处理后把结果写回 `.llm-task/responses/`，命令最多等 15 秒。
  这一项放在第 3 期（第 18 节），第 1、2 期的远程会话里 `llm-task` 不可用，并关掉 Claude / CodeBuddy 的官方后台任务（和那份方案的做法一致）。
- 例外十的保护（只有“可以执行命令”档能开作业、会话归属、限额、执行记录、审计、通知管理员）在远程会话里同样适用；`llm-task` 在内置镜像里也装在 root 拥有的目录里，容器里的普通用户改不了。
- **单回合时限**：用那份方案加的“按开发环境单独设”的时限，托管进程的时限等于它再加 60 秒。

## 21. 实施接口（契约，2026-11-18 人类要求“根据这份方案全面落实代码”）

三部分并行开发（runner-agent、MCP 管理器、工作台），以本节为准；实施中改了哪里就同步改这一节。

### 21.1 容器里的路径

| 路径 | 用途 |
|---|---|
| `/opt/mw/cli/bin/{node,claude,codex,codebuddy}` | 内置镜像里的命令行（root 拥有），`PATH` 最前面是 `/opt/mw/cli/bin` |
| `/workspace/sessions/<会话号>/` | 会话的工作目录 |
| `/workspace/.home/` | `HOME`；`CLAUDE_CONFIG_DIR=/workspace/.home/.claude`、`CODEX_HOME=/workspace/.home/.codex`、`CODEBUDDY_CONFIG_DIR=/workspace/.home/.codebuddy` |
| `/workspace/.mw/procs/<运行号>/` | 托管进程：`stdin`、`out`、`err`（只留最后 64 KB）、`pid`（进程组号）、`exit`、`in`（命名管道，只有交互进程有） |

### 21.2 管理器 ⇄ 工作台（管理器的管理接口，管理令牌）

| 接口 | 请求 | 应答 |
|---|---|---|
| `GET /admin/remote/ops?wait=0..25&limit=1..20` | — | `{"ops": [op, ...]}`；取走的操作标为 `sent`；`sent` 超过 60 秒没回结果的会再次给出（工作台按操作号去重） |
| `POST /admin/remote/ops/{op_id}/result` | `{"ok": true, "data": {...}}` 或 `{"ok": false, "error": {"code": "...", "message": "..."}}` | 204；不认识的操作 404 |
| `POST /admin/remote/procs/{proc_id}/output` | `{"offset": 已确认的字节数, "data_b64": "..."}` | `{"acked": 新的已确认字节数}`；`offset` 小于已确认数时只返回已确认数（重复的块），大于时 409 并带 `acked`；不认识的进程 404（工作台随后停掉它） |
| `POST /admin/remote/procs/{proc_id}/exit` | `{"exit_code": int\|null, "state": "exited"\|"killed"\|"timeout"\|"lost"\|"failed", "error": str\|null, "stderr_tail": str}` | 204；只在输出全部确认后发 |

操作（`op`）：`{"id": "ro_…", "kind": …, "container": "<远程容器号，工作台的 UUID>", "args": {…}, "created_at": 秒}`

| kind | args | 成功的 data |
|---|---|---|
| `start_proc` | `proc_id`（`rp_…`）、`purpose`（`turn` / `login` / `job` / `prepare`）、`platform`（`codex` / `claude` / `workbuddy`，`prepare` 时为 null）、`session_id`、`argv`、`cwd`、`env`（不含密钥）、`secret_env`（凭据，只在内存里转）、`stdin_b64`、`timeout_seconds`、`interactive`；`prepare` 另有 `repo_url`、`branch`（工作台自己拼命令，忽略 `argv`） | `{"run_id": "<容器服务器运行号>"}` |
| `signal_proc` | `proc_id`、`signal`（`TERM` / `KILL`） | `{}` |
| `input_proc` | `proc_id`、`data`（≤ 4 KB） | `{}` |
| `put_files` | `session_id`、`files: [{"path": 相对会话目录, "b64": …}]`（合计 ≤ 20 MB） | `{"written": n}` |
| `helper` | `name`：`remove_session`（`session_id`）、`transcript_exists`（`platform`、`native_id`）、`versions`（无） | `{"exit_code": int, "output": str}`；`transcript_exists` 另给 `{"exists": bool}`，`versions` 另给 `{"versions": {"codex": "0.169.0", ...}}` |
| `status` | — | `{"state": 容器状态, "host": 服务器名, "cpus", "memory_mb", "versions_ok": bool}` |

工作台校验：容器属于这个管理器和工作空间、不在待删除 / 已删除；`turn` / `login` 的 `argv[0]` 必须是这个平台的命令行（`codex` / `claude` / `codebuddy`，或 `/opt/mw/cli/bin/` 下的同名文件），`login` 的第二个参数必须是登录子命令；`job` 的 `argv` 必须是 `["bash", "-c", 命令]`；路径都必须在 `/workspace/sessions/<会话号>` 下。

### 21.3 工作台 ⇄ runner-agent

- 托管进程记在 `runner_runs` 里：新列 `kind`（`exec` 默认 / `proc`）、`owner_kind`、`owner_ref`、`acked_offset`。状态沿用：`queued` → `running` → `done` / `failed` / `timeout` / `unknown`；没结束的运行让回收认为容器正忙。
- 新指令（`runner_commands.kind`）：
  - `proc_start`：载荷 = 环境的 `runtime_payload` + `{"run_id", "proc_dir", "argv", "cwd", "env", "timeout", "interactive"}`。标准输入和凭据不落库：放在 Redis `runner:proc-input:<指令号>`（10 分钟过期），runner-agent 领指令时工作台才放进 `payload["proc_input"] = {"stdin_b64", "secret_env"}` 并删掉 Redis 里的；取不到时放 `{"missing": true}`，runner-agent 回报失败“输入已过期”。结果 `{"started": true, "pgid": int}`。
  - `proc_signal`：`{"env_id", "container", "run_id", "proc_dir", "signal"}`；结果 `{}`。runner-agent 用 `kill -TERM "-<进程组号>"`，`TERM` 后 10 秒还在就 `KILL`。
  - `proc_input`：`{"env_id", "container", "run_id", "proc_dir"}` + 领指令时注入的 `payload["proc_input"] = {"data"}`；写进命名管道 `in`。
- 新接口（运行服务器凭证）：
  - `POST /runner-api/v1/procs/{run_id}/output`：`{"offset", "data_b64"}`（每块 ≤ 256 KB）→ `{"acked"}`；工作台按 `owner_kind` 交给模块（21.4），模块转给管理器。
  - `POST /runner-api/v1/procs/{run_id}/exit`：`{"exit_code", "state": "exited"|"killed"|"timeout"|"lost", "stderr_tail", "error"}` → `{"accepted"}`；工作台结束这条运行并交给模块。
  - `POST /runner-api/v1/report` 的应答加 `procs: [{"run_id", "env_id", "container", "proc_dir", "acked", "timeout_at"}]`：这台服务器上还在跑的托管进程，runner-agent 据此（重启后）接着读。
- runner-agent 的读取：每个托管进程每 0.5 秒（连续 10 秒没有新输出后每 2 秒）用一次 `docker exec` 读 `out` 的大小、`exit` 和从已确认处开始的最多 256 KB；超过时限先 `TERM` 后 `KILL`，回报 `timeout`；容器没了回报 `lost`；`exit` 出现且输出全部确认后回报结束，再删掉进程目录。

### 21.4 工作台的核心与模块

- `runner_environments` 新列：`owner_kind`（`instance` 默认 / 模块 key，例如 `llm_bridge`）、`owner_ref`、`owner_label`、`no_auto_archive`（默认 false）。`owner_kind != 'instance'` 的环境：不算孤儿、不按实例配额、不自动归档（`no_auto_archive`）、空闲停止看 `runtime_metadata.idle_stop_seconds`（0 表示不停）；容器服务器页面上归档 / 删除 / 改删除条件返回 `409 MANAGED_BY_MODULE`。
- 模块清单新字段 `runner_proc_sink: "包.模块:属性"`：对象有 `async output(db, settings, run, offset, data) -> int` 和 `async exit(db, settings, run, info) -> None`。核心按 `owner_kind`（模块 key）找它。
- 核心给模块用的函数在 `app/domain/runner_managed.py`：建容器、启动 / 停止 / 删除、改资源、起托管进程、发信号、送输入、跑一条辅助命令并等结果、写文件、列目录、读文件。

### 21.5 页面接口

见第 12 节；字段名以 `services/api/openapi.json` 为准。

## 22. 实施记录（与方案不同或方案没写到的地方，2026-11-18）

人类 2026-11-18 要求“根据这份方案全面落实代码”。分三路实现（runner-agent、MCP 管理器、工作台与页面），接口按第 21 节。

1. **托管进程挂在“运行记录”上**：没有另建 `runner_procs` 表，而是 `runner_runs` 加 `kind=proc`（迁移 0079）。没结束的运行本来就让回收认为容器正忙，所以“正在跑回合的容器不回收”不用另写。
2. **托管进程的输入不落库**：标准输入（提问、图片）和凭据用工作台的凭证密钥加密后放 Redis（10 分钟过期），runner-agent 领指令时才解开、取一次就删。交互输入（登录的授权码）也一样。
3. **回收**：模块建的环境不算孤儿（原来“没有创建者实例”的环境会被删）；不自动归档（资源紧张时也只停止）；空闲停止看容器自己的设置（0 = 不停）。
4. **镜像**：内置模板按服务器建（名字 `mw-llm-dev-<服务器号前 8 位>`），模板构建好了以后由定时任务 `remote_tick` 接着建容器。自定义镜像 / 模板再加一层命令行（`COPY --from=<内置镜像>`），派生模板按容器建。“更新镜像”：按新版本重建模板，好了以后 `create_env` 带 `recreate`，runner-agent 删旧容器、按新镜像重建，数据卷保留。
5. **中转**：工作台的定时任务每分钟一次、跑约 50 秒，对每个有远程容器的管理器长轮询；长轮询时不占数据库连接。输出由 runner-api 的请求直接转给管理器；管理器暂时收不下时不确认，runner-agent 从已确认处重发（输出还在容器里），所以没有用 Redis 缓存输出。结束转不出去的由定时任务补发。
6. **工作台的校验**（21.2）：登录进程的工作目录是 `/workspace/.home`、第二个参数是 `login`（Codex）或 `auth`（Claude）；后台作业是 `bash -c`，管理器在命令前加 `exec 2>&1`；`HOME` 由容器设定，调用方传的会被丢掉，代理变量不能改。
7. **管理器这边**（`services/llm-bridge`）：
   - 固定参考资料不写进仓库的 `CLAUDE.md` / `AGENTS.md`（会覆盖仓库自己的），改为每回合作为系统提示带上（Codex 用 `-c developer_instructions=…`）；
   - 远程 Codex 只有“可执行命令”档（核验记录 V2）；
   - Codex 在容器里登录后查不到邮箱，记为 `ready` 并提示人确认是同一个账号；
   - 版本表按程序名（`codex` / `claude` / `codebuddy`）比对；管理器读不到自己的版本时（开发、测试环境）跳过检查。
8. **会话里的 `llm-task`** 在远程会话里暂不可用（返回 `NOT_SUPPORTED`，写明原因）；后台作业从页面或外层智能体的工具开时照常在容器里跑。第 14 节说的“请求文件”做法留到下一期。
9. **页面**：容器建好后能改网络、另加的域名和空闲停止；资源不能改（要更大的新建一个）。远程会话的文件下载上限是 20 MB（容器服务器读文件的上限），本地会话仍是 50 MB。
10. **上限**（D8）固定为 5 个 / 16 核 / 32 GB / 200 GB，还没有设置页面。
11. **默认网络是“全部外网”**（和 D4 不同）：订阅账号登录、刷新令牌要连的域名还没核验完（V3 的登录部分、V5），默认只连模型接口的话，会刷新的登录可能在容器里失败。页面上三档都能选，只用 API 密钥时可以改成“只连模型接口和代码仓库”。V3、V5 核验后再把默认改回 D4。
12. **旧接入包**：托管进程的三条指令和按新镜像重建从 runner-agent 0.4.0 起才有，旧版本会回“不支持的指令”。工作台在建容器、起进程、重建之前先看这台服务器上报的 runner-agent 版本，旧了就不派指令，直接提示“请在容器服务器页面重新部署接入包”；选服务器的列表里也写明这个原因。
13. **集成审查（#235，固定 head `8cb2df6`）后补的**：
    - **模块的模板只有模块能改**：`runner_templates` 加 `owner_kind`（迁移 0079）。`mw-` 开头的新模板名留给模块，智能体和管理员都不能建；模块建的模板，智能体和管理员都不能保存、停用、重建（`409 MANAGED_BY_MODULE`）。模块遇到同名、但不是它建的模板（例如保留之前抢注的）不用、不改，换备用名（`-2` … `-5`）。
    - **辅助命令超时不停共享的容器**：删会话目录、查会话记录、查版本、文件浏览都在容器里带 `timeout -s KILL`，runner-agent 看到 `keep_container` 时超时只结束这一条。删除会话目录改为先挪进 `/workspace/.trash`、再在后台删，马上返回。
    - **托管进程不会永远“正在运行”**：runner-agent 读输出时顺带看进程组还在不在；进程组没了却没有结束记录（外壳被杀），宽限 30 秒后报 `lost`；发了 KILL 之后 30 秒还没有结束记录，按 `timeout` / `killed` 上报。工作台的回收再兜底：过了时限加 30 分钟起进程的时限、再宽限 15 分钟还没结束的，记为结果未知并通知模块。
    - **查版本也只给白名单环境变量**：`CodexDriver.version()` 和 app-server 用同一份（T-0293）。
    - **留下的容器会被删掉**：登记删了（删除远程容器、移除管理器）但容器服务器那边的删除失败时，模块的定时任务找到“归 MCP 管理器、却没有登记”的环境再删，失败的每 10 分钟重试。
    - **新建不会重复**：新建远程容器、新增开发环境带 `request_id`（页面每次打开弹窗生成一个）；同一个工作空间的新建排队做，配额检查不会被并发绕过。
14. **没做的**：管理器级的远程容器总览页（现在从用它的开发环境进入）；Kubernetes 类容器服务器；真实账号下的 V1、V4、V5、V7（要人类验收）。
