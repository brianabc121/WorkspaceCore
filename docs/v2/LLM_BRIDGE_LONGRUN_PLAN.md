# 大模型客户端：长时间任务（后台作业、预约回来、循环）的优化方案

> 状态：**人类 2026-11-18 已决定（第 10 节），四期一起实施**（任务一：第 1、2 期；任务二：第 3、4 期；编号在 #235 预留）。起草：claude，2026-11-18。
> 范围：MCP 管理器上的开发会话怎样跑几个小时的任务、过几个小时回来看结果、根据结果再跑下一轮；
> 人和调用它的智能体怎样看到后台在跑什么、怎样停掉。
> 依据：
> - 现有代码（第 2 节，带文件和行号，main `4501ee7`）；
> - 锁定版本的三个官方程序（第 3 节）：Claude Code 2.1.323 和 CodeBuddy Code 2.184.0 看的是程序文件，Codex 0.169.0 看的是 `rust-v0.169.0` 源码，再对照官方文档；**没有跑过真实回合**；
> - 业内做法（第 4 节）：官方文档或博客写明的标“写明”，推出来的标“推断”。有几个站点本会话打不开，用的是搜索引擎对官方页面的摘录，采用前要再核对一遍关键数字。
>
> 第 10 节是人类的决定；第 12 节是实施情况。

## 1. 结论先说

1. **核心原则：等待不占回合。** 跑几个小时的东西交给管理器托管（“作业”），模型这一回合只做两件事：开作业、预约什么时候回来。然后回合就结束。
   作业结束或到了预约的时间，管理器给**同一个会话**发一条标明“系统发的、不是人发的”的消息，开新的一回合接着干。
   - 业内都是这么做的：Temporal 的定时器等待期间不占 worker；Inngest 的 sleep 不占并发名额；Devin 空闲时休眠，CI 失败时被唤醒；Claude 的 SDK 在后台任务完成时注入一条合成消息开新一轮（第 4 节）。
   - 对我们更要紧的是：现在一个等 CI 的回合会一直占着这个平台 3 个并发名额中的一个，还会撞上单回合时限（第 2.2 节）。
2. **官方程序自己的后台功能不能当地基。**
   - Claude Code 用 `-p` 时，回答完会先等后台命令，但最多等 10 分钟（用文本传提示词时），进程退出时把后台进程全部杀掉。
   - Codex 的后台进程能跨回合活着，但进程结束时不会叫醒模型，官方的相关 issue 还开着。
   所以作业要由管理器自己托管：独立的进程组、日志写盘、状态写进数据库。
3. **管理器已经有大约一半的零件**：
   - 持久化的回合队列；
   - 到点自动发起回合（额度恢复后自动继续用的就是它）；
   - 回合结束后叫醒发起的智能体；
   - 智能体给自己定时。

   要补的是：作业表、预约表、一个统一的调度协程、能看清进度的状态，以及给会话里的模型用的小工具和护栏。
4. **分四期做，每期单独能用**（第 9 节）：
   1. 先看得见：回合进行中显示正在跑的命令、跑了多久、最后一次有动静的时间；接上官方程序报出的后台任务事件；单回合时限可以按开发环境单独设。
   2. 预约回来：人和外层智能体可以说“3 小时后对这个会话说……”。
   3. 托管作业：作业结束后自动接着做，页面上有“后台任务”面板。
   4. 让会话里的模型自己开作业、自己预约回来，带循环护栏。

   人类 2026-11-18 决定：会话里的模型可以自己开作业、自己预约；外层智能体的新工具直接执行、不审批（第 10 节）。四期一起实施。
   **常驻的官方程序进程**（Claude 的流式输入模式）暂时不做，理由见 5.11。

## 2. 现在的情况（2026-11-18，main `4501ee7`）

| 隔离的长时间执行环境 | 工作台的运行环境（`docs/v2/RUNNER_PLAN.md`，`runner_*` / `env_*` 工具） | 智能体在运行服务器上建容器、执行命令；和管理器的会话工作目录不在同一个地方 |

### 2.2 缺口

1. **长时间等待会占住回合。**
   - 单回合时限默认 1800 秒，按总时长算（`engine.py` 60、1264 行），超过就中断、记为失败；最多只能调到 6 小时，而且整个管理器只有一个值。
   - 每个平台同时只跑 3 个会话（`concurrency`）。一个在等 CI 的回合会占住一个名额，别的会话只能排队。
2. **回合进行中看不清。**
   - Codex 驱动只在命令**跑完**时记一步（`drivers/codex.py` 586 行只处理 `item/completed`），命令跑的过程中 `progress` 还停在上一句话。
   - 没有“最后一次有动静的时间”和“这条命令跑了多久”，调用方分不清是在等 CI 还是卡住了，可能误取消。
   - 命令输出要等跑完才有。
3. **官方程序的后台任务管理器看不见，长了就会被停掉。**
   - 管理器每发一条消息启动一次 `claude -p`，写完问题就关掉标准输入（`drivers/cli_stream.py` 835–851 行）。
   - Claude 回答完先等后台命令，但用文本传提示词时最多等 10 分钟；进程退出时把后台进程全部杀掉（第 3 节）。
   - 程序报出的后台任务事件（`task_started`、`task_notification` 等）驱动全部忽略（`cli_stream.py` `_on_system` 只处理压缩相关的事件）。
4. **会话里的模型不能自己预约回来。** 只有外层智能体能用 `schedule_wakeup` 定时；它醒来后要自己记得去哪个会话发什么。
5. **管理器重启时，进行中的回合记为“结果未知”**（`engine.py` 374–381 行），不会接着做。

## 3. 三个官方程序自己能做什么

| | Claude Code 2.1.323 | CodeBuddy Code 2.184.0 | Codex 0.169.0 |
|---|---|---|---|
| 后台命令 | Bash 的 `run_in_background`：立即返回任务号，输出写进文件。前台命令到超时（默认 2 分钟，最长 10 分钟，程序里是 `120000` / `600000`）不杀，而是转到后台（写明） | 有 `run_in_background`（类型定义里有） | `exec_command` 等 0.25–30 秒后返回进程号，命令留在后台，模型用 `write_stdin` 轮询；最多 64 个进程（源码） |
| 回答结束时 | `-p` 先等主对话启动的后台命令跑完，再多跑一轮处理结果。后台命令的时限：无人值守默认 30 分钟、最长 2 小时，**用文本传提示词时默认 10 分钟**；后台子代理和 Monitor 最多等 10 分钟（`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`）（写明；程序里有 `1800000` / `7200000` 和这个变量） | 没有核实 | 回合结束，后台进程继续活在 app-server 进程里（源码） |
| 跨回合 / 跨进程 | 进程退出时杀掉所有后台进程，连 `setsid` 脱离的也杀；`--resume` 不会重启它们（写明） | 没有核实 | 跨回合活着；app-server 进程重启就没了（推断） |
| 完成后叫醒模型 | 只在常驻的 SDK 流式输入模式下：完成时注入一条合成消息、自动开新一轮，并注明“没有人类输入”（写明） | 没有核实 | **不会**。“进程退出时唤醒”和“轮询浪费 token”的 issue（openai/codex #32188、#13733）还开着 |
| 关掉后台功能 | `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`：命令到超时直接停止（写明；程序里有） | `CODEBUDDY_CODE_DISABLE_BACKGROUND_TASKS`（程序里有） | 没有对应开关（`background_terminal_max_timeout` 默认 300 秒，只管一次轮询最多等多久） |
| 能拿到的事件 | stream-json 的 `system` 事件：`task_started`、`task_progress`、`task_updated`、`task_notification`（程序里有；字段要再核对） | `task_started`、`task_progress`、`task_notification`（程序里有） | `item/started`（带 `processId`、`source`）、`item/commandExecution/outputDelta`（流式输出）、`terminalInteraction`、`item/completed`（源码）；另有实验接口 `thread/backgroundTerminals/*` |
| 定时 | `/loop`、Cron 只在会话常驻且空闲时触发，错过的不补；云端定时任务最短 1 小时（写明） | 没有核实 | Codex 桌面应用有定时任务；命令行和 app-server 里没有（摘录） |

结论：**三家都只保证“一个官方程序进程活着的时候”的后台**，而我们的驱动每回合起停一次进程（Codex 的 app-server 也会因为升级、重启而换掉）。跨小时的东西必须由管理器自己保管。

## 4. 业内怎么做

### 4.1 编码智能体产品

| 产品 | 后台执行 | 过一段时间再回来 | 可见性 | 防失控 |
|---|---|---|---|---|
| GitHub Copilot 编码智能体 | Actions runner，单个会话约 1 小时 | 不定时；PR 评论、“Fix with Copilot” 触发新一轮 | PR 里实时日志、智能体面板（进度、token、时长），可以停 | 每个会话算 premium request；CI 默认要人批准才跑 |
| Cursor Cloud Agents | 每个智能体一台 VM；智能体循环放在 Temporal 里，和 VM 的生命周期分开 | Automations（cron / 事件）、`followup` 接口 | 状态接口；只在结束或出错时发带签名的 webhook | 首次使用必须设花费上限 |
| Devin | 云端机器；没有活动时会话**休眠而不是结束** | PR 评论、CI 失败时自动唤醒；定时会话（cron 或一次性，一次性执行后自动停用、保留历史） | 进度时间线，每一步的命令可以展开；人可以接管终端 | 每个会话、每人、每个组织的 ACU 上限；暂停状态带原因（空闲 / 人停的 / 超额） |
| Google Jules | 每个任务一台短命 VM，环境可以做快照 | 定时任务 | `activities` 查询、通知 | 每 24 小时的任务数、并发数 |
| OpenHands | tmux 终端：命令到“无变化超时”先把已有输出交回模型，命令接着跑 | 没查到 | 事件写盘、轮询、webhook | 最多迭代次数、预算、卡死检测 |

一个教训（Cursor 论坛员工回复，不是正式文档）：VM 重置后，进程和没保存的输出都会丢；长任务要自己做检查点，不能指望后台进程一直活着。

### 4.2 持久化执行框架

| 框架 | 借鉴点 |
|---|---|
| Temporal | 定时器等待几小时到几天也不占 worker，崩溃后靠重放恢复；Activity 的超时分三层（单次尝试 / 含重试的总时长 / 心跳）；默认重试不限次数，必须自己设上限；循环太长要换新的执行记录（写明） |
| LangGraph | 每一步存检查点；后台运行时 worker 写心跳，服务关闭可以重新入队、从最后一个检查点接着跑；同一个线程上来了新输入，可选排队 / 拒绝 / 打断 / 回滚；文档专门提醒：不用的 cron 要删，不然一直花钱（写明） |
| Cloudflare Agents | `schedule(延时 / 时间 / cron)` 存在 SQLite 里，重启后还在；多个计划只把最近到期的那个设成闹钟；回调可能重跑，必须幂等（写明） |
| AWS AgentCore | 会话最长 8 小时、空闲 15 分钟结束；异步任务用“忙碌”状态挡住空闲超时。文档里有个坑：每次心跳都刷新更新时间，结果空闲超时永远不触发（写明）→ 心跳要反映真实进展（推断） |
| Inngest / Restate | sleep、等事件时不占并发名额；按 key 的并发、节流、只跑一个；取消在步骤之间生效，已经发生的副作用不回滚；外部写操作要带幂等键（写明） |

### 4.3 共识

1. **长命令由平台托管**：有编号、状态、日志文件、退出码。模型只负责开、查、停，不负责“一直开着进程等”。
2. **回来看以事件为主、定时为辅**：作业结束、CI 结束时唤醒，另有一次性或周期的定时；定时器和计划存数据库，重启不丢。
3. **唤醒就是一条合成消息**：写明是谁、因为什么发的；**不能当成人的指令或审批**。
4. **至少执行一次，加幂等**：重启后补发是正常的，所以有副作用的步骤要带幂等键；状态不明就记“结果未知”，不自动重做。
5. **多层护栏**：最多轮数、截止时间、预算、连续失败或没有进展的次数；超了就暂停，交给人决定，不悄悄续跑。
6. **超时分层**：单条命令、单个回合、整个作业、整条循环，各有各的时限；心跳只认真实进展。
7. **看得见、停得掉**：运行中、已完成两个列表；实时日志末尾；温和停止（给机会收尾）和强制停止分开。
8. **同一会话串行**：同一个会话同时只跑一个回合；定时到了而上一轮还没结束，默认不叠加。

## 5. 设计

### 5.1 三个新东西

| 名字 | 是什么 | 生命周期 |
|---|---|---|
| **作业（job）** | 管理器在会话的工作目录里替它跑的一条长命令，比如构建、测试、训练、`gh run watch` | 等待 → 运行中 → 成功 / 失败 / 超时 / 已停止 / 结果未知（管理器重启时正在跑的） |
| **预约（timer）** | “到某个时间，对这个会话说某句话” | 待执行 → 已发出 / 已取消 / 已跳过（会话归档了、循环停了） |
| **循环（chain）** | 由作业结束或预约触发、连续自动开的一串回合，共用一套护栏 | 进行中 → 结束 / 暂停待人决定（护栏到了） |

作业和预约都属于某个会话，存进管理器的 SQLite（新表 `jobs`、`timers`）。表结构要点：

- `jobs`：会话、发起者（人 / 外层智能体 / 会话里的模型，带调用方编号）、命令（脱敏后存）、状态、进程号与进程组、开始和结束时间、退出码、时限、日志文件与已写字节数、`last_output_at`（最后一次真有输出的时间）、结束后要不要接着做（`follow_up`）以及接着做时附的话。
- `timers`：会话、发起者、到点时间、要发的话、状态、发出后对应的回合、所属循环、幂等键（`timer:<编号>`）。
- `chains`：会话、开始时间、已经跑了几轮、连续失败几次、截止时间、状态。

### 5.2 一个统一的调度协程

把现在的 `_resume_loop`（只管额度恢复）扩成一个调度协程，统一看三类“到点的事”：平台额度恢复、预约到点、作业超时。

- 做法和 Cloudflare 一样：只睡到最近的那个到点时间；新加预约时用 `asyncio.Event` 提前叫醒它。
- 管理器启动时，先补处理停机期间已经到点的预约：**补发一次**，消息里写明“原定 X 点，晚了 Y 分钟”。这和 Claude 的 cron“错过不补”不同：我们的预约是“回来看结果”，晚了也要看。

### 5.3 作业怎么跑

- **位置和权限**：作业在会话自己的工作目录里，以和官方程序相同的普通用户跑。环境变量只给白名单，和驱动一样，不带管理器自己的令牌。
- **进程**：`start_new_session` 建独立进程组；停止时先发 TERM，过 10 秒还没停再发 KILL，整个进程组一起停。
- **日志**：stdout 和 stderr 合在一起写进数据卷上的文件。超过上限（默认 20 MB）后只留开头 1 MB 和最近的内容；读取时先脱敏，和预览文件用同一套规则（`workfiles.redact_preview`）。
- **心跳只认真实进展**：`last_output_at` 只在日志真的变长时更新。页面上显示“已经 N 分钟没有输出”，但不会因为这个自动停掉作业，到作业时限才停。这是吸取 AgentCore 的教训。
- **重启**：管理器所在的容器一重启，作业进程就没了。启动时把所有“运行中”的作业记为**结果未知**，按它的 `follow_up` 设置告诉会话“作业因管理器重启中断，不知道做到哪一步”。不假装它还在跑，这是吸取 Cursor 的教训。
- **重的作业不放在管理器上**：管理器容器和官方程序共用 CPU 和内存。要大算力的，建议放到工作台的运行环境（运行服务器）或远端 CI 上，作业只负责“等它、看它”。

### 5.4 作业结束、预约到点之后

1. 管理器给这个会话排一个系统回合（`source = {kind: "job" | "timer", id, chain}`），用现在补发“继续”的同一套代码，带幂等键。
2. 消息模板（写明不是人发的）：
   > 【管理器自动发出，不是人发的消息，不代表任何人的批准】你在 11:20 开的后台作业「跑完整测试」已结束：退出码 1，用时 2 小时 14 分。日志末尾 40 行：……（完整日志用 `llm-task job log <编号>` 看）。你当时留的话：“失败就看哪个用例挂了，修完再跑一遍”。
3. **合并，不叠加**：这个会话已经有一个排着的系统回合时，新的结束通知合并进那一条，不再另排。会话正在跑回合时，排在它后面，同一个会话仍然一次只跑一个回合。
4. **额度用完时顺延**：平台因为额度暂停着，就等恢复后再发，复用现有的暂停逻辑。

### 5.5 谁来发起

| 发起方 | 怎么发起 | 第几期 |
|---|---|---|
| 人 | 会话页面的“后台任务”面板：预约一条消息、停作业、取消预约 | 2、3 |
| 外层智能体（OpenClaw） | 工作台工具：`llm_bridge_send` 加 `deliver_at`（定时发），另加查看后台任务、停作业、取消预约的工具 | 2、3 |
| 会话里的模型（Claude / Codex / CodeBuddy） | 管理器在会话环境里放一个小命令 `llm-task`（见下），模型用 shell 调它：`llm-task job start --name 跑测试 -- make test`、`llm-task job log <编号>`、`llm-task at +3h "去看 CI 结果"` | 4 |

会话里的模型为什么先用小命令、不用 MCP 工具：

- 三家官方程序都能跑 shell，而且只有“可以执行命令”档位的环境才开作业，所以这个命令对三家一样好用；
- 挂 MCP 工具（Claude 的 `--mcp-config`、Codex 的 `mcp_servers` 配置）要分别在锁定版本上核验。

小命令叫 `llm-task`，不叫 `bridge`：Linux 的 iproute2 自带一个 `bridge` 命令，会撞名。

小命令经本机地址（`BRIDGE_SESSION_API_URL`，默认 `http://127.0.0.1:8787`）找管理器，带一个**只对这个会话、这一回合有效**的令牌。令牌在回合开始时写进会话工作目录的 `.llm-task/session.json`，回合结束就删掉、作废。
- 不放进环境变量：Codex 的 app-server 是常驻进程，命令继承的是它启动时的环境，没法每回合换。写成文件，三家用同一个办法。
- `.llm-task/` 加进仓库的 `.git/info/exclude`，不会被提交。

MCP 工具作为以后的选项。

### 5.6 循环与护栏

由作业结束或预约触发的自动回合算同一条“循环”。下面这些上限，管理员可以在“运行设置”里改：

| 护栏 | 建议默认 |
|---|---|
| 一条循环最多几轮 | 20 |
| 一条循环最长多久 | 72 小时 |
| 连续几轮失败（回合失败或作业失败）就暂停 | 3 |
| 每个会话每天最多几个自动回合 | 48 |
| 每个会话同时运行的作业 | **不限**（人类 2026-11-18 决定）；整个管理器也默认不限。两项都可以在“运行设置”里设上限，0 表示不限 |
| 单个作业最长 | 24 小时（可设 1–72 小时） |
| 每个会话待执行的预约 | 5 个；最早 1 分钟后，最远 7 天 |

到了上限：循环转为“暂停，等人决定”，不再自动开回合。管理器在会话页面标红，并按 5.8 通知调用方，由人或外层智能体决定继续还是停。

另外，额度用完自动继续的那套上限（`auto_resume_max`）照旧单独算。

### 5.7 回合进行中看得见（第 1 期）

`llm_turn_get` 和会话页面增加一个 `activity`：

| 字段 | 内容 |
|---|---|
| `last_event_at` / `quiet_seconds` | 最后一次有动静的时间、已经安静了多少秒 |
| `current` | 正在跑的命令或工具：内容、开始时间、已经跑了多久 |
| `output_tail` | Codex 有流式输出，留最后 40 行（脱敏）；Claude / CodeBuddy 没有流式的命令输出，跑完才有 |
| `background` | 官方程序报出的后台任务：说明、状态、开始时间 |

驱动改动：

- Codex 接上 `item/started`：命令一开始就记一步。再接上 `outputDelta`：只在内存里留输出末尾，不逐条写进库。
- Claude / CodeBuddy 接上 `task_*` 事件。字段先按锁定版本的类型定义核对。

工具说明里写清楚：状态是 `running`、有正在跑的命令、最近有动静，就是正常在等，不要取消。

### 5.8 结果送到调用方

- **外层智能体**：现在 `notify=true` 只盯单个回合（`watches.py`）。扩成“盯这个会话的自动回合”：通过工作台开的作业或预约，默认在它引出的自动回合结束后叫醒这个实例，提示词里只写会话、回合编号和状态，内容让它自己取。这和现在的做法一致。
- **人**：会话页面的“后台任务”面板（5.9）；循环暂停时，加一条工作台通知。
- **对接方式**：工作台不需要管理器主动推送，沿用现在“隔十几秒问一次状态”的轮询。管理器加一个按调用方列出“新结束的自动回合”的接口，工作台据此找到要叫醒的实例。

### 5.9 页面

- **会话页面的“后台任务”面板**（样子参考 Claude App 的后台任务）：
  - **运行中**：作业名、已运行时长、多久没有输出、停止按钮；
  - **预约**：什么时候、发什么，可以取消；
  - **已完成**：结果、退出码、日志末尾，可以看完整日志或下载；
  - 循环暂停时顶部有一行红色提示，带“继续”和“停止”。
- 会话里的回合列表上，自动回合标明“作业结束后自动接着做”或“预约的回来”。
- **“运行设置”加一组“后台任务”**：总开关、5.6 的上限。
- **开发环境的弹窗加两项**：允许后台作业（只在“可以执行命令”档位可选）；这个环境的单回合时限（不填就用管理器的设置）。

### 5.10 停得掉

- 停作业：先 TERM，再 KILL（5.3）；停掉后**不**自动接着做，除非停的人勾选“停掉后也告诉会话”。
- 取消预约、停循环：立即生效，已经排上的系统回合一起取消。
- 归档会话：停掉它所有的作业、取消所有预约。

### 5.11 为什么暂时不做“常驻官方程序”

让每个会话的 Claude 进程常驻、标准输入不关，就能用上官方自己的后台任务和完成后自动开新一轮（第 3 节），看起来省事。但是：

1. **只有 Claude 有这种模式**，Codex 和 CodeBuddy 都没有，三家会做成三套；
2. **每个会话一直占着一个进程和内存**，管理器重启时全部断掉，而且 `--resume` 不会重启后台命令；
3. **官方的上限仍在**（后台命令最长 2 小时），跨小时的作业还是要另想办法；
4. 我们的额度暂停、并发名额、回合队列都按“一回合一个进程”设计，改动面最大。

管理器自己托管作业和预约，三家通用，状态都在我们手里。等第 4 期做完、真有需要，再评估常驻模式。

在那之前怎么处理官方自带的后台：

- **第 1 期**：先把它报出的后台任务显示出来，不关掉。
- **第 3 期**：托管作业上线后，给 Claude、CodeBuddy 设关闭后台的环境变量（`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`、`CODEBUDDY_CODE_DISABLE_BACKGROUND_TASKS=1`），并在说明里告诉模型“要等很久就用 `llm-task job`”。避免它把东西放到后台、回答结束后被悄悄停掉。

## 8. 安全

- **只在“可以执行命令”档位的开发环境允许作业。** 否则“只读”和“只能改文件”的环境，会被作业绕过去跑命令。Codex 的作业不受 Codex 自己的沙箱约束，所以同样只在管理员明确打开的环境里允许。
- 作业的环境变量只给白名单，不带管理器的令牌和回合令牌；日志和预览一样先脱敏；日志有大小上限；作业的工作目录限定在会话目录。
  - 作业和管理器是同一个用户，本来能读 `/proc/<管理器>/environ`。所以容器的 1 号进程（`bridge/pid1.py`）和管理器都设成不可转储（`PR_SET_DUMPABLE=0`），同一个用户的进程读不到它们的环境变量和内存（12.5）。
  - 官方程序（Claude、CodeBuddy、Codex 的 app-server）只拿到白名单里的环境变量（`bridge/drivers/base.py` 的 `PROGRAM_ENV_PASS`），不带管理器的 `BRIDGE_*`。它们没有设成不可转储，而且它们跑的命令会继承它们的环境，所以这一条必须靠白名单。原来 Codex 拿的是完整的环境，合并后由集成会话发现，在 T-0293 修了（12.6）。
  - 每个会话的作业有自己的 HOME，用 `bash -c` 启动（不是登录 shell），一个会话写进启动文件、凭据文件的东西不会被别的会话的作业用上。
- 会话工作目录里的东西会话能改，仓库里也能提交符号链接。管理器在工作目录里写令牌、改 `.git/info/exclude` 时一路不跟随符号链接（`O_NOFOLLOW`），不会被引着去覆盖别的文件（12.5）。
- **自动回合的消息写明“不是人发的、不代表批准”**。工作台和外层智能体也不能把它当作人的指令（AGENTS.md 第 8 节的审批规则不变）。
- 会话里的 `llm-task` 命令用回合令牌：只对这个会话有效，回合结束就作废，有调用频率上限，不能动别的会话。只在能开作业的会话（“可以执行命令”档位）里写令牌；页面的文件浏览、回合的产出文件都不包括 `.llm-task`。
- `llm-task` 在镜像里装在 root 拥有的 `/usr/local/bin`。数据目录下的 `bin` 只在开发、测试时用，而且放在 PATH 的最后：作业能写这个目录，放在前面就能用同名程序顶替官方程序。
- **已知的限制**：作业、“可以执行命令”档位的官方程序和管理器是同一个用户，又没有操作系统级沙箱（页面上本来就有这条提醒）。它们能读写数据卷：
  - 别的会话的记录（`bridge.sqlite3`）、工作目录，以及回合进行中别的会话的令牌文件；
  - 各平台的登录凭据。

  这次新增的是：Codex 在这一档的作业不在它自己的沙箱里；外层智能体可以不经模型直接开作业。所以只给信得过的调用方、只在需要的开发环境打开“可以执行命令”档位。
  要真正隔开，需要作业用单独的用户或单独的容器运行（以后再做，见第 12.5 节）。管理令牌这一项挡住了长期运行的进程（上面第一条）；例外是 Docker 的健康检查：它每 30 秒起一次、几十毫秒就结束，Docker 用容器的环境变量启动它，所以它带着管理令牌，同一个用户的作业碰巧在它运行时能读到（12.7）。这和“能读写数据卷”是同一类限制。
- 所有开、停、预约、继续循环都记进管理器的事件和工作台的审计。
- **需要人类批准的规则变化**：
  - 外层智能体通过工作台开作业、预约、继续循环，按 AGENTS.md 第 8 节，是新的“直接执行、不审批”的工具，要写进例外九；
  - 会话里的模型自己开作业、自己预约，等于允许它在没人看着时连续消耗额度（有 5.6 的上限）。

  这两件人类已在 2026-11-18 决定（第 10 节）。

## 10. 人类的决定（2026-11-18）

人类在对话中答复：
1. **会话里的模型可以自己预约回来、自己开作业**（第 4 期做）。
2. **外层智能体的新工具按“直接执行、不审批”处理**：写进 `docs/AGENTS.md` 第 8 节，作为例外十。
3. 然后**按优化后的方案全面落实代码**，四期一起做。

4. 起草时建议“每个会话同时最多 3 个作业”，人类答复：“这一条要改一下，不做上限限制”。所以每个会话、整个管理器同时运行的作业数都**默认不限**，管理员可以在“运行设置”里设上限。

其余没有单独答复的，按方案的推荐执行，都可以在“运行设置”里调整：
- 方向：等待不占回合，由管理器托管作业和预约；暂不做常驻官方程序（5.11）。

- 作业只在“可以执行命令”档位的开发环境允许（第 8 节）。

## 11. 没有核实的

- 所有关于官方程序的结论，都来自程序文件、源码和官方文档，**没有在真实账号上跑过**。重点要实测的：
  - Claude `-p` 回答结束后等后台命令的实际行为和时限；
  - `task_*` 事件的字段；
  - Codex 后台进程在 app-server 里跨回合存活。
- 我在 2026-11-18 的对话里根据程序文本说过“Claude 回答完 5 秒后就杀掉后台 shell”，**以官方文档为准，这个说法不对**：它会先等后台命令（有时限），进程退出时才全部杀掉。程序里的“5 秒宽限”是哪种情况下的收尾，没有核实。
- 业内资料里有几个站点本会话打不开（docs.github.com、openai.com、temporal.io、aws、cloudflare），用的是搜索引擎对官方页面的摘录；采用某个具体数字之前再核对一遍。
- CodeBuddy 回答结束时怎样处理后台任务，没有核实。

### 12.2 和起草时不一样的地方

- **名字**：起草时写的 `llm_send` 加 `deliver_at`、`llm_session_tasks`、`llm_chain_resume` / `_stop`，做成了独立的 `llm_timer_create`、`llm_tasks`、`llm_chain_control`（第 6 节）。定时发一条消息和“预约回来”是同一件事，不再给 `llm_send` 加参数。
- **开关**：起草时写“`jobs_enabled` 默认关”和开发环境的 `allow_jobs`。实际是：作业本来就只在管理员设为“可以执行命令”档位的开发环境里能开（这一档是管理员明确选的），`jobs_enabled` 默认开、作为总开关；不再给环境单独加一项，免得两个开关意思重叠。
- **同时运行的作业**：按人类的决定默认不限（第 10 节第 4 条）。
- **日志截断**：写满 20 MB 后不再写文件，只在内存里留最近 256 KB，作业结束时补到文件末尾并写明中间省略了多少。读取时脱敏（`bridge.redact`）。命令按原样存（要用它运行），给人和智能体看时脱敏。
- **单回合时限**：开发环境的“单回合时限”范围 30 秒到 6 小时，不填用管理器的设置。
- **会话页面上的回合**：自动回合的消息开头带固定标记，页面据此标明“MCP 管理器（自动接着做）”。

### 12.3 存储升级

管理器的 SQLite 在启动时用 `CREATE TABLE IF NOT EXISTS` 加三张新表（`jobs`、`timers`、`chains`）和它们的索引，不改、不删旧表的列和数据。升级后第一次启动自动建表；退回旧版本的管理器时，旧版本不认识这三张表，直接忽略，原有会话、回合不受影响（只是作业和预约不再执行）。作业日志写在数据目录的 `jobs/` 下，作业结束 7 天后删掉日志文件（记录留着）；`llm-task` 写在数据目录的 `bin/` 下，每次启动重写。工作台没有数据表变化。

### 12.4 验证到哪一步（第一版）

- 管理器单元测试：活动视图、环境单独时限、预约（最早 1 分钟、个数上限、补发）、合并、轮数 / 时长 / 每天 / 连续失败四种护栏、作业结束后接着做、只在“可以执行命令”档位开作业、停止、归档、重启后结果未知、回合令牌只对自己的会话和这一回合有效、`llm-task` 命令、进程组与孤儿进程、驱动的事件与说明。

### 12.6 合并后补的一处（T-0293）

集成会话合并 PR #255 后指出：`bridge/drivers/codex.py` 启动 `codex app-server` 时传的是完整的 `os.environ`，里面有 `BRIDGE_ADMIN_TOKEN`。这段代码在本方案之前就有。

- 影响：app-server 没有设成不可转储，同一个用户的作业能读它的 `/proc/<pid>/environ`。更直接的是，Codex 在“可以执行命令”档位跑的命令继承 app-server 的环境，本身就带着管理令牌。12.5 的冒烟检查只查了 1 号进程和 uvicorn，app-server 要用到 Codex 才启动，所以没查到。
- 改法：三家官方程序共用一份环境变量白名单（`PROGRAM_ENV_PASS`，原来是 `cli_stream.py` 的 `_ENV_PASS`）；Codex 另外只加 `CODEX_HOME` 和 `HOME`。
- 测试：`test_official_programs_never_get_the_bridge_settings` 记下 Codex 和 Claude 实际收到的环境变量，确认没有 `BRIDGE_*`，在旧代码上失败。冒烟检查先列一次 Codex 的模型（启动真实的 app-server），再查容器里每个进程的环境变量都没有非空的管理令牌。



### 12.7 Docker 健康检查带着管理令牌（T-0297）

#257 合并后 main 上 ci-llm-bridge 的冒烟检查失败一次：12.6 加的“容器里每个进程的环境变量都没有非空的管理令牌”这一项，扫到了 Docker 的健康检查进程。

- 原因：Docker 用容器的环境变量（`Config.Env`，里面有 `BRIDGE_ADMIN_TOKEN`）启动健康检查；镜像里改不了这一点。健康检查每 30 秒起一次、几十毫秒就结束，所以这项检查碰巧赶上它运行时才失败，同一个作业里两分钟前跑的同一项是通过的。
- 影响：同一个用户的作业如果一直盯着 `/proc`，能在健康检查运行的那一瞬间读到管理令牌。它和第 8 节“作业和管理器是同一个用户，能读写数据卷（包括所有会话的记录）”是同一类已知限制，没有给作业新的能力；要彻底隔开，仍是作业用单独的用户或单独的容器运行（12.5），或者管理令牌不放在容器的环境变量里（需要改部署方式，另行决定）。
- 改法：
  - Dockerfile 的 `HEALTHCHECK` 改用 exec 形式（`["python", "-I", "-c", …]`），不经过 `/bin/sh`，少一个带着令牌的进程；
  - 冒烟检查按这条命令行认出健康检查、不算在内，其余进程（1 号进程、管理器、官方程序）照查。旧的 `/bin/sh -c` 形式不会被放过。
