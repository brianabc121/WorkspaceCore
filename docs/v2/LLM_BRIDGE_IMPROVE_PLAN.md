# 大模型客户端（MCP 管理器）改进方案

> 状态：**已批准，实施中**（人类 2026-11-15 要求按这份文档全面落实；第 7 节的 5 件事没有单独答复，按文中的推荐做）。起草：claude，T-0246。
> 实施记录见第 9 节。
> 范围：只看三条链路的深度——① OpenClaw 智能体经工具调用；② 管理员事后查看、回溯会话；③ 人在聊天页日常使用。
> 不讨论部署、登录方式、新增平台。
> 依据：逐条读了现在 main 上的代码（文中给出位置），并查了业内的做法（第 6 节列出来源和哪些没能核实）。

## 1. 结论先说

现在的设计能用，三条链路各有一批“小毛病”，但它们大多出自同一个根：**回合的状态、过程和出处只在管理器里存了一份很薄的记录，三条链路各自拿它的一小部分、各自轮询。** 所以智能体不知道回合什么时候完、为什么排队；管理员查不到是谁因为什么事发起的、花了多少；人看到的回答是一整块蹦出来的。

建议分三层做，顺序不能反：

| 层 | 做什么 | 为什么先后这样排 |
|---|---|---|
| 第 0 层：修正 | 5 处和已批准规则对不上的地方、2 处会误导智能体的地方（第 2 节） | 是缺陷，不是优化；不需要新的设计决定 |
| 第 1 层：底座 | 统一的回合状态、带序号的事件流、出处、工作台里的会话索引（第 3 节） | 三条链路后面的改进都靠它；不先做就会各做各的、再返工 |
| 第 2 层：三条链路 | 各自的改进（第 4 节） | 建在底座上，彼此可以分开做、分开验收 |

有 5 件事要你先定（第 7 节），其中“开发会话里让人当场批准命令”牵涉例外九的边界，我没有擅自设计成放宽权限的样子。

## 3. 第 1 层：底座（三条链路共用）

### 3.1 一个统一的回合状态

现在回合的状态是 `queued / running / completed / failed / interrupted / unknown / cancelled`，但**“为什么在等”和“接下来会怎样”没有表达出来**：等平台名额、等额度恢复，看到的都只是 `queued`；被插入的消息打断的回合不指向接替它的那一回合；额度中断后续跑的是另一条回合，要自己顺着找。

建议回合对外只有一种样子，三条链路都读它：

| 字段 | 含义 |
|---|---|
| `status` | 不变 |
| `waiting` | 排队时：`{reason: 会话里前面有消息 / 等平台名额 / 平台因额度暂停, position, until}` |
| `next_turn_id` | 被打断或续跑时，指向接着做的那一回合；一路跟到底就是最终结果 |
| `failure` | 失败时：`kind`、说明、**能不能重试**、**多久以后重试** |
| `timing` | 排队、开始、结束的时间和用时 |
| `usage` | 这一回合的 token 数（官方程序报的，标明是它报的数） |
| `outputs` | 这一回合产生的文件、图片的编号（不是路径字符串） |

业内的任务协议都是这个思路：把“在等人或在等条件”和“失败”分开，是一种可以恢复的中间状态（MCP 的 Tasks 扩展、A2A 的任务状态都是这样分的）。我们的“额度暂停”正好属于这一类。

### 3.2 一条带序号的事件流

管理器里已经有 `events` 表，每条有递增的编号，网页用它做长轮询。建议把它正式当成**唯一的过程记录**，并补两样：

1. **更细的事件**：现在 Claude / CodeBuddy 是“一整段回答一条事件”，Codex 是“一个条目完成一条事件”，所以回答是整块出现的。官方程序本身能给出逐字的增量（Claude Code 的无界面模式有输出增量的开关，Codex 的本机服务有条目增量的通知）——**这两点要在锁定版本上核验后才做**，核验不了就保持现状并写明。
2. **一条推送通道**：网页用“服务器推送事件”（SSE）接事件流，断线后带着上次的编号接着读。轮询保留作兜底。

好处是三条链路共用：人看到逐字输出，断线、刷新、换设备都能接上；管理员回放的就是同一份；智能体等待回合也用同一个编号。业内的共识也是“续传靠服务端存下来的事件和编号，不靠连接本身”。

### 3.3 出处：这一回合是谁、因为什么发起的

现在只记了“谁”（实例或人的名字）。**查不到它是哪个任务、哪个项目、哪次执行、哪条 IM 消息引起的**；反过来从智能体的执行记录也跳不到会话（新建会话的执行记录里甚至没有会话编号）。

建议由**工作台**（不是智能体自己填）在每次调用时带上出处：实例、这次执行记录的编号、它当时在做的任务和项目。管理器存下来；工作台的执行记录里反过来记会话和回合的编号。这样两边都能点过去。

### 3.4 工作台里的一张会话索引

对话内容继续只存在管理器里（不改这个原则）。但工作台现在**完全没有会话的任何记录**，所以做不了跨管理器的列表、按人或按智能体筛选、用量汇总。

建议工作台加一张很薄的索引表：会话编号、哪个管理器、平台、谁建的、出处、标题、最后活动时间、回合数、失败和中断的数量、累计 token。**不含对话内容。** 由工作台的后台任务定期向每个管理器取“从上次编号以后变了什么”来更新（需要迁移）。

这张表同时解决三件事：管理员的跨管理器查找和筛选；用量按人、按智能体、按天汇总；回合结束时由工作台去唤醒智能体（第 4.1 节）。

## 4. 第 2 层：三条链路各自的改进

### 4.1 智能体调用

**现在最大的三个问题：**

1. **只能轮询。** 发送最多等 50 秒，之后要反复取回合，每次又最多等 50 秒，还都算进每分钟 120 次的限额。一个跑半小时的开发回合要轮询几十次。
2. **拿到的东西要么太多、要么太少。** 回合结果从不截断（超过 4 MB 直接报错）；会话记录从最早的开始翻页、没有总数；另一方面，过程（跑了什么命令、改了什么文件）、产出的文件都拿不到，文件只是一串路径。
3. **出错时不知道该不该重试。** 没登录、账号不对、管理器连不上、熔断、结果未知，全都变成同一个 `EXTERNAL_UNAVAILABLE`，没有“能不能重试”“多久以后”。

**建议：**

| # | 做法 | 业内对应的做法 |
|---|---|---|
| A1 | **回合结束时主动唤醒智能体**：发送时可以选“结束后叫我”。回合到了结束、失败或中断状态，工作台经现有的唤醒机制叫醒这个实例，带上回合编号和一句结果摘要。至少送达一次，按回合编号去重；轮询保留作兜底 | A2A 的推送通知、OpenAI 后台模式的回调，都是“完成后通知、再按编号取结果” |
| A2 | **结果默认给精简的**：取回合时默认只给最终回答（超过约 2 万字截断，并说明怎么取后面的），可选 `detail=steps` 看过程、`detail=full` 看全部；读会话默认给最新的一页并带总数 | Anthropic 的工具设计建议：默认简洁、可选详细、分页、截断时告诉下一步怎么取 |
| A3 | **错误分开说**：没登录、额度暂停（带恢复时间）、发送限额（带重置时间）、管理器连不上（可重试）、结果未知（去查这个 `request_id` 的回合）各有各的代码，并带“能不能重试”“多久以后” | Claude Code 的重试事件带错误分类和等待时间；同一篇工具设计建议要求错误信息可操作 |
| A4 | **文件进出按编号**：产出的文件给编号，智能体可以按编号取（限大小），或者让工作台把它放进自己的运行环境、知识库；发送时可以带上知识库或运行环境里的文件。不经对话传文件内容 | “大结果存成制品、只回传引用” |
| A5 | **少一次往返**：发送时可以不给会话，由工具按平台和模型新建一个再发（最常见的用法一步完成） | 工具设计建议：合并常用的连续调用 |
| A6 | **状态查询只给智能体用得上的**：去掉套餐类型、账号标识、登录方式；并按这个实例被允许的平台过滤 | 最小够用 |

暂不建议做：让智能体用“多模型同问”（用得少，等有需求再加）。

### 4.2 管理员查看、回溯

**现在最大的三个问题：**

1. **找不到。** 搜索只匹配标题；不能按“哪个智能体”“哪个人”“哪段时间”“有没有失败”筛选；聊天页最多显示 100 个会话、没有“加载更多”；每个管理器各看各的。
2. **看不全。** 回合没有开始、结束时间和用时；没有 token 数；命令的输出被丢掉了（存了但不给页面）；开发会话没有改动对比，而且**一归档工作目录就删了**，证据没了；修改排队中的消息会覆盖原文，也不记是谁改的。
3. **对不上。** 查不到因果（见 3.3）；审计里智能体的写操作不进审计日志（只有执行记录），读别人的会话、下载附件也不记；审计条目挂在“管理器”上而不是“会话”上，没有中文名称，点不过去。

**建议：**

| # | 做法 | 业内对应的做法 |
|---|---|---|
| B1 | **“会话记录”页**（在管理页里）：跨管理器的列表，按发起人（某个智能体 / 某个人 / 官方程序里已有）、平台、用法、时间段、有没有失败或中断筛选；全文搜索提问和回答（管理器里用 SQLite 自带的全文索引）；可以翻页 | 可观测工具都按“会话 → 用户”归组，并能按用户、时间、状态筛选 |
| B2 | **回合详情补齐**：开始、结束、用时；实际用的模型；token 数；命令和它的输出；改了哪些文件 | — |
| B3 | **开发回合留下改动对比**：回合结束时把工作目录的改动存成一份补丁，归档后还在；页面上按文件看对比 | Claude Code、Codex 的界面都是“文件列表 + 对比” |
| B4 | **出处两头能点**：会话头上显示“由智能体 X 在任务 Y 的第 N 次执行里发起”，能点到任务和执行记录；执行记录里能点到会话的那一回合。通知里的链接直接到那一回合 | 用“父调用编号”把子任务挂回父任务 |
| B5 | **用量页**：按天、按人、按智能体、按平台汇总 token 数和回合数（失败和中断的也算）。写明是官方程序报的数，不是账单；CodeBuddy 的积分拿不到 | 按用户、按智能体归集用量，并标明是估算 |
| B6 | **审计补齐**：智能体的写操作也进审计日志；读别人的会话、下载附件记一条；条目挂在会话上，有中文名称，能点到会话；修改排队消息时保留原文和修改人 | 企业版聊天产品都把“谁做了什么”的活动记录和“说了什么”的内容分开存、分开授权 |
| B7 | **通知**：智能体的回合失败、平台因额度暂停和恢复、被限额拒绝、智能体接手人的会话。同类的合并 | — |
| B8 | **保留期和导出**：对话内容可以设保留多少天（到期只删内容，活动记录和用量留着）；单个会话可以导出成 Markdown | 合规接口的共同做法：内容到期可删，活动记录不随之消失 |

暂不建议做：给审计日志加防篡改的哈希链、给会话打分和复核队列——是多人团队和合规场景的做法，个人工作台现在用不上。

### 4.3 人日常聊天

**现在最大的四个问题：**

1. **回答是整块出现的。** 一段话的回答要等全部写完才一次显示；等的时候只有“正在回答…”几个字，没有用时，也不显示它在做什么（管理器算了进度，页面没用）。
2. **只显示纯文字。** 标题、列表、表格、链接都不渲染，只有三个反引号的代码块有格式；代码块和回答都没有复制按钮。
3. **发错了、失败了没法补救。** 不能重试失败的回合（只能重新打一遍）、不能重新生成、不能改上一条再发。
4. **草稿和状态容易丢、看不到。** 换个会话或刷新，草稿和已选的附件就没了；额度暂停时对话里只写“排队中…”不说原因；长回合跑完了，人不在这个页面就不知道。

**建议：**

| # | 做法 | 说明 |
|---|---|---|
| C1 | **逐字输出 + 断线接续**（底座 3.2）；等待时显示已用时间和“正在做什么”那一行 | 这是体感差别最大的一项 |
| C2 | **Markdown 渲染**：标题、列表、表格、代码高亮；代码块和整条回答有复制按钮。不渲染原始 HTML；链接在新窗口打开 | 原方案出于安全把链接也关了，建议放开链接、继续禁止 HTML |
| C3 | **重试 / 重新生成**：失败、未知、被停止的回合旁边有“重试”，一键用原文再发；最后一条回答可以“重新生成” | 不需要平台支持分叉，先做 |
| C4 | **改上一条再发**：需要平台支持“从某处分叉会话”。官方程序有这个能力，但要在锁定版本上核验；核验不了就不做 | 见第 7 节 |
| C5 | **草稿按会话保存**在浏览器里，刷新、切换都在；已上传没发出的附件重新进会话时还列着 | — |
| C6 | **对话里说清楚在等什么**：等平台名额排第几、平台因额度暂停到几点（底座 3.1 的 `waiting`） | — |
| C7 | **跑完叫我**：人不在这个会话时，回合结束发一条工作台通知，标签页标题上也有标记 | Claude Code 的手机端也是“完成或需要人时提醒” |
| C8 | **每回合显示用量**：这一回合的 token 数、实际用的模型；会话信息里显示累计 | 数据已经存了，只是没给页面 |
| C9 | **会话管理**：全文搜索（和 B1 共用）、“加载更多”、置顶、取消归档、导出；标题在发出第一条时就定下来，不等第一回合结束 | — |
| C10 | **每条消息可以换模型和推理强度** | Claude / CodeBuddy 每回合本来就是一次新的调用，可以换；Codex 要核验 |
| C11 | **键盘**：Esc 停止、输入框空时按 ↑ 修改上一条排队中的消息 | — |

**单独的一项（C12）：开发会话里当场批准。** 现在开发会话的权限完全由环境的档位事先定死，官方程序中途想问人、想请求许可时，一律自动拒绝。业内的做法是弹一张卡片：允许一次、总是允许、拒绝并说明。这一项牵涉例外九，放在第 7 节由你决定。

## 5. 分期

每一期都能单独合并、单独验收；后一期不挡前一期上线。

| 期 | 内容 | 涉及 |
|---|---|---|

## 6. 业内做法的来源，以及哪些没能核实

## 7. 需要你决定的 5 件事

| # | 问题 | 我的建议 |
|---|---|---|
| 1 | 第 0 层的修正是否不等整份方案、先做 | 先做。0-1、0-2、0-3 是权限和密钥保护比规则写的宽 |
| 2 | 0-3 的密钥检查命中时：**拒绝发送**，还是**替换成占位再发** | 拒绝并说明。和发邮件、写 Issue 时的做法一致，也不会让模型拿到残缺的内容 |
| 3 | 对话内容的保留期（B8）：默认一直保留，还是默认多少天 | 默认一直保留，页面上可以改；到期只删内容，活动记录和用量留着 |
| 4 | 开发会话里当场批准（C12）要不要做 | 要做的话只能**收紧**：在管理员定好的环境档位之内，让人逐次确认；不能借它放宽档位、不能让智能体发起的会话等人批准（没人时照旧自动拒绝）。这样不改例外九；如果你想让它能临时放宽，需要改例外九 |
| 5 | 工作台里加会话索引表（3.4）：索引里存不存标题 | 存标题（已脱敏的那份），否则跨管理器搜索和列表做不了；不存任何提问和回答 |

## 8. 这份方案没有覆盖的

- 没有用真实账号重新验证三家平台的行为；文中“现在的情况”都来自代码和现有测试。
- 没有评估每一期的工作量；批准后按期拆成任务时再估。
- 管理器之间的会话迁移、每会话一个容器的强隔离，不在这次范围内（后者见 `docs/v2/LLM_BRIDGE_PLAN.md` 第 16 节）。
