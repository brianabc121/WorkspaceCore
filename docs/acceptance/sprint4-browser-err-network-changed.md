## 3. 原因（推断，没有复现）

`net::ERR_NETWORK_CHANGED` 是 Chromium 的报错：浏览器检测到宿主机的网络配置变了（网卡增减、地址变化），就把正在进行的请求中断掉。

这个脚本运行期间，会改动宿主机网络的只有一件事：启动模拟 GitHub 容器（`startFakeGitHub`）。

- `docker run -p 127.0.0.1:…` 会在宿主机上新建一对虚拟网卡。
- `docker network connect` 会把容器接进 integrations 网络。
- 新网卡的地址要过一两秒才定下来，IPv6 地址要等重复地址检测结束。

推断是：页面正好在这段时间里有请求在路上（事件流、轮询），就被中断了。

**证据和不确定的地方：**

- 两次失败都发生在容器启动前后几秒内。日志里 `Error response from daemon: No such container: ws-e2e-fake-github` 这一行，标出了脚本启动容器的时间。
- 本地复现失败：在会话沙箱里用真实 Chromium + Docker 试了两种时序，都没有出现这个错误。一种是先起容器、再开浏览器；另一种是浏览器持续发请求时起容器。这个沙箱没有 IPv6，网络环境和 CI 的虚拟机不一样，所以这个结论只能算推断。

## 4. 已经做过的处理

| 任务 / PR | 做了什么 | 结果 |
|---|---|---|
| T-0215 / PR #188 | 把启动模拟 GitHub，从“连接 GitHub”那一步挪到启动浏览器之前 | 不够：PR #189 上又出现了。这次容器在 21:42:18 启动，浏览器随后马上开始加载 |
| T-0217 / PR #190 | ① 模拟 GitHub 在脚本最开头、准备数据之前启动，从容器启动到启动浏览器至少 5 秒；② 只把 `net::ERR_NETWORK_CHANGED` 这一条不算作页面错误 | 待 CI 验证 |

关于第 ② 条：

- 这条错误是浏览器在网络变化时自己报的环境事件，应用本身不会产生。
- 其他控制台错误照常判失败，各步的功能断言也不变。
- 脚本里本来就用同样的办法忽略登录前预期的 401。
- 加它是因为第 ① 条只是按推断调整时序；加上第 ② 条，同一个环境事件就不会再让 CI 偶发变红。

## 5. 再遇到时怎么处理

1. **先确认是这个问题**：
   - 失败的是 `compose` 任务。
   - 失败的步骤是某个浏览器验收（`node tests/e2e/*_browser.cjs`）。
   - 前面各步都“通过”，最后一行带 `net::ERR_NETWORK_CHANGED`。
2. **对时间**：
   - 在日志里找出这一步开始的时间、`No such container: ws-e2e-fake-github`（或其他 `docker run` / `docker compose stop`）的时间，以及失败那一行的时间。
   - 如果失败前几秒内有容器启停，就符合第 3 节的推断。
3. **PR 上的处理**（按 D-0004 和 PR 的处理规则）：
   - 这个 PR 没改相关页面和脚本时，在 PR 上说明一次：失败的检查、为什么不是这个 PR 的问题、指向这份记录。
   - 等同一轮其他任务跑完后，把失败的 `compose` 重跑**一次**。
   - 重跑还失败，就当真实问题查，不再重跑。
4. **如果是别的浏览器验收报这个错**：
   - 看它在页面打开期间有没有起停容器。例如 Sprint 5 浏览器验收会停掉 Prometheus 再启动。
   - 有的话，按第 4 节同样处理：把容器操作挪到打开页面之前，必要时也不把这一条算作页面错误。
5. **怎么拿日志**：
   - 日志很长，要按任务取（`get_job_logs` 带 `job_id`），保存成文件后用 grep 找“失败”和 `##[group]Run node tests/e2e/`。
   - 只取最后几百行可能看不到失败的那一步。
