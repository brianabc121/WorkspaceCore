# 2026-11-03 一键部署脚本：先问完，再在后台运行（T-0094）

## 1. 背景

T-0092 把部署放进 tmux 会话，解决了 SSH 断开会中断部署的问题；T-0093 修了 `curl | bash` 时接不回会话的问题。
但人类指出更根本的问题：tmux 只保证进程不被杀掉，**脚本仍然边做边问**，不仅部署开头要问三个参数，
中途还要确认很多事，其中最典型的是“去浏览器完成首次安装、创建管理员后回到终端按回车”。断线后，部署会停在某个问题上，
等人重新接回终端回答；用户需要一直守着终端。

人类在对话中选定的方案：

- 管理员仍在网页的「首次安装」里创建（密码只在浏览器里输入），脚本**自动检测**是否完成，不用回到终端按回车；
- 后台运行改用**系统服务 + 日志**，不再用 tmux。

## 2. 设计

### 2.1 两段

| 阶段 | 在哪里 | 做什么 |
|---|---|---|
| 前台（plan） | 当前终端，大约一分钟 | 检查系统、域名解析、端口、`.env`，把需要回答的问题**一次问完**，显示汇总并确认；回答写进 `<代码目录>/.deploy/answers.env` |
| 后台（run） | `systemd-run --unit my-workspace-deploy`（没有 systemd 时 `setsid nohup`） | 按回答文件做全部耗时的事，**不再提问**；输出写进 `.deploy/deploy.log` |

前台启动后台后接着显示日志（`tail -F`）。按 Ctrl+C、断开 SSH 都只是不看了；`deploy.sh status`、`deploy.sh logs` 之后随时查看。
再次运行同一条命令（包括 `curl … | sudo bash`）时，发现已经有后台任务在运行，就直接接着显示进度，不会开始第二次部署。

### 2.2 回答

- 原来散落在各个函数里的 `confirm` / `ask` 改为 `decide 键 问题 默认值` / `choose 变量 键 问题 默认值`：
  前台阶段询问并记下；后台阶段只读回答，**没有记下的就按默认值继续并写进日志**，不会停下来等人。
- 前台的 `plan_install` / `plan_connect` / `plan_upgrade` 只检查、只提问，不改系统；问到的键与后台用到的键相同。
  覆盖的问题：安装 Docker / Compose 插件、域名未解析是否继续、ufw 放行 80 / 443、重新生成 `.env`、沿用旧的 `BACKUP_PASSWORD`、
  n8n（是否部署、owner 邮箱、是否用子域名对外与域名）、OpenIM（默认值按内存与磁盘决定）、OpenClaw 接入入口（是否配置、域名或 IP、
  ufw 放行端口）、升级（是否升级、目标提交）。
- 回答文件是 `键=值` 的纯文本（权限 600，目录 700），读取时只接受大写键名、不执行任何内容；**不含任何密码**。
- 需要密码的少数情况不带到后台：`connect` 时如果 n8n 已经有 owner 账号，在前台当场输入并接入；部署（install）的后台遇到这种情况就跳过，
  列为“需要你处理的事项”。后台生成的 n8n 初始密码只加密保存到工作台，不写进日志。
- 升级：前台确认的目标提交（`UPGRADE_TO`）写进回答，后台升级到这个提交，即使远端之后又有了新提交；拉取新代码后用新版本的脚本，
  带着 `--run --answers` 在同一个后台任务里做完剩下的步骤。

### 2.3 网页上的首次安装

服务启动后，后台每 5 秒用 `app.commands.connect status` 检测一次 `setup=done`，最多等 24 小时；状态是 `waiting_setup`。
前台（以及 `status`）看到这个状态时在终端显示网址与安装凭据；**安装凭据不写进日志**。超时后不报错，列为待办：
“在浏览器完成首次安装后运行 `deploy.sh connect`”。

### 2.4 状态与续跑

- `.deploy/state`：动作、状态（`starting` / `running` / `waiting_setup` / `done` / `failed`）、当前步骤、开始与结束时间、进程号、
  失败原因；`.deploy/todo`：需要人处理的事项。后台同一时间只运行一个（`flock`）。
- 失败或被中断（例如服务器重启）后重新运行同样的命令：前台问“沿用上次的回答？”，沿用时不再重复提问。
  各步骤本来就可以重复执行（`.env` 保留、镜像与构建有缓存、已接入的组件跳过），所以重新运行很快到达上次失败的地方。
- 后台运行中不能清空项目（`reset` 会拒绝）。

### 2.5 兼容

- `--foreground`（或 `WORKSPACE_FOREGROUND=1`，旧的 `WORKSPACE_NO_TMUX=1` 也认）：不转到后台，在当前终端边问边做，调试用。
- 从旧版本升级时，旧脚本拉取代码后用 `--after-pull` 启动新版本：新版本在原来的终端里接着做完（不再转到后台）。
- 以前版本的 tmux 部署会话还在时，新脚本提示先接回去处理完（`tmux -L my-workspace attach -t deploy`），避免同时部署两次。
- 部署、升级、接入需要 root：不是 root 时用 sudo 重新运行（后台阶段没有终端，不能再输入 sudo 密码）。
- systemd-run 默认不传环境变量：显式传入 `HOME`（`docker login` 的凭据）、`PATH`、代理变量等。

## 3. 验证

- `services/api/tests/test_deploy_script.py`：回答文件读写（不执行内容、权限）、前台问并记下 / 后台不问、组件选择、
  后台用记下的回答配置接入入口；**真实进程**的端到端：前台提问 → setsid 后台运行 → 前台跟随日志 → 等网页首次安装（安装凭据只在终端）
  → 完成；Ctrl+C 只停止显示、再次运行接着显示同一个任务；失败原因与 `status`、沿用回答重新运行；systemd-run 的参数；
  后台升级到确认过的提交并交给新版本脚本；旧 tmux 会话的提示。
- 本机用真实的 Docker（本会话自己的 dockerd，临时副本 `/…/t94/ws`）：
  1. `deploy.sh install --domain ws.t94.test --email … --answers … --yes`：前台检查、汇总后转到后台（没有 systemd：`setsid nohup`）；
     沙箱代理拦截 PyPI 的 TLS，镜像构建失败——前台显示“后台任务失败：make up 失败”，状态文件记下失败的步骤与原因；
  2. 再次运行同一条命令：提示上次没有完成并沿用回答；这次撞上本机测试留下的 Docker 网段冲突，脚本给出已有的处理提示；
  3. 换网段、临时副本里改用本机已有的镜像后：`make up`、迁移、冒烟检查都在后台通过，HTTPS 检查对测试域名按设计只提醒；
     旧镜像没有 `app.commands.connect`，读不到工作台状态 → 由此加上“读不到时重试 2 分钟，仍然不行就列为待办”；
  4. 用当前代码构建 api 镜像后运行 `deploy.sh connect`：后台进入“等待首次安装”，`status` 在终端显示网址与安装凭据，
     日志里没有安装凭据；调用首次安装接口（和浏览器一样）创建管理员后，后台 4 秒内检测到并接着接入组件，前台以 0 退出。
  另外发现并修正：前台跟随日志时任务失败会多打印一行 ERR 陷阱的信息（改为直接按结果退出）；Docker Hub 限流有时只报
  `429 Too Many Requests`，拉取镜像的重试现在也认这种写法。
- `shellcheck -S warning`（koalaman/shellcheck:v0.10.0）没有警告。
