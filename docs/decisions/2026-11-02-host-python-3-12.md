# ADR：服务器上的项目脚本使用 Python 3.12（T-0074）

- 状态：已采纳（2026-11-02，人类在对话中要求“一键部署时把服务器的 Python 升级到 3.12”）
- 关联：`scripts/deploy.sh`（T-0072）、`scripts/init_env.py`（T-0068，仍兼容 3.8+）、`services/api/Dockerfile`（`python:3.12.15-slim-trixie`）

## 1. 背景

应用本身（api、worker）跑在 Docker 镜像里，镜像自带 Python 3.12，与服务器上的 Python 无关。
服务器上用到 Python 的只有仓库里的辅助脚本：`make env`（`scripts/init_env.py`）、`deploy.sh` 改写 `.env`、备份脚本解析 JSON、`make perf`。
CI 用 3.12 运行这些脚本，而服务器自带的版本五花八门（Debian 11 是 3.9，Debian 12 是 3.11，Ubuntu 22.04 是 3.10，Debian 最小安装可能没有 python3）。
人类部署时就在 3.9 上遇到过 `TypeError`（T-0072 已修）。服务器上统一用 3.12，脚本的运行环境就和 CI、镜像一致。

## 2. 决定

- **不替换系统自带的 `python3`。** apt、`add-apt-repository`、`unattended-upgrades` 等系统工具依赖发行版的 `python3` 和它的模块；
  替换或用 `update-alternatives` 改指向都可能把系统弄坏，所以 3.12 与系统的 python3 并存。
- `deploy.sh` 的 `ensure_python`：已有能用的 `python3.12`（例如 Ubuntu 24.04 自带的，或用户自己装的）就直接用；
  没有时下载 python-build-standalone 的独立构建，解压到 `/opt/my-workspace/python-<版本>`（属主 root，其他用户只读），
  链接为 `/usr/local/bin/python3.12`。下载先校验 SHA-256，不一致就停止，什么都不装。
- `/usr/local/bin/python3.12` 已存在、不能用、又不是本脚本装的：停止并提示，不覆盖用户的文件。
- 本脚本装过的旧版本（`/opt/my-workspace/python-*`）在锁定版本改变后，下次部署或升级时自动换成新版本并删掉旧目录。
- `Makefile` 的 `PYTHON` 与备份脚本优先用 `python3.12`，没有时退回 `python3`（开发机上不强制装 3.12；`init_env.py` 仍兼容 3.8+）。
- 清空项目（包括删除代码目录）不删除 `/opt/my-workspace` 里的 Python：它是服务器上的工具，不含项目数据。

## 3. 锁定的版本与来源

| 项目 | 值 |
|---|---|
| 发行方 | python-build-standalone（Astral 维护，uv 安装 Python 时用的同一套构建）：`https://github.com/astral-sh/python-build-standalone` |
| 构建 | `20261026`（2026-10-26 发布） |
| Python | `3.12.16`（3.12 系列在该构建中的最新版本） |
| 变体 | `install_only_stripped`（去掉调试符号，约 35 MB），glibc 版：`x86_64-unknown-linux-gnu`、`aarch64-unknown-linux-gnu` |
| x86_64 SHA-256 | `ce4f6d0a6cfdb3bed6e44c2f9affd85943c76a42e25ad3a259002f31d6fb8a20` |
| aarch64 SHA-256 | `bb4b6392670c5d3f93876996fcaa19858a4a413a0c7720144c18b0d6f1f0db2d` |
| 下载地址 | `https://github.com/astral-sh/python-build-standalone/releases/download/20261026/cpython-3.12.16%2B20261026-<架构>-unknown-linux-gnu-install_only_stripped.tar.gz`；GitHub 下载失败时用 Astral 的镜像 `https://releases.astral.sh/github/python-build-standalone/releases/download/…`（同一文件，同样校验） |

核验方法（2026-11-02）：

1. 从 PyPI 查到 uv 的最新版本 0.13.6（2026-10-27 上传），用它列出 3.12 的可下载版本：最新是 `cpython-3.12.16`，构建 `20261026`；
2. 下载该构建发布页上的 `SHA256SUMS`，取出上表两个文件的校验和；
3. 下载两个安装包，`sha256sum -c` 与 `SHA256SUMS` 一致；
4. 再用 uv 0.13.6 安装同一版本（uv 用它内置的校验和验证下载），解压结果与第 3 步的文件逐个比较：除 uv 自己加的 `BUILD`、改写的
   `_sysconfigdata` 与 `EXTERNALLY-MANAGED` 外完全相同。两个来源的校验和一致；
5. x86_64 版解压后的 `python3.12` 在 Debian 11 / 12、Ubuntu 22.04 / 24.04 的容器里都能运行（`ssl`、`sqlite3`、`json`、`secrets` 可以导入）；
   aarch64 版只核对了校验和，没有在 ARM 机器上运行过。

需要 glibc 2.17 以上（以上发行版都满足）；不支持 musl（Alpine）和其他架构，遇到时脚本提示手动安装 `python3.12`。

## 4. 以后升级

1. 用最新的 uv 运行 `uv python list 3.12 --only-downloads --show-urls`，得到最新的 3.12 版本和构建日期；
2. 下载该构建的 `SHA256SUMS`，取出 `cpython-<版本>+<构建>-{x86_64,aarch64}-unknown-linux-gnu-install_only_stripped.tar.gz` 两行；
3. 改 `deploy.sh` 里的 `PY_VERSION`、`PY_BUILD`、`PY_SHA256_X86_64`、`PY_SHA256_AARCH64`，并更新本文第 3 节；
4. 已部署的服务器下次运行 `deploy.sh upgrade` 时会自动换成新版本。

`services/api/tests/test_deploy_script.py` 检查锁定的小版本与 api 镜像一致、校验和格式正确、`deploy.sh` 不直接调用系统的 `python3`。
