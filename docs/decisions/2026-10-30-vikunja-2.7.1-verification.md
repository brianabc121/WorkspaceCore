## 1. 结论

| 项目 | 结论 |
|---|---|
| 锁定版本 | Vikunja **2.7.1**，镜像 `vikunja/vikunja:2.7.1@sha256:f7dc8428d10aef17f3075886d3c1c022f566ec456f88985f02c137f4fc534576` |

| 认证 | 带权限范围的 API Token（`tk_` 前缀，Bearer），必须设置过期时间；最小权限见第 3 节 |

| 部署 | 独立 Compose `infra/vikunja/compose.yaml`，经受控网络 `integrations` 与工作台互通；关闭自助注册；为让 Webhook 发到私有地址打开了 `outgoingrequests.allownonroutableips`（风险与缓解见第 6 节） |

## 3. API v2、认证与最小权限

- 实例上 `/api/v2/openapi.json`（`application/openapi+json`）与 `/api/v2/docs` 可用；`/api/v1/docs.json` 仍然存在，但 Connector 不使用 v1。
  两个独立启动的实例导出的文档除 `servers` 外完全相同。存档：`infra/vikunja/openapi/vikunja-2.7.1-api-v2.json`
  （去掉实例地址、按键排序；SHA-256 `26f814bba64d350839b2ad4793f1b7181752f7ac21b233f5c5d2c7713c93f83a`），作为契约测试的基准。
- 认证方式（`components.securitySchemes`）：`APITokenAuth`（Bearer，`tk_` 前缀，按权限范围授权）、`JWTKeyAuth`（用户登录会话）、
  `BasicAuth`（只用于通知订阅源）。**Connector 只用 API Token**，不保存用户的 Vikunja 密码。
- Token 由用户在 Vikunja 原生界面（或 `POST /api/v2/tokens`，需要登录会话）创建：
  - `permissions` 是 `{分组: [动作]}`，可用的值来自 `GET /api/v2/routes`；同一个动作同时覆盖 v1 与 v2 路由
    （实测只授 `tasks.create` 就能调用 v2 的 `POST /projects/{project}/tasks`）；
  - `expires_at` 必填（不填返回 422 `non zero value required`），明文 Token 只在创建时返回一次，可以 `DELETE /tokens/{id}` 吊销；
  - Token 以创建者的身份访问，只能看到创建者有权限的项目。
- Sprint 3 需要的最小权限：

  | 分组 | 动作 | 用途 |
  |---|---|---|
  | `projects` | `read_all`、`read_one` | 项目列表与详情 |
  | `tasks` | `create`、`read_all`、`read_one`、`update`、`delete` | 任务读写 |
  | `projects_webhooks` | `create`、`read_all`、`update`、`delete` | 可选：由工作台自动为每个项目注册 Webhook |
  | `labels`、`tasks_labels` | `read_all`；`create`、`delete`、`read_all` | 可选：需要写标签时才授予（第 5.2 节） |

- 越权与失效的表现：Token 无效、过期**或缺少该动作的权限**都返回 **401**，响应体是旧格式 `{"code":11,"message":"…invalid token…"}`，
  三者无法区分；Token 有效但创建者对该项目没有权限时返回 **403**（problem+json，`detail` 为 “You don't have the permission to see this”）。
- 多用户场景可以用 bot 用户（`/api/v2/user/bots`，用户名以 `bot-` 开头，由真实用户创建并给它分享项目）作为独立的服务身份；
  V1 个人模式先用用户本人的受限 Token（规范 7.1），以后多用户映射时重新评估。

## 4. 项目与任务接口

| 操作 | 端点 | 说明 |
|---|---|---|
| 项目列表 | `GET /api/v2/projects` | `page`（从 1 开始）、`per_page`（默认并最多 `max_items_per_page`=50，超过时静默截断）、`q`、`is_archived`、`expand=permissions`（返回 `max_permission`：0 读、1 读写、2 管理） |
| 全部任务 | `GET /api/v2/tasks` | 分页参数同上；`filter`（`=`、`!=`、`>`、`>=`、`<`、`<=`、`like`、`in`、`not in`，用 `&&` / `\|\|` 组合）、`filter_timezone`、`sort_by` / `order_by`、`q`、`expand` |
| 项目内任务 | `GET /api/v2/projects/{project}/tasks` | 同上 |
| 创建任务 | `POST /api/v2/projects/{project}/tasks` | 201，返回 Task；项目取自路径 |
| 读取任务 | `GET /api/v2/tasks/{task}` | 200 + `ETag`（形如 `"1793368827000000000-2"`）；文档说明可用 `If-None-Match` 得到 304（未实测） |
| 修改任务 | `PATCH /api/v2/tasks/{task}` | `application/merge-patch+json` 或 `application/json-patch+json`；未知字段 422；`PUT` 会整体替换，不使用 |
| 删除任务 | `DELETE /api/v2/tasks/{task}` | 204 |

- 列表响应体：`{items, page, per_page, total, total_pages}`（不靠响应头分页）。
- 增量同步：`filter=updated > <时间>` 与 `sort_by=updated` 可用（实测）。响应里的 `updated` 只精确到秒（创建时的响应带纳秒），
  所以游标要用 `>=` 并留重叠窗口，按 (任务 ID, `updated`) 去重。
- 错误：v2 校验与业务错误是 problem+json（`title`、`status`、`detail`、可选的 Vikunja `code`、`errors[]`）；
  **`errors[].value` 会回显请求内容**，日志与返回给前端时都要去掉。401 用旧格式（第 3 节）。
- 富文本：任务 `description` 存为 HTML。加 `?format=markdown`（`PATCH` 用请求头 `X-Vikunja-Format: markdown`）可以按 GFM 读写；
  写入时原始 HTML 会被去掉（实测 `<script>` 被移除）。工作台按 Markdown 文本读写，前端只按纯文本显示，不渲染 HTML。

## 5. 字段与行为

### 5.1 Task 字段（Sprint 3 用到的部分）

| Vikunja 字段 | 类型 / 取值 | 说明 |
|---|---|---|
| `id` | int64 | 全局唯一；外部 ID 用 `vikunja:task:<id>` |
| `project_id` | int64 | 修改为其他项目即移动任务（需要目标项目的写权限） |
| `index`、`identifier` | int64、string | 项目内序号；`identifier` 形如 `PROJ-12`，项目没有标识时为 `#<index>` |
| `title` | string，至少 1 个字符 | 空标题 422 |
| `description` | string（HTML / Markdown，见第 4 节） | |
| `done`、`done_at` | bool、date-time | `done_at` 由服务端设置 |
| `priority` | int64 | 前端常量 0 未设置、1 低、2 中、3 高、4 紧急、5 立即（`frontend/src/constants/priorities.ts`，tag v2.7.1）；**API 不校验范围**（实测 9 也被接受），工作台自己限制为 0–5 |
| `due_date`、`start_date`、`end_date` | date-time | **未设置时为 `0001-01-01T00:00:00Z`**，工作台映射为 `null`；merge-patch 写 `null` 会清空为该零值 |
| `labels` | Label[]（只读） | 要用标签端点（`/tasks/{task}/labels`）增删，标签需先存在 |
| `assignees` | User[]（只读） | Sprint 3 不处理 |
| `percent_done` | 0–1 | |
| `created`、`updated` | date-time（只读） | `updated` 作为外部更新时间（`source_updated_at`） |
| `deleted_at` | date-time（只读） | 接口返回里始终为 null（删除后整条消失，第 1 节） |
| `bucket_id`、`position`、`repeat_*`、`reminders` | | 视图与重复规则，Sprint 3 不处理 |

Project 字段：`id`、`title`、`description`、`identifier`、`hex_color`、`is_archived`、`parent_project_id`（0 为顶层）、`max_permission`、`created`、`updated`。

### 5.2 统一 DTO 的映射建议（T-0019 定稿）

- ProjectDTO：`id = "vikunja:project:<id>"`，`title`，`archived = is_archived`，`parent_id`（0 → null），`source_url = <VIKUNJA_PUBLIC_URL>projects/<id>`。
  原生界面的路由 `/projects/:projectId`、`/tasks/:id` 见 tag v2.7.1 的 `frontend/src/router/index.ts`。
- TaskDTO（规范 6.3）：`id = "vikunja:task:<id>"`，`project_id = "vikunja:project:<project_id>"`，`title`，
  `description`（Markdown 文本），`status = done ? "done" : "open"`，`priority`（0–5），`due_at`（零值 → null），
  `labels`（标签标题，Sprint 3 是否支持写入由契约决定；写入需要额外权限和多次调用），
  `source_url = <VIKUNJA_PUBLIC_URL>tasks/<id>`，`source_updated_at = updated`。
- `tested_version`：集成的元数据里记录 `{"tested_version": "2.7.1", "api_version": "v2"}`，并在测试连接时保存 `/api/v2/info` 报告的实例版本；
  两者不一致时在集成状态里提示，不自动信任新版本。

### 5.3 并发

`GET` 返回 ETag，但 `PATCH` 带着过期的 `If-Match` 照样成功（实测 200），没有 412。Vikunja 侧只有“后写覆盖”。
工作台若要避免覆盖别人的修改，只能在写入前读取并比较 `updated`（读与写之间仍有窗口，契约里写明）。

### 5.4 幂等与结果未知

Vikunja 不识别幂等键，同一请求发两次就有两个任务。`POST` 超时或连接中断时结果未知：
不能直接重试；先在目标项目里按 `filter=created >= <发送时间 - 余量>` 查找标题相同、由 Token 所有者创建的任务，找到就当作成功，
找不到再由用户确认是否重试（规范 4.1）。`created` 的过滤实测可用。

## 6. Webhook

- 注册：`POST /api/v2/projects/{project}/webhooks`，`{target_url, events, secret, basic_auth_user, basic_auth_password}`，
  需要该项目的写权限；`secret` 与 Basic Auth 只写不读。**用户级 Webhook（`/user/settings/webhooks`）只支持
  `task.overdue`、`task.reminder.fired`、`tasks.overdue`**，所以任务变化必须按项目注册；新建的项目需要补注册（对账时检查）。
- 可订阅事件（`GET /api/v2/webhooks/events`，19 个）：`project.deleted`、`project.shared.team`、`project.shared.user`、`project.updated`、
  `task.assignee.created`、`task.assignee.deleted`、`task.attachment.created`、`task.attachment.deleted`、`task.comment.created`、
  `task.comment.deleted`、`task.comment.edited`、`task.created`、`task.deleted`、`task.overdue`、`task.relation.created`、
  `task.relation.deleted`、`task.reminder.fired`、`task.updated`、`tasks.overdue`。Sprint 3 至少需要 `task.created`、`task.updated`、`task.deleted`、`project.updated`、`project.deleted`。
- 投递（实测 3 次，全部签名校验通过；源码 `pkg/models/webhooks.go` 的 `sendWebhookPayload`，tag v2.7.1）：
  - `POST`，`Content-Type: application/json`，`User-Agent: Vikunja/v2.7.1`；
  - 设置了 secret 时带 `X-Vikunja-Signature`：对**原始请求体**做 HMAC-SHA256，十六进制小写；设置了 Basic Auth 时再带 `Authorization`；
  - 请求体 `{"event_name": "task.updated", "time": "<RFC 3339，纳秒>", "data": {"doer": {...}, "project": {...}, "task": {...}}}`；
    `doer` 只有 `id`、`username`、`name`、`created`、`updated`（不含邮箱）；`task.deleted` 的 `task` 是删除前的最后状态。
- **没有时间戳头、没有投递 ID**：签名挡不住重放。工作台按事件去重：建议 `event_key = sha256(原始请求体)`（请求体含纳秒级 `time`），
  并且处理时以任务的 `updated` 判断新旧，旧事件不覆盖新数据。
- 送达与重试：异步投递，单次超时 `webhooks.timeoutseconds`（默认 30 秒）。目标返回非 2xx 或连接失败时，实测在约 2.3 秒内共尝试 6 次，
  之后丢弃（日志 `handler_poisoned`），不会再补发。**接收端短暂不可用超过几秒就会永久丢事件**，周期对账是必需的。
- SSRF 防护：`outgoingrequests.allownonroutableips` 默认 false，发往私有地址的 Webhook 会被拒绝
  （实测 `prohibited IP address: 172.17.0.1 … denied by: 172.16.0.0/12`）。

**部署取舍**：同机部署时，Webhook 的目标是 integrations 网络里的 caddy（私有地址），所以 `infra/vikunja/compose.yaml` 打开了
`VIKUNJA_OUTGOINGREQUESTS_ALLOWNONROUTABLEIPS=true`。风险：任何能创建 Webhook 的 Vikunja 用户都可以让 Vikunja 请求它能到达的内网地址。缓解：
1. 关闭自助注册（实测 `POST /register` 返回 404），只有管理员用 `make vikunja-user` 创建的人能登录；
2. Vikunja 只加入自己的默认网络和 integrations 网络，能到达的只有 caddy、api、worker，碰不到工作台的 PostgreSQL / Redis
   （实测从 Vikunja 解析不到 `postgres`、`redis`）；
3. 多人使用或对外开放注册时，改为关闭该选项，设置 `outgoingrequests.proxyurl` 走只放行工作台地址的出站代理（官方建议的 mole）。

## 7. 错误与限流 → Connector 错误分类（规范第 7 节）

| Vikunja 响应 | 分类 | 工作台的处理 |
|---|---|---|
| 401（`code` 11） | `AUTH_FAILED` | 集成状态改为 unauthorized，提示重新配置 Token；不重试 |
| 403 | `AUTH_FAILED`（资源级） | 该资源无权访问；不改集成状态 |
| 404（任务 `code` 4002） | 资源不存在 | 读取时作为 tombstone 候选（结合对账确认） |
| 422 | `VALIDATION_FAILED` | 去掉 `errors[].value` 后再记录或返回 |
| 429（`Retry-After` 秒数，`X-Ratelimit-Limit` / `-Remaining` / `-Reset`） | `RATE_LIMITED` | 按 `Retry-After` 退避；不把空结果当作正常 |
| 5xx、连接失败、读超时（读操作） | `UNAVAILABLE` | 有限重试 + 退避；首页模块显示 stale / unavailable |
| 写操作超时或连接中断 | `TIMEOUT_UNKNOWN` | 不重试，按第 5.4 节查询结果 |

限流默认关闭（`ratelimit.enabled=false`）；打开后按用户计数，超限返回 429 `{"message":"Too Many Requests"}`（实测）。

## 8. 部署（`infra/vikunja/compose.yaml`）

- 独立的 Compose 项目，镜像带 digest；`read_only` 根文件系统、`cap_drop: ALL`、`no-new-privileges` 下运行正常（实测健康检查 `vikunja healthcheck` 通过）。
- 数据：SQLite（`/db/vikunja.db`）与附件目录，各用一个卷；卷第一次创建时属 root，由一次性的 `volume-init` 改为 uid 1000
  （不改会启动失败：`permission denied`）。V1 个人使用 SQLite 足够；改用 PostgreSQL 时另行核验。
- 配置：`VIKUNJA_SERVICE_SECRET` 必填（2.7.1 中旧的 `service.jwtsecret` 已弃用；不设置时每次重启随机生成，已签发的登录与 Token 全部失效）；
  关闭自助注册与 CORS（原生界面与 API 同源）；原生界面默认只绑定 `127.0.0.1:3456`。
- 网络：core 的 `compose.yaml` 新增内部网络 `integrations`（caddy、api、worker 加入），Vikunja 以 external 方式加入。实测：
  api 与 worker 能访问 `http://vikunja:3456/api/v2/info`；Vikunja 发往 `http://caddy:8080/api/v1/webhooks/vikunja/<id>` 的 Webhook 送达 api。
- 工作台侧（T-0020）：集成的 `base_url` 要做 SSRF 防护，同时允许管理员显式配置的 Vikunja 地址（如 `http://vikunja:3456`），不能因为它是私有地址就拒绝。

- 未测试：Vikunja 使用 PostgreSQL / MySQL、CalDAV、大量数据的分页性能、Webhook 的 Basic Auth、标签写入流程。

## 10. 后果

- T-0019 契约：ProjectDTO / TaskDTO 按第 5.2 节；修改的并发语义按第 5.3 节写明；创建任务的结果未知按第 5.4 节；
  Webhook 端点按第 6 节校验 `X-Vikunja-Signature`、按请求体哈希去重；错误分类按第 7 节。
- T-0020：Connector 只用 v2 与 API Token；以存档的 OpenAPI 做契约测试；`base_url` 的 SSRF 防护需要允许显式配置的地址。
- T-0021：每个项目注册 Webhook（或提示用户手动注册）；对账必须覆盖删除（全量差集）和丢失的事件。
