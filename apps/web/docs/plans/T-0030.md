# T-0030 Knowledge and Calendar Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement each task in this session, then request one independent whole-branch review.

**Goal:** Deliver knowledge bookmarks, a shared calendar, related documents and two dashboard cards.

**Architecture:** Reuse the authenticated OpenAPI client, workspace-keyed Vue Query caches, existing forms, dialogs and theme variables. Pages remount for user/workspace changes. Knowledge is metadata only; every request goes to the BFF.

**Tech Stack:** Existing Vue 3, TypeScript, Vue Query, vee-validate, Zod and Vitest; no new dependencies.

**Spec:** `.collab/tasks/T-0030-sprint-4-frontend-knowledge-calendar.md`, `docs/decisions/2026-10-30-sprint-4-knowledge-search-contract.md`, `docs/DEVELOPMENT_SPEC.md` sections 7.2 and 8.

## Global Constraints

- Node 22 and `npm ci`; edits limited to `apps/web/**`, optional `ci-web.yml`, and the task file.
- Do not modify generated `src/services/schema.d.ts`, backend contracts or `docs/TASKS.md`.
- Explicit `X-Workspace-Id`; query keys include user and workspace; never retain inaccessible cached content.
- Viewer reads only; source management requires admin; only a bookmark's creator changes visibility.
- All local writes carry versions where required; unknown results and conflicts require a read refresh, never an automatic write retry.
- Plain text notes; safe external URLs; no requests to AFFiNE.
- Calendar uses agenda plus week view. End boundaries are exclusive. Timed inputs use the selected IANA timezone, with nonexistent DST times rejected.

## Review Focus

- A delayed write or query from the prior workspace must not populate the current page or card.
- Changing a bookmark must preserve linked resources that are absent from a partial options list.
- All-day events spanning multiple dates must respect the exclusive end, including DST weeks.
- Authorization loss must hide previously loaded resource data; an ordinary refresh failure may show clearly marked stale data.
- A successful write followed by a failed refresh must not invite a duplicate submission.
